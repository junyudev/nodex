# Dictation Behavior

## Intent

Dictation turns a bounded microphone recording or selected WebM file into text. It runs in the Electron app and is separate from realtime voice conversation. Service policy admits capture; transcription requests require ChatGPT authentication. This document owns the user-visible Composer, global dictation, Voice settings, recording recovery, and error behavior.

## Capability and ownership model

- Main publishes one capability snapshot for Composer, global dictation, streaming, sounds, account dictionary, history, semantic cleanup, authentication, and the current microphone owner. Each capability change independently updates its consumers.
- Composer requires ChatGPT authentication. Global capture can be available with another authenticated method or a runtime that does not require login, when its service gates and native capabilities allow it. This does not grant backend transcription access: requests still require valid ChatGPT credentials.
- `microphoneOwner` is the mutual-exclusion authority. Dictation cannot start while realtime voice owns the microphone; realtime voice cannot take ownership from an active dictation session.
- A capture surface owns its `DictationSessionController`, `MediaStream`, recorder, waveform graph, AudioWorklet, and streaming session protocol. Main owns the authenticated WebSocket for each attempt. Detaching a Composer finishes captured speech into its owning draft; incomplete acquisition is cancelled. Explicit cancellation and application teardown stop every track and invalidate late results. Activation remains exclusive through transcription and delivery.
- Main owns microphone permission, settings, recording history, streaming credential preparation, global hotkeys, the auxiliary window, and cross-application paste.
- Composer and the global bar use the same capture controller contract. Composer inserts or submits text; global dictation pastes into the foreground application at delivery.
- Capture availability follows the current authentication lifetime, default-host feature, dictation admission, workspace policy, and native capabilities. Global capture and streaming are standard capabilities of admitted sessions and do not depend on remote rollout assignment. Packaged dictation sounds remain configurable independently of service policy; the account dictionary retains its service gate. Policy initializes from authenticated bootstrap when available and otherwise uses the service SDK; live evaluations update admission without restarting the app. Account mutations revoke pending requests before switching credentials, invalidate cached policy, and close account-specific editing. Missing dictation-admission or account-dictionary evaluations do not enable those capabilities.

## Composer behavior

- The active Thread Composer shows a `Dictate` button when capture is supported. Clicking begins recording. Holding the configured Composer shortcut begins on keydown and stops on keyup.
- Ordinary Composer recording uses compact inline microphone feedback and keeps the editor available. Without streaming, recording uses a `cancel | waveform | stop | send` footer; the scrolling waveform advances at 30 px/s. `Stop dictation` transcribes and inserts; `Transcribe and send` inserts through the ordinary Composer path and submits through the ordinary submit policy.
- Transcription retains its active presentation until delivery. An insert action can still upgrade to send; the send-transcription presentation hides the microphone control.
- A stop action may upgrade from insert to send while finalization is in progress, but text is applied exactly once. Cancel during recording or transcription applies no text.
- Buffered text replaces the current editor selection with word boundaries preserved; without an editor selection, it appends at the end. Existing whitespace is retained rather than duplicated.
- Streaming revisions update editor-owned ranges. Moving the selection or authoring a document transaction starts a new segment. Late revisions preserve the current caret; IME composition queues updates. Cancellation restores only untouched recoverable ranges, preserving user edits. A single segment accepts the full final transcript; multiple segments retain their placements. The editor remains mounted throughout capture and can reconcile completion with a persisted draft after detaching.
- Interrupted or failed transcription preserves recognized text and exposes recovery in the Composer. Automatically recovered text waits for `Add to message`; an explicit `Retry` appends its successful result while that Composer remains mounted. A retry completed after detachment stays in recording history without appending. `View recording` opens that recording in Voice settings, creating a primary window if necessary, and `Dismiss` leaves history intact. Recovery never automatically submits a message.
- The visible transcript behavior after insertion or send remains governed by [Codex Thread Transcript Behavior](codex-thread-transcript-behavior.md).

## Session lifecycle

The controller has explicit idle, permission/acquisition, recording, stopping, transcribing, retryable-error, and disposed states. Only one session and one acquisition generation may be current. React Effect cleanup detaches the surface without permanently disabling its retained controller; subsequent Effect setup remains able to start dictation. Recovery tracks saving/saved/unavailable audio separately from recovering/recovered/failed transcription.

- Permission completes before `getUserMedia` begins. A release, cancel, replacement start, unmount, or capability change invalidates the generation; a late stream is stopped immediately and cannot activate recording.
- The device policy tries the selected microphone, then the current built-in microphone hint when macOS is routing input/output through Bluetooth, then the system default, then the first real input. Permission or security failures never trigger device fallback. A missing, busy, or unsupported route may continue to the next safe candidate.
- `MediaRecorder` records continuously and emits recovery chunks every five seconds. An `AudioWorklet` separately produces mono PCM16 frames for streaming and never owns the durable recording.
- Recordings shorter than 250 ms, or with no audio chunk, are cancelled locally and are not uploaded. Composer-owned capture stops once at 595 seconds (9 minutes 55 seconds), saves the recording, and follows ordinary transcription and insertion without automatically sending the message or showing a desktop duration-limit error. This limit still applies when a global shortcut routes into an eligible Composer. The standalone global bar has no local recording-duration timer; stream expiry or failure leaves buffered capture running until the user stops, then ordinary buffered recovery transcribes the retained audio. Duration policy belongs to the capture owner rather than the session's diagnostic surface.
- Recording duration freezes when capture stops and excludes subsequent transcription, cleanup, and retry waits. Stream finalization begins at stop intent and overlaps the recorder's terminal data delivery; PCM is flushed before microphone tracks stop. Recorder errors, ended tracks, repeated stop/cancel, and late transcription results cannot finalize or apply a session twice.

## Transcription and recovery

- Eligible ChatGPT sessions always attempt streaming when no explicit language is selected, while retaining the complete `MediaRecorder` recording. Missing or false remote streaming rollout values, including later live updates, do not disable this capability. Authentication, workspace permission and routing constraints still apply. A caller's optional language lookup runs once inside the session activation lease; ordinary Codex Composer omits it.
- A trusted renderer transfers one dedicated RPC port per streaming attempt. Main prepares the authenticated backend route and owns a Node WebSocket to `/dictation/stream?dictation_surface=composer|global`; the renderer receives only a send/dispose capability and selected diagnostics. Authorization, account identity, desktop originator, versioned User-Agent, and the preferred system language stay in Main. The socket offers `chatgpt-dictation` and `codex-desktop`, permits no redirects, and bounds messages at 8 MiB. Socket creation, preparation/start/finish timeout, malformed events, failed transcripts, or abnormal closure disables only that attempt.
- Streaming and buffered transcription share authenticated workspace routing, destination network permissions, and account revocation. When the primary runtime lacks supported routing discovery, Main uses the verified bundled routing runtime with an ephemeral credential store, checks the same network and residency constraints, and scopes the result to the account and host generation. Unknown or conflicting routes fail explicitly. Main resolves the actual WSS endpoint through Electron's proxy rules and uses the selected HTTP, HTTPS, or SOCKS proxy; proxy setup failure never silently switches to a direct connection. Production endpoints require TLS; plaintext is allowed only for loopback development services.
- A successful non-empty streaming final is used directly and does not send a buffered request.
- A failed single stream falls back to the complete recording. Explicit segment boundaries retain per-segment PCM: recovery uploads only failed nonempty segments as mono PCM16 WAV, preserves completed segments, and does not duplicate their text. Abort never falls back. Recovery-capable surfaces preserve existing editor text and require an explicit action to add automatically recovered text.
- A silent-output AudioContext and mono AudioWorklet are prepared ahead of capture and warmed again after teardown. The worklet batches 2048 float samples, transfers them within the renderer, and flushes a partial tail before acknowledging stop. The renderer applies gain before signed PCM16 encoding: RMS target 0.063, silence threshold 0.003, gain cap 4, peak cap 0.708, immediate gain reduction, and gain increases smoothed by 0.35. Silence resets gain to 1; PCM conversion truncates toward zero.
- Audio can accumulate while the WebSocket starts; queued frames drain after `session.started`. Preparation and startup each have a 10-second deadline; startup distinguishes a missing WebSocket handshake from a missing session acknowledgment. First-audio timeout is 2 seconds and audio-flush timeout is 1 second. Composer session-close timeout is 60 seconds; the global bar uses 8 seconds. Composer supplies recording and segment-attempt identities; the standalone global bar omits them. `session.close` follows the tail-frame acknowledgment and completed connection startup. Success requires the service's `session.updated` acknowledgment with status `closed`; a WebSocket close without that acknowledgment triggers recovery even with close code 1000. Fatal session errors and failed transcripts also trigger recovery.
- Final text preserves first-observed utterance order and the highest final revision. Every observed utterance must have a final revision before the stream result can be used; unfinished utterances trigger recovery from the full recording instead of inserting partial text. Asset lifecycle events are accepted without affecting text. Successful empty results and failures on known-silent audio finish without inserting text or uploading the same silent recording. Silence requires the completed AudioWorklet capture and its tail-frame receipt; a failed startup's partial audio cannot suppress buffered recovery.
- Streaming diagnostics retain selected request metadata, proxy type, HTTP rejection status, edge-challenge classification, and categorical network failures. They never retain tokens, account identifiers, routing URLs, response bodies, or raw native errors.
- Each new recording can attempt streaming again after a failed connection. Capability availability describes permission to attempt streaming; only the per-attempt connection evidence proves whether a socket opened or its result was used.
- The standalone global bar reads the same capability snapshot through its own sandboxed preload before choosing a transport. An unavailable or unknown capability, an explicit language, and a failed capability read remain distinct diagnostic reasons when no WebSocket is attempted. A failed capability query preserves buffered capture and records `capability-read-failed` rather than silently presenting an empty connection report.
- A retryable buffered failure preserves the same recording and offers `Retry`; retry does not ask the user to speak again.
- Composer, global dictation, and history retry preserve the raw transcription result. The optional semantic-cleanup transport is not enabled by these surfaces.
- Empty successful transcription cancels provisional text without an error. Recovery that still yields no text remains retryable. Composer start failures use the app-owned notification surface; retained-audio recovery uses the inline recovery actions.

## Recording history and Voice settings

Settings → Voice owns:

- input-device selection, including `System default` and an explicit unavailable selection;
- an inline Dictation shortcut for hold and double-tap activation, with an independent Single-tap shortcut inside Advanced; both share the chord recorder with Settings → Keyboard shortcuts;
- the account voice-language preference; ordinary Codex Composer leaves language unspecified, while callers that explicitly use this preference route a selected language through buffered transcription;
- a single Dictation sounds preference, enabled by default, that controls Composer and standalone global feedback;
- an account Voice dictionary when permitted, with a device-local dictionary fallback for global dictation;
- the twenty most recent recoverable recordings.

Capture controls require Composer or global availability. Recording history remains available independently of capture and authentication; local copy, download, and deletion do not require login. Transcription and retry require ChatGPT authentication. On supported platforms, global shortcuts and the device-local dictionary remain visible and editable while capture is unavailable, authentication changes, or the native runtime recovers. Configuration follows the command keymap's platform availability rather than live capture admission. A Dictation section is shown only when it contains a setting. Editing an enabled macOS global binding requests Input Monitoring and Accessibility permission; startup, shortcut removal, and unrelated keymap edits do not prompt.

Account dictionary operations capture the account and user once and reject identity changes. Entries are trimmed on add and limited to 100 characters; the list limit is the smaller of the service limit and 200. Import requires an explicit preview and confirmation, adds selected local entries sequentially, and removes only the successfully processed exact local entries after the complete import succeeds. Duplicate entries can be accepted, but account-change, cancellation, and request failures preserve the local originals. Closing the dialog cancels pending operations.

Shortcut capture waits for a non-modifier key before committing a chord, so pressing Control and then Y records `Ctrl+Y`, not `Ctrl`. Modifier-only global bindings commit after release and preserve supported left/right identities. A focused macOS shortcut editor captures bare gestures through the native boundary, including Fn combinations that do not reliably produce DOM key events. Existing global bindings remain suspended during capture; committing a regular chord, cancellation, focus loss, navigation, or renderer teardown ends native observation and restores registrations.

The Dictation shortcut is always visible on supported platforms. Advanced reveals the optional Single-tap shortcut; closing it cancels unfinished capture. Each shortcut can be edited or cleared independently, and the two shortcuts must use different keys. Clearing one preserves the other and all other Voice settings.

Ordinary shortcut capture is layout-aware. In particular, Option-modified character output such as `¥` is never persisted as the shortcut key: Nodex records the logical key for the current keyboard layout and Main compiles it to the corresponding macOS physical key code. A keyboard-layout change refreshes the native binding set without changing the shortcut shown to the user. If the browser layout API is unavailable, Nodex uses its complete deterministic default map.

An ordinary global shortcut must contain exactly one supported non-modifier key and at least one of Cmd/Ctrl or Alt. Shift does not qualify by itself. Invalid unmodified chords such as `Y` and `Shift+Y` leave the previous setting unchanged and show `Shortcut must include Cmd/Ctrl or Alt.` Supported macOS bare bindings include Fn, left Control, left/right Option, left/right Command, supported double-modifier forms, and combinations of two or more distinct Ctrl/Command/Alt/Shift/Fn families. Right Control and a single left/right Shift are rejected. The same validation runs before persistence in Main even when a renderer bypasses the visible settings control. Invalid persisted overrides are ignored. Expected validation, permission, unsupported-key, and native conflict outcomes remain typed setting results.

Each session creates a Profile-scoped history entry and appends ordered chunks while recording. Completed entries retain duration, surface, audio MIME type, status, and an optional transcript. A process interruption changes an unfinished `recording` entry to `interrupted` on the next scan. Recent rows show transcript-or-status plus timestamp, with an inline copy or retry action and an overflow menu for download/delete. Users can retry transcription from retained audio, download reconstructed audio through a native Save dialog, or delete a non-active entry. Retention never deletes an active recording.

`Transcribe WebM…` opens a native single-file chooser in Voice settings. Main validates a nonempty regular WebM file of at most 64 MiB and saves its exact bytes in the same private history before uploading it through buffered transcription. Imported entries retain only the file name, not its original path; unknown capture duration is not presented as a measured duration. Cancelling the chooser creates no entry. The row shows transcription progress, then the raw text with a copy action; transcription never inserts or pastes text elsewhere. Failed or cancelled transcription retains the file for Retry. Leaving Voice settings or changing accounts cancels the pending upload. File transcription does not acquire a microphone, request capture permissions, or depend on a capture service gate. The upload budget accounts for multipart overhead and Base64 expansion of retained audio.

History is a recovery feature, not a second conversation transcript. Deleting a recording does not remove text already inserted or sent. Dictation settings are Main-owned and shared by every window.

## Performance details

Each recent recording can disclose the latest attempt's local performance details. The collapsed line identifies the result actually used (WebSocket, buffered upload, or saved transcript), the outcome, and text-delivery latency. Recordings without measurements say that details are available for new attempts.

- The primary latency runs from stopping capture to text delivery. Initial file transcription starts its clock after import, measures reading saved audio through saving the transcript, and is labelled as total transcription time. Recovery and retry attempts start their own clock and are labelled accordingly; time spent waiting for the user to retry is excluded.
- Capture-surface stages retain start offsets, durations, and completed, failed, or skipped outcomes for permission, microphone preparation, recording, recorder finalization, streaming finalization, buffered transcription, text cleanup, history saving, and delivery. Concurrent stages are not added together. WebSocket timing uses the recording renderer's monotonic clock; HTTP request durations use Main's monotonic clock and remain separate from capture-surface offsets.
- Streaming details distinguish an attempted connection, an opened WebSocket, a started session, sent audio frames/bytes, received transcript events, and the result ultimately used. Details retain measured preparation/handshake/start/finish durations, negotiated protocol category, provider mode, observed close code, and a stable failure or skip reason. Selected Main evidence remains available when connection preparation or the RPC capability fails, while session messages and audio wait for that capability. A socket close after acknowledged session completion retains its close code without creating a failure. Missing observations remain unknown rather than implying success.
- Buffered transcription and semantic cleanup retain independent request timings, outcome, HTTP status when observed, local request ID, optional server request ID, HTTP attempt count, and the cleanup model. Request preparation to response headers includes local preparation, authentication, upload, and server wait; response-body consumption is separate. Network transit and server-internal processing cannot be inferred from these measurements.
- HTTP and WebSocket diagnostics expose only the configured originator and User-Agent plus the presence of bearer authentication and the account header. Raw authentication, account values, and unselected headers are never exposed.
- Global delivery waits for the native paste and clipboard-restoration receipt before ending the correlated renderer session. Hiding the bar and releasing capture do not cancel pending delivery; explicit cancellation, replacement, closure, or renderer loss do. Its text-delivery estimate subtracts the measured clipboard-restoration interval from completion latency; it estimates shortcut dispatch, not rendering in the target app. Retrying a failed paste reuses the saved transcript without another transcription or cleanup request.
- Main validates and retains one bounded diagnostics report with each recording. A later attempt replaces the previous report; an older late report cannot overwrite a newer attempt. Diagnostics writes are best-effort and do not delay successful text delivery.
- `Copy diagnostics` exports only the closed diagnostic contract. It never includes audio, transcript, surrounding text, dictionary values, device labels, account identifiers, authentication tokens, raw subprotocols, full URLs, clipboard content, or raw server errors. Deleting the recording also removes its diagnostics.

## Global dictation

- Global dictation shortcuts are available on macOS and Windows. macOS also supports bare modifiers, including Fn. The primary Dictation shortcut starts hold recording after 250 ms; releasing its ordinary key or a required modifier stops it. A short first tap followed by a second press within 400 ms of release starts hands-free recording immediately; releasing the second press leaves recording active, and a later press stops it. The independent Single-tap shortcut starts on its first non-repeat press and stops on the next; its release never activates another session. Pressing Single-tap while a hold is active stops that recording. A pending primary hold is cancelled by Single-tap. Ordinary chords register with the operating system, so conflicts are observable; Escape cancels the active session.
- On macOS, Input Monitoring observes global key transitions. Accessibility is independently required for cross-application paste; denying it does not disable Composer dictation.
- Each Nodex window has one in-app router that offers the correlated session only to a currently eligible target. A Composer must be visible and own editor focus; a Floating Composer must additionally be expanded. Collapsed, hidden, unfocused, busy, stale, or unmounted Composers decline immediately. If an eligible Composer accepts within 150 ms, it records and inserts in-app without opening a second recorder; otherwise Main shows the compact global bar and routes the shared controller there.
- The global bar is a 720 × 84 frameless, transparent, non-activating macOS window positioned bottom-center on the active display. It stays available across Spaces and fullscreen apps without changing Nodex's foreground application identity, Dock presence, or application menu. It does not take keyboard focus. Its content is pointer-through except while the pointer is over the bar.
- The standalone bar hides after completion, cancellation, or dismissal. Listening uses four fixed compact level bars; it never scrolls a waveform across the window. Releasing hold or stopping toggle replaces the canvas immediately with the compact activity spinner and the accessible status `Transcribing…` while the same outer pill remains mounted.
- The helper has no visible cancel control during listening or transcription. Transcription recovery expands to 180 px; paste recovery retains the compact 84 px window. Right-clicking the helper offers the native `Close window` action. Interactive regions temporarily accept pointer input without activating or focusing the helper window.
- Start and stop sounds are best-effort and follow the Dictation sounds preference captured at activation. Playback failure never affects capture. Hold activation confirms after 100 ms from the initial press, following the primary shortcut's 250 ms gesture threshold. The separate 250 ms minimum audio duration begins when the recorder starts. Repeated keydown events cannot start or stop another session; regular-key release rearms the chord even if its modifiers remain held. The native release watcher also reconciles a chord released before its activation request arrives.
- On completion, Main pastes `trim(transcript) + " "` into the current foreground application. It waits at least 150 ms from stop intent before paste.
- Main fences the clipboard at stop intent, snapshots every bounded clipboard format, dispatches paste, and waits about 700 ms. It restores the snapshot only if the clipboard still contains Nodex's inserted text. A newer user copy before delivery or during restoration always wins.
- Accessibility denial or paste failure leaves the transcript/audio in history. Recovery explains whether text was copied for manual paste or a newer clipboard was preserved, with explicit Copy, Open Settings when relevant, and Dismiss actions. Transcription recovery offers Copy, View recording, Retry, and Dismiss without automatically pasting recovered text.
- Exactly one Nodex instance may own global dictation across production, development, and disposable Profiles. Losing that machine-wide ownership immediately cancels capture, unregisters native bindings, and closes the helper. Global shortcut replacement is atomic: the complete desired binding set either becomes active at one generation or the previous set remains active. A native-helper transport crash cancels the current lease, starts bounded-backoff recovery, recreates the helper, and replays the desired set. Configuration or permission rejection does not mark the transport unhealthy. App shutdown interrupts supervision and releases the helper/window through the Main Profile Scope.

## Permissions and errors

- macOS microphone access is a typed, awaited operation. `granted` proceeds; `denied` and `restricted` do not repeatedly prompt and offer System Settings; unavailable platforms report unavailability.
- Electron grants only audio capture to an owned, top-level, trusted app renderer. Camera, guest, subframe, cross-origin, and unowned requests are denied.
- User-facing failures distinguish microphone blocked, missing, busy, unsupported constraints/capture, interrupted capture, network, rate limit, authentication, service, history, Accessibility, and paste.
- Errors retain only stable operation/kind/status/native-name diagnostics. Audio, transcript, device labels, dictionary values, clipboard content, and raw service bodies are never logged or sent to telemetry.

## Platform and release boundary

Composer dictation requires an Electron media environment. Global dictation has macOS and Windows adapters; Linux reports it unavailable. macOS releases require the microphone usage description and audio-input entitlement, appropriate nested-code entitlements, and a packaged native helper that passes runtime manifest and architecture checks. Windows releases additionally require native shortcut, release-monitor, and clipboard validation on Windows. Nodex currently distributes macOS releases. The Windows adapters do not by themselves supply a Windows application: primary/Core/native resource packaging and release validation remain prerequisites. A Windows distribution must also provide verified routing discovery when its primary runtime lacks it; unknown routes are never guessed.
