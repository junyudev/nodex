# Workbench Shell

## Intent

The Workbench has four sidebar destinations: Home for chats, Projects, and Inbox; Space for Pages, Databases, and Canvases; Scheduled for scheduled tasks and their runs; Plugins (Customize) for plugins and skills. Home presents each Project as a folder in its sidebar. Expanded Projects show durable Project-owned Sessions, but a Project can have zero Sessions until the first ordinary New Chat action ensures its Core-owned default draft. Each Window Session renders an owner-scoped Scene through one shared composition: a Project Scene's protected root is the Project's own Inbox with its Views as ordinary tabs beside it, the singleton Inbox Scene's protected root is the Library Inbox with Library content as ordinary tabs beside it, a Session Scene keeps Conversation as its primary plane, and Space uses the singleton Library Scene to present trusted Library content as ordinary tabs without a protected primary. A Project Agent Dock can observe and send to one real Session without changing the selected Scene. Core-backed domain data remains shared; Scene surfaces, Dock presentation, and panel arrangement do not synchronize across windows.

Detailed Auto-review preset, config, and approval-lifecycle rules are specified in [Auto-review Behavior](./auto-review-behavior.md).
Thread Summary content and row actions are specified in [Thread Summary Panel Behavior](./thread-summary-panel-behavior.md). Scheduled, Inbox, and Settings route behavior is specified in [Scheduled Route Behavior](./scheduled-route-behavior.md), [Inbox Behavior](./inbox-behavior.md), and [Settings Route Behavior](./settings-route-behavior.md).

## Layout

- Navigation rail: Home, Space, Scheduled, then Plugins. Each owns a contextual sidebar; Plugins opens Customize, whose sidebar lists Plugins, Skills, and the installed plugins, and whose pages are specified in [Plugins Behavior](./plugins-behavior.md). The rail remains visible when the contextual sidebar is collapsed and while Settings is open. Selection follows the Workbench location, including the return location while in Settings. Every destination previews its sidebar on hover.
- Home sidebar: Projects render as folders with separate navigation and disclosure controls. The visible Project label opens its Project Scene without changing disclosure; the leading marker becomes a chevron on row hover/focus and only folds or expands Session children. A Project's Inbox count and row actions share the same trailing area: the count rests at the right edge, and hover, keyboard focus or an open row menu replaces it with the actions. A collapsed Project adds one status beside that count: the unread dot when any chat is unread or waiting on its person, otherwise a spinner when any chat is working; an expanded Project shows none.
- Chat row status: each Chat row shows at most one status in a 20px slot at its trailing edge, after the title and any resting pin, and hides it while hover, keyboard focus or an open menu reveals the row actions. A chat waiting on its person shows the unread dot; otherwise a working chat shows the spinner (muted and slower for background work), and an unread chat shows the unread dot: an 8px accent dot. An unread or waiting chat keeps that fact in the row's accessible description even while its spinner shows, and the row's accessible name stays its title. Unread chats keep the hover Pin action. The chat hover card repeats the unread state with a small accent dot after the chat's age.
- Space sidebar: Content lists the Library's root Pages, Databases, and Canvases in Library order, including Project resources and the Library Inbox Database. Opening, selecting, or editing content never reorders Content or changes which rows it lists; only creating, moving, reordering, or removing roots does. New content enters at the top, so the first page always shows what was just created. It reads bounded continuation windows whose identity is independent of selection, keeping one row beyond its revealed depth loaded, and an active root outside the loaded rows joins after them. Its first header row, `New page`, creates a root Page and opens it; the row's trailing `New Page or Database` menu creates either root kind. Resource actions and Library reordering remain available; selecting a root opens or focuses its ordinary Space tab.
- Space home: an empty Pages leaf shows the Space home rather than a blank pane or a picker behind another click. It has a `Space` heading with an inline Search and a `New` menu (Page, Database), kind tabs (Recent, Pages, Databases, Canvases), and Library content in last-edited order with Location and Last edited columns. Search filters titles, and Page content when Pages are included, in place; Escape clears it. Opening a row presents it in that leaf. Each kind has its own empty and no-results message, and the list loads more as it scrolls.
- Contextual sidebar: Home, Space, and Scheduled share a 288px default width, collapse, resize, and floating-reveal behavior. While the sidebar is collapsed, resting on a rail destination for 100ms previews its contextual sidebar without changing the routed content; moving to the other destination switches the preview immediately. The peek begins 4px beyond the rail and 4px below the titlebar, keeps the pinned sidebar’s right edge, and adds no duplicate window navigation. Content-edge movement alone does not open it. The peek stays open while the pointer travels from the rail toward it (an aimed path that lapses after 1s without progress), rests on it or on the rail's destination band, while one of its menus (including native context menus) is open, while focus is inside it, and during a drag that started inside it. Otherwise it closes 100ms after the pointer leaves; Escape, another rail action, or pinning the sidebar closes it at once, and Escape suppresses reopening until the pointer leaves the destinations.
- Project children: each expanded Project lists ordered Sessions. A new Project starts with zero Sessions and still opens its Database immediately. Its first ordinary New Chat action immediately ensures one durable default-draft Session and lists it; repeated actions select the same Session until first Thread link or Archive releases the slot.
- Sidebar pagination: Projects, Project children, Chats, custom Sections, and Space Content show a first page and reveal more with `Show more`. The selected row stays visible without taking a page slot: selecting a listed row never changes which rows are listed, and a selected row beyond the page joins in list order as one extra row. `Show more` appears only while unselected rows are hidden, and `Show less` only when collapsing would hide one. Every paginated list (Pinned, Projects, each Project's chats, Chats, custom Sections, and Space Content) remembers how far it is revealed as a Profile preference, like section collapse, so switching destinations, reopening the window, or relaunching restores the same rows; a list that reads its rows in windows reads further until that depth is filled.
- Sidebar Sections: users may create named custom Sections in Home above the Projects group from a Project or Chat context menu and place Projects and Project Sessions into one mixed ordered list. The Projects header has no duplicate create-Section action. Moving a Project changes only its list placement: the same Project row renderer, disclosure state, marker, actions, hover card, child rows, pagination, and context menu are used in Projects, Pinned, and custom Sections. Moving a Session likewise changes only placement: custom Sections use the same Chat row renderer, title and status presentation, hover card, hover-revealed Pin and Archive actions, rename behavior, and native context menu as Project, Pinned, and Chats lanes. A directly placed Session is a root-level row aligned with the Section content edge; only Sessions rendered as Project children use the grouped indentation, which keeps an empty leading column so their titles align under the Project name; their status uses the same trailing slot as every Chat row. A collapsed custom Section shows the same single dot or spinner at the right end of its header, with unread before working. A Session's direct placement overrides inherited presentation from its Project; the Session remains owned by that Project and is omitted from the Project's nested list while directly placed. Pinned and custom placement are mutually exclusive. Project and Chat rows may be dropped onto an empty, populated, expanded, or collapsed custom Section; hovering the Section header or its empty space highlights that whole destination with the sidebar hover background and inserts at the start of its mixed list. The target remains mounted while collapsed and extends through the gap below the Section. Populated Sections resolve the pointer above or below either item kind to one exact mixed insertion boundary with the blue rail and outlined leading dot, without also highlighting the container. Dropping preserves the destination’s disclosure state. Reordering within a Section uses the same mixed boundary and one atomic Core item move. A Project row's narrow top and bottom edges remain mixed-list insertion boundaries while its center and leading target accept a Chat into that Project. While an external Chat is over any whole-Project target, the outer Project group—including its header and children—shows one 2px inset accent ring, 10px radius, and a 10% accent tint; nested row/icon/gutter targets must not add separate gray hover blocks. Custom Sections and their contents support pointer and keyboard organization; `Alt+ArrowUp/Down` moves a focused Section. Collapsed state is a Profile preference, while definitions, placement, and order remain Core state. The header shows aggregate running or unread state even while collapsed and creates a durable threadless projectless Session directly in that Section. Its overflow menu contains exactly `Edit section`, `Archive all chats`, and `Delete section`; Section order is changed by direct drag or keyboard organization, not duplicate move commands in this menu. Archive all is a confirmed, set-based action over every effective Session, including inherited Project children; when it archives the selected Session, Workbench creates and selects a replacement draft in the same Section. Deleting a Section releases its visible organization without deleting its Projects, Sessions, or Threads and offers Undo.
- Sidebar header: Home, Space, and Scheduled share one header so switching destinations never moves it: a 52px title row (`Nodex`, `Space`, or `Scheduled` at 18px semibold, with trailing 28px Search) followed by the destination's 30px primary rows, which always begin at the same position. Home's rows are `Inbox` then `New chat`; Space's row is `New page`; Scheduled's row is `New task`, and its Search toggles an inline field instead of opening the command palette. The `Inbox` row sits directly above `New chat` and opens the Inbox Scene on its Inbox tab, keeping any tabs opened beside it. Its trailing count is the number of messages still in the Inbox, shown muted; the `⌘/Ctrl+Shift+D` keycap appears only on hover.
- Rail foot: from the bottom up, the Nodex account avatar, the native Codex account control, and one usage meter per Claude subscription account sit at the bottom of the navigation rail, so all stay reachable with the contextual sidebar collapsed and while Settings is open. The avatar and the Codex control always hold the two lowest slots, so Claude meters appearing or disappearing above them never move them. The avatar opens the Nodex account menu, including Settings. Nodex identity is independent of native Agent authentication; its menu and Account page follow [Nodex Account Login](./nodex-account-login-behavior.md). A usage meter is the provider's mark inside one ring that shows what is left of the account-wide window that runs out first; a model-only window such as `Weekly · Fable` never drives it. The ring stays neutral, turns amber at 35% left and red at 15%, and draws a red track once a window is used up. A reading older than 30 minutes stays visible but dimmed; a window whose reset has passed since the reading is unknown, never assumed full; a dotted ring means nothing current is known; an amber dot means the latest read failed and the previous reading, if any, is shown. Hovering or focusing a meter opens its card: provider, plan and signed-in address; one bar per window with what is left and when it resets, where a used-up window says `Limit reached` and counts down to its reset; and a footer that separates the account's limits, which count use from every app and device, from this computer's reading of them: when it was taken, or that it could not be refreshed and which reading is shown. A signed-in Codex account's card adds `Sign out` and any available quota resets, kept behind a disclosure so a passing pointer cannot spend one; Codex refreshes its reading every minute and when its card opens. A Codex API-key account shows an empty ring whose card says no subscription limits apply. A signed-out Codex account shows its mark in an open ring with a plus where the ring opens; its tooltip and the sign-in popover it opens beside the rail both say `Sign in to Codex`, so it is never taken for the Nodex account. While the Codex account is still unknown the slot holds a dotted Codex meter that breathes while the account loads; when it cannot load, it rests with an amber dot and its tooltip gives the reason. Nodex keeps retrying, and clicking it asks again at once. Claude meters show what Claude Code reports when Nodex checks a Claude Agent, through the same check that lists its models, and while it replies; Nodex never asks the account directly. Each reading is dated by when Claude Code fetched it: Claude Code may answer from a reading it stored, including one up to an hour old when it cannot reach the usage service, and such a reading keeps its earlier time. Nodex keeps one Claude reading for every window. While a Claude meter shows and Agent execution is running, it reads again once the reading is five minutes old; while execution is stopped nothing reads on its own and the meter keeps its last reading. Opening a Claude card reads again unless that happened within the last minute, starting Agent execution when it is stopped. Claude readings also follow what Nodex already knows: whenever it lists its Agents, and when Agent settings change, a Claude reply ends or Agent execution becomes available. A failed read, including one where Claude Code answered without the account's windows, keeps the previous reading and marks it as not refreshed; it never hides the meter as an account without limits. A Claude card adds `Sign out`, which signs Claude Code out of that account for every Claude profile the meter covers, as `claude auth logout` would, including outside Nodex; a profile still signed in through its environment, such as an API key or token, says so. Signing in again uses `claude auth login`. Until Claude has been read once the slot holds a dotted Claude meter that breathes while it loads and rests with an amber dot when it cannot be read; Nodex retries every five minutes while Agent execution runs, and clicking it asks again at once. Disabled, uninstalled and signed-out Claude instances without a reading, and accounts that cannot have subscription limits such as an API key or Bedrock, show no meter; instances signed in to the same account share one meter with the freshest reading. A window opened after an account was first read starts from what Nodex already knows, so it never waits on an empty slot.
- Active Scene header: a Session Scene uses the active thread title row without a separate session title, project-name subtitle, or empty toolbar row. A Project Scene renders the Project marker and name at the start of the root surface tab strip; it does not add a `Home` label or a second title row. Space renders `Space / <root>` and appends the selected child title when the active surface is below that root; its resource tabs remain the only content-level title row. Project identity, tabs, surface actions, and the Database toolbar are all outside the Electron drag region. The fixed global header owns the left chrome (`Sidebar`, `Back`, `Forward`, and collapsed-only `New chat`) plus the top-right bottom-panel control. Session Scenes also expose the right-panel control, while Project, Inbox, and Library Scenes omit it because their surface stacks are structurally full-width. Bottom-panel surface creation plus the plain `Close` X action belong to the bottom-panel tab header. There is no attach/detach thread toolbar button.
- Owner root: a Session Scene hosts its Conversation on the primary plane and shows the new-thread composer when no Thread is attached. A Project Scene places the Project's Inbox as the first, non-closable `Inbox` tab in the full-width right surface stack; [Inbox Behavior](./inbox-behavior.md) owns its contents. It cannot be moved, split away, or sent to the bottom panel. The Project's Database Views, including the default View that the Home's `Open Board` button opens or focuses in the Home's tab group, are ordinary closable tabs, and other Project surfaces retain normal tab and split behavior. The Inbox Scene places the Library Inbox the same way, as its first, non-closable `Inbox` tab; the Inbox Database that `Open Inbox as a Database` opens or focuses, and content opened from it, are ordinary Library tabs in the source tab group, so triage never leaves for Space. It has no Agent Dock or floating composer, and chats still open their own Session Scene. Every Inbox, in either Scene, opens a message's Page as a preview in the group to its right, creating that group when the Inbox's group is alone; this group is the Inbox's side panel, with no separate collapse control. The Library Scene has no owner root: every Page, Database, View, and Canvas is an ordinary closable surface, and closing the final surface reveals the empty Space chooser. Database `Ask agent` reveals and focuses the Agent Dock only in a Project Scene; it does not create a Session or a Conversation surface.
- Thread summary: attached Chats show a summary action in their titlebar. Placement uses the target chat-pane width after sidebar and right-panel reservations. Below 1096px it opens a dismissible popover; from 1096px through 1535px a pinned summary shifts the transcript and Composer left together by 154px; at 1536px and above it occupies the trailing gutter without shifting content. The 300px panel rests 8px inside the chat pane. Responsive changes and pin toggles animate one shared content offset, including while the transcript is loading, and interrupted transitions continue from their current position. Opening a right panel only changes the available width; it does not independently clear the pin preference. In full view the Chat's title row is hidden and a compact summary control joins the workspace controls: while content fills the view it opens the summary as a popover over the content, and with the Chat tab selected the pinned summary uses the full Scene width. Chat changes and full-width hide/restore settle the content position immediately, as does reduced motion. Pinned entry/exit slides and fades without scaling; hidden controls cannot receive focus. The narrow popover aligns below the titlebar at the chat pane’s trailing edge, slides within that pane, dismisses on Escape or outside interaction, and preserves the pin preference. Right-panel tab selection alone keeps it open. Returning to a wider pane dismisses the transient popover and restores the saved pin state. Section content and actions follow [Thread Summary Panel Behavior](./thread-summary-panel-behavior.md).
- Content panel: a Session's content panel renders Window Session-local ordered surfaces and split groups beside its Conversation, on either side. `Move to right pane` / `Move to left pane` swaps them; each Session remembers its side, and a Session that has not chosen one follows the most recent choice, which is a Profile preference (content on the right by default). Newly materialized Session Scenes start collapsed. A Session is in one of four presentations: split view (Conversation and content side by side), Chat only (content hidden with its tabs retained), full view showing the selected content tab, or full view with the Chat tab selected. Hiding tabs leaves full view; closing the last content tab in full view keeps full view with the Chat tab selected. Project, Inbox, and Library Scenes use the same panel tree and tab implementation as fixed-open, full-width surface stacks. Collapse and restore-width controls apply only to Session panels; responsive layout preserves Project and Space content roots while allowing the contextual sidebar to close. A Project may activate the initial Welcome Page while retaining Database as the first protected tab. The Library Scene may be empty. When the sidebar is collapsed and a content strip starts at the window's leading edge (full view, or content on the left), the tab header reserves the measured left titlebar rail so `Show sidebar`, Back, Forward, and compact `New chat` never overlap the tabs. The persisted layout shape supports split leaves; header start reservation applies only to the top-left group and trailing expand/restore controls apply only to eligible Session groups.
- Floating composer: full-width Session right panels float the shared root Composer over `review`, `browser`, `db_view`, `page_stage`, `canvas_stage`, and root-targeted `image_editor` tabs. Image editing may bind it before New Chat has a Thread; a side-Composer target never projects into it. A Project Scene floats the same footer-only conversation connector as its Agent Dock on every active surface except its Inbox Home, which has its own composer; the Dock still covers `New chat` and blank Session targets. A body portal mirrors the full-width pane's rect and zoom. The composer rests in one of five docks (bottom center by default, bottom left or right, top left or right) with its frame 10px and its surface 16px inside the pane. Compact, it is the 44px auto-single-line prompt alone; its 46px header (Minimize, run status, title, the context rail, and the move handle) folds open while the prompt has focus, while dragging or resizing, or while the move menu is open, and stays open when the body has no prompt to focus. The rail's leading chat selector is followed by mutable new-chat runtime context. Dragging the header or the frame's margin moves the composer; release springs it into the nearest dock: bottom center while it rests in the lower half across the middle half of the pane, otherwise the nearest corner, with a frame at least half the pane wide following the pointer horizontally. Escape or window blur cancels a drag. A frame nearing a corner dock shrinks to 95%; releasing with the pointer in that corner minimizes it there, and dropping on either 24px edge of the pane returns a Session to split view with its Chat on that side. Either edge resizes the width (360px surface minimum, pane minus 20px maximum) while the opposite edge holds still, then the frame glides back to its dock. Width, expanded height, and the last chosen dock are window-wide Profile preferences; each Scene persists whether its composer is shown, its dock, and its bubble corner without Back/Forward history, so switching tabs or owners, leaving full width, and restoring the window preserve them. Clicking the move handle offers `Open in full view` (selects the Chat tab), `Move to left pane`, and `Move to right pane` for Sessions, then `Minimize composer`. Minimizing collapses the surface into a 36px bubble resting 16px inside its own corner (bottom right by default); it shows a spinner while running and a dot when input is needed, can be dragged between corners, and restores and focuses the prompt. With a transcript, clicking the header expands the composer into the latest turn above a divider at the stored height (640px by default, between 400px and the pane minus 32px); the edge away from the dock and its two corners resize the height. Escape, a pointer outside, or focus leaving collapses it. While compact, an unread completed response stacks a preview card beside the composer, or beside the hovered bubble, that opens the conversation or dismisses it and marks it read; expanding also marks it read. Panes narrower than 640px keep the composer at the bottom center at full width without dragging. Bottom docks keep 118px pane scroll clearance; Browser reserves none. Minimizing leaves chat and Main-owned runtimes active. The shared adaptive footer compares the prompt's measured longest unwrapped line with the compact input width left by its actual controls. Visual wrapping, explicit line breaks, attachments, errors, or dictation promote the normal Session composer shape with a full-width prompt row and the standard split control row—context and planning controls left, model, dictation, and submit right—while scrolling remains owned only by the capped prompt editor; side-chat, Terminal, Files placeholders, blank Session homes, and resuming Session pages stay on their existing non-overlay paths.
- Bottom panel: the bottom panel renders one tab group below the primary/right-panel row and spans the full active Scene width. It has a top-edge resize handle, defaults to 280px tall, and can be shown or hidden from the fixed global `Toggle bottom panel` button. Opening a collapsed empty bottom panel creates and selects Terminal when the active owner has an eligible Terminal workspace; reopening a non-empty panel preserves its existing tabs and selection, while owners without Terminal capability keep the empty chooser. Empty panel choosers and panel new-tab menus use owner- and panel-specific capabilities. Attached project-backed Session bottom panels order Terminal, Browser, Files, Side chat; attached projectless Session bottom panels order Side chat, Browser, Terminal. Threadless Sessions omit Side chat. Project bottom panels offer Terminal, Browser, and Files with explicit Project context and never create a Session to host them. Review remains right-panel-only at creation. Inbox and Library Scene panels expose only the shared Library picker for Page, Database, and Canvas content.
- Browser surfaces: `browser` is a real multi-surface kind backed by the Main-owned Browser Platform. The renderer supplies navigation chrome and stable body-attached host geometry; it never imperatively navigates the guest. Every route is identified by canonical Scene owner key, owning Window Session, and Browser tab, while its opaque storage identity links the shell to atomically persisted URL/title/favicon and Chromium back/forward history. A manually opened Project Browser has no agent owner. Every Browser Use runtime tab instead carries its own exact `codexSessionId`; target selection never rewrites it. Starting an idle turn awaits capture of the owning Session presentation route, with a real Session materialized before a Project Dock draft starts and a newly created Thread promoted before its first turn. A visible Browser Use request creates or activates the Browser surface in that Session Scene before selecting the task; background and hide requests update it without navigation. Every live Browser Use tab in the Window Session receives a retained body host from the renderer-wide runtime projection regardless of which Project or Session Scene is selected; Scene-owned panel and background hosts may supersede it only for the same exact route identity. Ordinary reopen preserves identities; duplicate, new-window clone, and fork copy presentation but remint runtime/storage identities. Switching panels, Dock visibility, full-width presentation, and retained Browser Use hosting preserve the live page; explicit surface close performs generation-fenced descriptor removal, Main teardown, guest destruction, and acknowledgement. A 32-page detached budget suspends only unprotected pages and restores them from the durable snapshot when selected again.
- Opening an HTTP or HTTPS link in a new window clones the current Project or Session Scene, selects a new Browser surface, and retains its Project/Session context. The new window has independent Browser tab and storage identities and does not reopen an unrelated closed window. Library, Inbox, and empty Scenes do not offer this action.
- Browser chrome includes back/forward, reload/stop, address and connection state, find, open external, annotations, page options, the full zoom ladder, printing, image screenshots, responsive/fixed device emulation, Profile-wide data clearing, download status, and Browser settings. The app-shell Browser tab icon is live runtime chrome: it shows a double-circle throbber alone while waiting for the first response, clips an available favicon inside that throbber after response, and completes its 250 ms favicon transition before removing the throbber when loading settles. Stop, failure, blank, detached, restored, and suspended states are settled; they never retain a hidden loading animation. The resolved app reduced-motion preference keeps the same readable phases while removing throbber animation and completion transition. Waiting/loading truth remains transient Browser runtime state and is never persisted into Scene configuration. Blank tabs are New tabs (see New tab below); their local-server section shows one row of up to four server tiles with live thumbnails, hides when the Project has no known servers, and keeps refresh, show-mode, sort, hide, and `Show more` controls. DNS, offline, refused, timeout, certificate, policy, renderer-crash, and generic failures retain the tab and expose a safe recovery action. Browser tab context menus put `New tab to the right`, `Reload`, and `Duplicate` before the generic move, close, and split actions; page context menus add policy-checked navigation, copy/edit, image attachment, annotation, and inspect actions.
- A New tab’s focused address bar suggests matching tools, other tabs across both panels of its Scene, and up to five recently edited Pages whose titles match and are not already open. Tool and tab matches start at word boundaries; exact and title-prefix matches lead. Exact/prefix Page matches precede web search, substring Page matches follow it, and URL navigation always leads. The list keeps at most eight rows, including the typed navigation/search choice; explicit schemes and `www.` suppress workspace matches. Arrow keys wrap selection, Enter accepts, hover selects, and pointer acceptance retains input focus. Escape dismisses suggestions first, then restores and blurs the address; composition keys are ignored. Tools and Pages replace the New tab in its own group; switching to an existing tab activates it before closing the New tab. Loaded Browser tabs keep ordinary address submission and blur navigation.

An agent download requires a short-lived one-use grant for the exact route and URL chain. Annotations support element, selected-text, and region anchors, multi-selection, comments and constrained design previews, original view, discard, and bounded screenshot evidence added through the shared composer attachment model. In non-Electron runtime Browser renders an explicit desktop-only unavailable state.
- A Session content panel has a resize handle on the edge adjoining its Conversation in split view. Full view removes that divider and shows either the selected content tab or Chat; selecting Chat fills the Scene with the Conversation while keeping content tabs listed. The titlebar workspace control returns it to split view. Project and Pages surface stacks have neither resize nor restore-width controls because full width is their structural layout.

## Scene And Surface Semantics

Each user submission captures its submitting Workbench presentation before asynchronous
submission work begins. Main stamps the Window Session and renderer generation;
the originating Scene, revision, focused target, and selected surface identities
stay attached to that exact submission when another window owns the Conversation. Fresh Session and side-chat
launches retain the same origin through materialization. Queued follow-ups retain
their enqueue origin; editing a queued message replaces it with the editing
submission's origin. Interrupted steering retains its origin if the message later
starts a Turn, and accepted steering replaces the context for subsequent tool calls in that Turn. Already issued observations retain their original evidence. Rejected submissions do not replace accepted context.
Only selected surfaces in visible panels contribute submission context. Context contains bounded resource metadata, never full editor state, favicon payloads, or image collections. Budget limits yield explicit partial coverage; missing or malformed supplemental context yields explicit unavailability without blocking an otherwise authorized message. Sender, target, and explicit attachment validation remain mandatory.
These anchors are transient: cold reopen, autonomous work, and native notification
replies have no inferred presentation. Navigation after submission never retargets
an anchor to the currently selected window or Scene.

Application tools observe the submitting Scene by default. Explicit refresh reads
the submitting window's current Scene; an exact discovered Scene reference may
select another target. Without a submission anchor, discovery returns candidates
and requires an explicit target, even when only one window is available. Missing
renderer replies never establish a unique window. Observations expire after one
minute and are bound to the exact Turn, Profile, backend generation, and renderer
revision. Tab and group continuations retain their original observation and
filters; changed presentations require a new observation.

Tab descriptions verify Page, View, and Canvas identities and titles in Core
before returning them. Tabs expose observation-scoped handles and
presentation state. A submitted target that has since closed or changed retains
its original content identity but has no actionable tab handle. Title or favicon changes alone do not invalidate the resource target. Group
results contain bounded summaries; their tabs use the separate filtered tab list.

Application tab controls use those observation-scoped handles and the same Scene
command executor as pointer and keyboard actions. Commands validate the observed
presentation revision before applying an atomic layout change. Exact retries keep
the original operation ID and revision, returning the retained receipt rather than
applying a second change. Closing saves content and releases view attachments;
opening accepts semantic targets and creates internal runtime identities in Nodex.
Protected primaries and each Scene's permitted surface kinds remain enforced.
Successful changes require a new observation before subsequent commands.

`set_panel_state` accepts optional `side: "left" | "right"` only for a Session's
`right` panel. Bottom panels and Project, Inbox, and Library Scenes reject side
changes with `invalid_placement`. Panel observations expose the saved side when
one is set. `size.fullWidth` and `collapsed` are independent Session presentation
choices:

| `size.fullWidth` | `collapsed` | Session presentation                                 |
| ---------------- | ----------- | ---------------------------------------------------- |
| `false`          | `false`     | Split view with Conversation and content             |
| `false`          | `true`      | Chat only, with content tabs hidden                  |
| `true`           | `false`     | Full view with a content tab selected                |
| `true`           | `true`      | Full view with Chat selected and content tabs listed |

Collapsing the panel preserves `size.fullWidth`. Closing its final content tab
keeps full view with Chat selected when full view is active. A command that hides
tabs and exits full view sends `collapsed: true` and `size.fullWidth: false`.
Physical side is normalized away from bottom panels and non-Session Scenes, just
as panel dimensions that do not apply are discarded. Project, Inbox, and Library
content stacks remain fixed open and full width.

Page content reads wait for the exact mounted editor to synchronize before reading
canonical content. Closing, replacing, or reloading that editor during preparation
invalidates the read; a different occurrence cannot complete its preparation.
Page edits retain the returned body validator and preserve Block identities.

Database View content reads distinguish the loaded, viewport, and selected
occurrences and report their coverage. They preserve the surface's effective
shared rules, personal overrides, search, and display state. A complete effective
query runs those captured rules in a new Core snapshot, independently of the
renderer's bounded window. It either returns the requested bounded result or fails
its budget; it does not silently truncate or provide a resumable SQL snapshot.
See [Agent CLI Queries](agent-cli-queries.md) for query and authorization semantics.

The global header shows `Content issues` only while an edit needs attention:
an unconfirmed action, a failed Undo or Redo, actionable Page/Canvas save
trouble, or retained drafts. Its absence makes no all-content-saved claim.
Routine saving stays beside the affected content; a successful edit that cannot
be undone is only a native Undo limitation and does not raise an alert.

The manually opened popover identifies each problem by its original
Library/Project and available Page, View, or Canvas location. Navigation and
recovery preserve that routing context. Separate actions in one scope remain
separate; the same retained draft observed through multiple surfaces appears
once, preferring the live document's recovery controls. Retained drafts stay
separate from the current document's save state and open the shared recovery
review. The header neither follows focus nor replaces Page version history.

Each problem leads with its failure or unconfirmed-result title, followed by
the explanation. Recovery actions have visible button surfaces at rest: the
primary action is filled and alternatives are outlined. The original content
location is one outlined Library/Project path with a navigation arrow; static
context stays plain. An in-progress action stays visible and disabled with a
loading indicator while its owner confirms the result.

`Check again` confirms the exact submitted action. `Retry undo` and `Retry redo`
retry the corresponding failed replay. `Clear undo history` lives in the
secondary actions menu, which names the affected Project or Library, and
requires a root-hosted confirmation describing the affected shared Page and
Database timeline. It changes no content and does not abandon submitted
requests. The confirmation rechecks the history revision, so later edits make
it stale; ordinary submission cannot offer it.

Explicitly converting one View's layout preserves only that View identity and its layout-neutral settings. The public Canvas Block ID is the target; the surface never persists `documentId`, scene state, or Page host coordinates. Opening the same Canvas again focuses the existing target where the owner Scene and routing context match. Within one renderer, inline Page Canvas and Canvas Stage share one Document session/provider/outbox only when their Core-authored `libraryId + routingContext + documentId` identity matches, while retaining independent Excalidraw bindings, camera, undo/tool state, asset resolver, and presence participant.

A single-click from a Board or List DB View opens or replaces a renderer-local preview; double-click, command-palette results, Thread Page links, and explicit pickers open a durable Scene surface. Only the selected body mounts. Every live Page Document session publishes its authoritative Y.Text title through one renderer-lifetime `(libraryId, pageId)` presentation overlay, so all matching Session, Project, Inbox, and Library tab handles, the Space Content row, and the Space breadcrumb update together for local or remote edits. A durable Page surface retains that publisher with its editor session while React detaches the selected body; independent surface leases prevent one surface from clearing another. After the final session retires, the overlay retains its last observed title until canonical state either presents the same title or causally follows the exact durable Document head that acknowledged it. An unrelated head advance is never settlement proof, while a later remote title or Document-generation reset can still take over. Canonical Page and Library projections remain the committed fallback, while Window Session and Scene title snapshots are cold-start fallbacks and are not rewritten per keystroke. A transient Core deadline during the initial Document read keeps the Page in a `Core is busy` state and retries twice with short bounded backoff; a non-retryable failure stops immediately, and an exhausted transient failure exposes one explicit retry action without rendering the raw Core error. Unmounting the surface cancels the retry chain. Shell, exact Page/routing-context hydration, missing-target states, retained Page model, preview promotion, and close cleanup follow the shared Page Stage lifecycle.

Its config stores `terminalSessionId` plus an explicit Project or Session context. Project context starts from the Project root without inventing a Session. Session context uses attached Thread cwd or Project root; a projectless Session requires an attached Thread with a non-empty cwd and never falls back to user home or process cwd. Browser surfaces are not Scene singletons; users can create blank tabs to the right, reload, and duplicate existing Browser tabs from the tab context menu. Session re-home is independent of Scene descriptors; targets re-resolve under the new domain scope.

- File identity: a file surface uses `file:<host>:<canonical absolute path>` across preview, pinning, movement, restore, and window cloning. Canonicalization is lexical and preserves filesystem case; host authorization remains separate. Reopening a file focuses its existing Scene occurrence across groups. Empty Files explorers distinguish Host, Project, workspace root, and working directory. Resource identity excludes panel placement and mutable display state. Chat Markdown file links decode URI-encoded path segments once before opening the file, independently of line fragments.

Board/List DB-view Page clicks open `page_stage` as a right-panel renderer-local preview in the nearest right-side group, creating a right-side group first when the right panel is full-width with only the DB group. Image editing opens a right-panel-only renderer-local `image_editor` preview. Each panel leaf has at most one italic preview, so opening another image or ordinary preview in that leaf replaces the previous unpinned preview. Persistable previews remain omitted from the Scene until the user interacts with the body, chooses `Pin tab`, or double-clicks the label. Pinning an image first resolves bounded stable asset locators, then replaces the ephemeral descriptor with one durable `image_editor` surface at the same tab/leaf identity; failure leaves the preview intact. Pinned images follow ordinary reorder, move, split, close, clone, and restore semantics. Files, Browser, and Page Stage previews preserve surface identity when pinned; distinct Browser runtimes have distinct identities. Each ordinary preview has an independent lifetime token, so an asynchronous save or pin cannot clear a replacement preview, including a reopened instance of the same file. Persistence or save failure leaves the preview available for retry. The selected body follows the normal fresh-view lifecycle. Close/delete, image download, and local Open controls are preview-safe and act without first pinning. Image editor behavior is owned by [User Attachment Image Editor Behavior](./user-attachment-image-editor-behavior.md).
- Side chat tabs: Side chat is a renderer-local Session Scene action/tab family, not a persisted `WorkbenchSurfaceDescriptor` kind. Side chat actions create renderer-local loading tabs (`sidechat-loading:<parentThreadId>:<index>`) in the requested panel. Main resolves the parent before starting the fork and does not hold the parent's non-reentrant causal command lane: creating a temporary child reads but does not mutate its parent. Main then creates and hydrates an app-server `thread/fork` with `ephemeral: true` and `excludeTurns: true`; the invoking renderer attaches through the same owner/checkpoint lifecycle as an ordinary Thread before replacing the tab with a closable ready tab (`sidechat:<threadId>`). A rejected or timed-out fork/attachment settles as a closable failed tab with the concrete error and Retry action; it never remains a false loading tab or silently disappears. Side chat titles are `Side chat`, then `Side chat 2`, `Side chat 3`, and so on for that Session Scene. They can move between the right and bottom panels in renderer memory, but they are never persisted, pinned, archived, listed as normal Project Threads, or restored after app restart.
- Ready side-chat tabs render the local conversation body and composer without the normal thread-stage title header; the side-chat tab itself is the only top title row.
- Side-chat start input contains only parent conversation identity and optional prompt/settings. Main derives execution context from the parent detail. Project-backed parent navigation remains `project:<id>/session:<id>/thread:<id>`; projectless navigation is `session:<id>/thread:<id>` and never fabricates `project:null`.
- Session-Thread links are the durable local ownership path for Codex Threads. Pages may open as Scene surfaces or mention Threads, but they do not own Codex Threads. A distinct Workspace-owned Linked chat edge can associate a Page with a durable Project Session without changing either owner, changing Page ownership, or depending on a Scene or attached Thread.
- Page Stage exposes a bounded, compact `Linked chats` Property keyed by Project Session identity, including threadless Chats, Chat title, execution state, independent unread state, quiet current-Chat presentation, retry/load-more, and explicit relation removal. Linked Chats use the same wrapping chip grammar as other multi-value Page Properties; activity appears inside each chip, and the trailing value-lane `+` offers `Link to chat…`, plus `New chat` when the Page opens in a Project's presentation, since a new Chat needs a Project. Space Pages show the same Property. The Property does not expose Thread execution target, CWD, preview, or same-Project metadata. Selecting a chip navigates to that Session. With no relation, Linked chats starts behind the shared `N more properties` disclosure; expanding it reveals the shared `Empty` add/link entry point. A linked Session or actionable error promotes the row, and once shown it stays stable for the mounted Page session even if its last relation is removed. `New chat` uses the same atomic Session-plus-initial-Page operation as Board/List, while linking to a Chat does not send or start a Turn. Removing a relation does not close a Scene or delete, archive, read, or detach the Page, Session, or Thread.
- Project Agent Dock: the single context rail begins with a Project-scoped chat picker whose first option is always `New chat`; it reuses bounded sidebar Session ordering, exposes explicit load-more/retry states, and exact-hydrates the selected Session. Selection changes neither Workbench location nor Browser ownership. The unbound Dock draft stays Window-local until first send, then coalesces through the same Core default-draft ensure used by ordinary New Chat and binds only after Thread start succeeds. Existing targets share the canonical conversation/footer state with their full chat page, and the floating composer expands into their latest turn. Selector rows and the trigger never render status words: a fixed leading slot shows the shared spinner for running, the shared accent dot for unread or attention, and a neutral dot for idle/read. `Open chat` is the only target-row navigation action.
- The unbound `New chat` target has a Window Session Scene-local draft identity and creates no Core row until first send. Duplicate sends coalesce through one default-draft ensure and one Thread start. Ensure or Thread-start failure preserves the unbound draft and its content for retry; only a successful start binds the Dock to the Session, after which the next explicit `New chat` receives a fresh draft identity.
- A worktree start is recovered from the Main-synchronized pending-worktree collection by the bound `projectSessionId`, never from Dock-local memory. Until the exact pending entry resolves to a real Thread, its client identity remains in the same Thread/Composer scope, the target row shows compact setup progress or failure attention, and both composer availability and the action boundary prevent a second start. `View setup details` explicitly opens the existing recovery route; reload, retry, continue, work-locally, and cancellation follow [Codex Worktree Creation Behavior](codex-worktree-creation-behavior.md).
- Dock target and visibility are persisted Scene presentation but are excluded from Back/Forward history. If exact hydration proves that a bound Session was archived, deleted, or moved to another Project, sending is disabled and the Dock returns safely to its retained new-chat draft. A bounded summary window that does not contain the binding is never sufficient evidence.

## Storage Ownership

- SQLite owns shared Project Session domain data:
  - `project_sessions`: nullable Project id, `no_thread_fallback_title`, order, and pin/archive/unread state.
  - `project_session_threads`: optional Session-to-Thread attachments; canonical Thread metadata lives in `codex_threads`.
  - `project_session_pages`: non-owning, non-authorizing Page–Session Linked chat edges; Page access, Session ownership, optional Thread state, and presentation remain in their existing authorities.
  - Session lists return a derived `displayTitle`; attached Sessions prefer `codex_threads.thread_name`/preview and only fall back to `no_thread_fallback_title`.
  - Session rename commits its title through Core before updating a live conversation or backend. Attached Codex conversations synchronize the current committed title without another durable title mutation; a rejected rename has no conversation-side effects.
  - Session commands serialize per Session through commit and backend synchronization. Archive and restore commit Core state first, then reconcile only the attached Thread identified by that receipt. Backend or descendant cleanup uses the host lifecycle owner. A synchronization failure retains the committed operation identity for retry and does not imply that the Session change was rolled back.
- Core Workspace owns the atomic default-draft role and its Project/projectless uniqueness and graduation rules; renderer callers receive only the ensured Session. Main's revisioned Window Session catalog persists the canonical layout: the selected Workbench location, the previous stable Home location, Project-keyed Database search, and strict `WorkbenchSceneSnapshot` values keyed by canonical owner key. Project, Inbox, and Session Scenes own semantic primaries; the singleton Library Scene deliberately owns none. Every Scene owns right/bottom panel trees, stable sizes, selected leaves/surfaces, MRU, collapse/full-width, and persisted descriptors; Project Scenes additionally own Agent Dock target/draft state. Writes use ownership validation, compare-and-swap `layoutRevision`, bounded codecs, atomic replacement, and fsync.
- Clone retains canonical file resource identities and remints other surface/tree/Browser identities plus the unbound Project draft identity, while retaining bindings to real Sessions, image asset locators, and Composer visibility. Malformed owner/primary, Pages Library identity, Agent Dock, image locator, or kind/config combinations fail closed.
- Profile preferences are separate from Window Session layout. Per-Project view presentation, DB view preferences, sidebar collapse/width/disclosure, and bounded recent Pages persist through the focused profile-preference Adapter; they do not add another active Scene or server-data owner.
- App-window Back/Forward history and previews remain renderer-local because they are live interaction state, not cold-restore authority.
- Renderer server-state cache owns exact Project/Session detail, bounded summary windows, and bounded Page Chat projections. Sidebar rows come from Project/projectless windows, but an active restored Project or Session owner is hydrated by exact identity and never inferred missing from a bounded list. Mutations that return a full Session seed its detail cache. Board/List activity is a batched join with visible Page IDs rather than per-row hydration or Database state. Full Project Session list reads are reserved for slow domain paths and never carry Scene layout.
- Renderer presentation mounts exactly one selected owner Scene and one selected body per panel leaf. Switching disposes the previous React view; scoped renderer state restores explicit presentation, while Query and the Codex/Browser/Terminal/Document Modules preserve their own data and runtime continuity. The existing Session renderer receives a leaf compatibility projection from Scene, but there is no second writable `sessionViewsBySessionId` store.
- Renderer-local side chat state owns temporary tab identity, loading/ready/failed status, failure presentation, and panel placement. Runtime side chats create temporary bound Sessions with the parent’s captured context, Agent settings and working directory. They never execute before a new submission, show only their own messages, and retain the binding across panel remounts. Closing discards the temporary conversation; used chats ask for confirmation. Context capture, provider behavior and temporary lifetime follow [Agent Runtime behavior](agent-runtime-behavior.md). Native side-chat surfaces retain their own temporary-thread lifecycle.
- Core schema v90 removes historical `project_session_tabs`, `panel_state_json`, and `left_pane_collapsed`. It preserves Session/Thread/Project/content data and extracts at most one valid Database View target into `initial_database_view_id`; the old shared arrangement is intentionally discarded because no Window Session owner can be inferred. Historical schema v93 replaces that pointer with `database_starter`, and historical schema v99 removes the field after v98's Yjs-integrity migration: it deletes only unthreaded marked starter Sessions and preserves threaded marked rows as ordinary Sessions. Fresh Project creation creates no Session.
- Old stage-rail/window layout snapshots are best-effort migration inputs only; after decode, owner-scoped Scene state is authoritative for presentation and Core never owns it.

## Navigation

- Home restores the window's last stable Project, Session, Inbox, or empty location; leaving Scheduled through Home returns there rather than reopening Scheduled, even after Scheduled presented a run or Heartbeat chat. Space restores its existing Library Scene, including tabs, splits, and selection; the Inbox likewise restores its Inbox Scene. Switching destinations enters the same app-window navigation history as other Workbench navigation. Cold reopen retains both the selected destination and the previous Home location; removing its Project or Session repairs the checkpoint and history through the normal missing-owner transition.
- Scene switching synchronously unmounts the previous owner route and mounts the selected owner's Scene composition: a Session primary plus its panel groups, a Project's root-bearing full-width surface stack plus bottom panel and Agent Dock, or the primary-free Pages full-width stack. Exactly one owner route and one route header exist. Project selection never selects a first Session, and sidebar disclosure never changes location.
- Scene switching reuses exact cached Project/Session detail and authoritative Module state without calling the full Project Session list solely because the owner changed. Returning to an owner or panel surface creates a fresh React view and restores only explicitly owned presentation such as Composer drafts, transcript state, and registered viewport snapshots; ephemeral component-local state resets. Page Stage scopes its snapshot to the PageTab/editor-session identity and records a fully visible semantic Block anchor plus its viewport offset, with explicit top, bottom, and absolute-offset fallbacks. It restores only after the actual EditorView DOM attaches, continuously compensates layout changes from images, equations, diagrams, embedded surfaces, and other Block implementations, yields while wheel, touch, pointer, or keyboard navigation is active, then adopts the settled viewport as the next anchor. Teardown persists the last observed anchor without measuring a DOM tree that may already be collapsing.
- App-window Back/Forward controls are available as titlebar buttons, command palette commands, `Cmd/Ctrl+[` and `Cmd/Ctrl+]`, desktop mouse Back/Forward buttons, and the macOS application menu; all routes enter the same shell-owned navigation executor. The command ids are `navigateBack` and `navigateForward`, labels are `Back` and `Forward`, and the disabled state follows the shell-local back/forward stacks.
- Each history snapshot stores the exact Workbench location, previous Home location, and all owner-keyed Scene snapshots, including primary target where applicable, right/bottom active surfaces, collapse state, and right-panel full-width state. Presenting a Library target and selecting Pages commit as one transition. Settings routes, command palette state, task search, and Browser webview history stay outside this stack.
- Tab switching persists only through the owning Window Session Scene's panel leaf layout.
- Browser-sidebar webview navigation remains separate from app-window history. Browser tab `canGoBack` / `canGoForward` and `webContents.goBack` / `goForward` must not drive the top-left workbench Back/Forward buttons.
- Review is a Session Scene singleton kind across both right and bottom panels and is available only after that Session has an attached Thread. Project, Inbox, and Library Scenes cannot own Review. DB View is deduped by exact target and Canvas Stage by `(routingContext, canvasBlockId)` within its owner Scene, so repeated opens focus rather than duplicate the same target. Browser is deliberately multi-surface; creation affordances keep showing Browser even when Browser tabs already exist, and Browser tab context menus add `New tab to the right`, `Reload`, and `Duplicate` before the generic close actions.
- Tab context menus append generic close actions after feature-provided items: `Close`, `Close other tabs`, and `Close tabs to the right`. `Close other tabs` is enabled only when another closable tab exists in the same leaf; `Close tabs to the right` is enabled only when at least one closable tab follows the current tab. Cross-panel move and split actions remain below the generic close block when available.
- Tab reorder mutates only the owner Scene's panel tree; no Core Session mutation or cross-window invalidation occurs.
- Closing a persisted local panel surface removes that descriptor from the owner Scene. Every panel surface is closable independently of how many siblings exist; if it was the panel's final persisted surface, the local reducer collapses the panel and retains the final empty group as its fallback. Project and Session primaries are not closable panel surfaces; Pages has no protected primary and permits an empty tablist. Terminal backend exit removes matching descriptors after Main publishes exit; local Terminal close releases its Window Session lease without killing the PTY. Browser close tears down its Main runtime, Files/Page/Canvas close flush their owning lifecycle before removal, and closing a Conversation surface never archives/deletes its Session. Closing a preview drops only renderer-local preview state.
- Closing a Runtime side-chat tab removes only its panel placement; the product Session and its execution remain available. Session creation failures stay closable and retry in the same panel. A native temporary side-chat tab sends a best-effort discard when closed; missing native threads render an expired panel with `Start new side chat`.
- Owner routing changes are synchronous so route cleanup/setup and header ownership complete in one deterministic lifecycle. Lower-priority data refreshes may still use transitions, but routing itself must not have warm/cold branches.
- React keys should reset only the active Scene/surface body that changed; switching owners must not force unrelated global stores to remount.
- When a full-width right-panel tab collapses the primary viewport to zero width, the selected route and owning runtime stay active. In a Session Scene, Composer, footer, and lifecycle coordinator remain active while transcript children unmount. Restoring regular width remounts primary content from its explicit runtime state.
- Only the selected Scene may register shell side effects such as global header actions, summary panels, composer overlay targets, panel measurement refs, or visible Browser webview ids.

## Keyboard Model

- Existing global command palette, settings, and editor shortcuts remain in force. Undo/redo is local to the focused editable surface; the shell owns no Project-wide history stack.
- Native Zoom and Undo/Redo target the frame that currently owns input focus. Hidden retained pages and standby interactive responses cannot take those commands from Workbench; a focused embedded page keeps its own commands.
- The previous stage-order shortcuts (`View -> Card -> Thread -> Diff`) are retired as primary shell semantics.
- Project/Session/surface keyboard shortcuts follow the hierarchy: Project disclosure control, Project navigation control, Session row, owner primary, and right/bottom panel groups.
- `Cmd/Ctrl+J` executes the shell-global `toggleBottomPanel` command and shows or hides the selected Scene's bottom panel. Toolbar, command palette, Browser-runtime keyboard handling, and desktop application menu share the same shell executor; Electron owns the desktop accelerator so one keypress cannot toggle twice. It works from editable and desktop Browser surfaces, preserves explicit user unassignment, and safely no-ops only when no Scene is active.
- `Ctrl+\`` focuses an existing eligible Terminal surface or creates one in the selected Scene's bottom panel. `Alt+Cmd/Ctrl+S` starts Side chat only in an eligible Session Scene. The global terminal drawer is not part of the Scene model.
- `Cmd/Ctrl+Shift+[` and `Cmd/Ctrl+Shift+]` cycle the previous/next tab for the focused right or bottom panel tab group in the selected Project, Session, Inbox, or Library Scene. Cycling resolves the nearest split leaf or the last focused leaf from the native menu route, wraps within that leaf, works from Page editor content in that leaf, no-ops for zero or one tab, and does not replace plain `Cmd/Ctrl+[` / `Cmd/Ctrl+]` app-window Back/Forward.
- `Cmd/Ctrl+W` closes the active closable tab in the focused right or bottom panel tab group through the owning Session or Scene tab adapter, with the same close semantics as tab chrome. It works from Page editor content in that leaf, ignores input fields and dialogs, no-ops for non-closable tabs, and must not close the app window. Closing an inactive tab preserves the current selection. A Browser tab created or duplicated to the right records its opener in an ephemeral, generation-scoped tree. Closing an active current-generation child selects the nearest right descendant of the same opener tree, then the nearest left descendant, then its opener. Selecting an unrelated tab or moving/reordering a tracked tab invalidates that affinity. Without a valid opener result, selection stays within the same split leaf and follows physical order: the right neighbor first, then the left neighbor at the row edge. Visit recency does not override either rule. Close-button and middle-click single-tab closes use the same routing. On macOS, Close Window uses `Cmd+Shift+W`.

## UI Contract

- The navigation rail is 52px wide with 36px buttons spaced 8px apart. The shared titlebar is 44px high. The rail, contextual sidebar and opaque content surface begin below that titlebar; the content frame retains 4px end and bottom gutters. Titlebar and rail share the window frame. When navigation is pinned, its 65% surface owns the outer left corners and opaque content owns the right corners; their internal hairline divider stays flat and continues into the titlebar as a short column divider before titlebar content and before a split content pane's tabs. One page-surface shadow outlines the sidebar and content as a single 12px-rounded page. Dividers and hairlines use the theme's translucent border ink, so they read equally light over the frame, the sidebar, and opaque content. Top-edge content tab rows occupy the titlebar outside the clipped content surface; lower split and bottom-pane headers remain inside their panes. Native window buttons and renderer controls consume one shared geometry contract, including scale-aware native safe areas.
- Window dragging belongs to the titlebar box alone. Every titlebar control (buttons, links, inputs, tabs) is a no-drag hole, while empty titlebar space, spacers, and titlebar content wrappers drag the window; titlebar content declares no drag behavior of its own. Body content never drags the window. Clicking a titlebar control of an inactive window performs its action on the first click.
- Titlebar tabs are dense pills: the selected tab is a raised surface with a hairline border, other tabs show only a hover fill, and the inline `+` follows the last tab without a backdrop of its own. Overflowing tabs and titles fade through alpha masks so they blend with the pane or the translucent titlebar.
- The collapsed-sidebar peek is an opaque elevated surface with an 8px radius, hairline border, and card shadow; it slides in briefly and settles out faster.
- A chat has one workspace control group in the global titlebar: `Enter full view` / `Exit full view` (`⇧⌘F`, shown in its tooltip) and the Tabs control. While content sits on the left in split view, `Enter full view` instead ends the content's own tab strip, before the column divider and the Chat's title row, and the global group keeps the Tabs control. Hiding its right content pane retains its tabs and selection. While hidden, the Tabs button shows the retained count (`9+` above nine with an exact accessible count); hover opens the live-title chooser, and clicking the button restores split view. Hiding the pane does not open the chooser under a resting pointer; it opens on the next hover. Choosing a row opens split view; its expand action opens full view. In split view the Tabs control hides the content pane, and in full view it restores split view. Full view is reachable from split or hidden presentation and preserves the selected tab. Keyboard entry and Escape preserve focus. Closing individual tabs remains separate from hiding the pane. Project and Space primary content stays visible and does not acquire chat-only collapse controls. In split view, Chat actions offers `Move to right pane` or `Move to left pane` (the content's side) after Copy; it is absent in full view. In full view, the top-left content strip leads with a fixed Chat tab: the chat bubble, the Chat's live title, and an always-visible Chat actions menu. While a content tab fills the view, the bubble carries the chat's live status as its sidebar row does: a spinner while it runs and a dot when it needs attention or has an unread reply. The tab cannot be closed or dragged, and its separator shows only when neither it nor the tab beside it is selected. Selecting it fills the Scene with the Conversation while every content tab stays listed and none is selected; selecting a content tab returns to it. Double-clicking the Chat tab returns to split view, and its context menu (native on the desktop, with arrow icons) offers `Move to left pane` and `Move to right pane`, which return to split view with the Chat on that side. Exiting full view with no content opens a New tab beside the Chat.
- Surfaces should use the generated theme layers and token classes before adding local CSS.
- The default palette uses the shared surface and foreground roles in each appearance. Terminal backgrounds and text use those same roles; the cursor follows the foreground, selection uses the shared scrim, and ANSI colors follow the semantic accent and text hierarchy. Navigation tools use the secondary ghost control role at rest and its primary foreground on hover or selection. Sidebar section titles use the tertiary text role once, without multiplying it by another opacity; primary navigation labels retain their shared muted-ink treatment.
- Native desktop chrome shows the window's native material through one frame tint (the secondary surface at 85% in light, the tertiary surface at 80% in dark). The rail and titlebar add no paint of their own; content surfaces remain opaque. An unfocused window, a very large window, or Reduce transparency switches the window to its opaque color under the same tint. Browsers use the same sidebar palette.
- Left titlebar navigation uses one grouped toolbar rail. Back renders lucide `ArrowLeft` with `icon-xs`; Forward reuses the same icon with `icon-xs -scale-x-100`. Each button has matching `aria-label`, `title`, tooltip text, command palette title, and disabled styling. ### Workspace Files search

Local file comparison and blame reads follow the [Files Git data contract](workspace-file-git-data.md).

File results and references open in the active Session, Project, Library, or Inbox Scene without creating a chat. Reopening a matching file focuses its existing tab and reveals the requested one-based line and UTF-16 column. Pinning or restoring a file keeps its host and path. Replacing a preview saves its edits first; failed saves retain the current preview, and a superseded opening request cannot replace it.

Files search shares the host-scoped native fuzzy-search session with Composer and Command Palette. Query, root, and runtime changes fence stale results; closing its consumer releases the session. Directory browsing retains the selected host, including home-directory expansion, and fences remote results by connection generation and capability source. Local directory browsing reads entries asynchronously and sorts in yielding batches so wide folders do not monopolize Main. Local imports and folder manifests apply their entry budgets while traversing, before sorting.

Files tabs identify each file by its host and canonical absolute path. Preview, pinning, switching groups, and reopening a saved Scene preserve that host; equal paths on different hosts are distinct files. Content samples identify text, image, PDF, audio, video, archive, or other binary content and its detected MIME type independently of the filename. Previews have a 256 MiB size ceiling. Local audio and video stream through the renderer's protected media route with byte-range seeking. Base64 reads, including remote media, default to a 128 MiB limit and can request a smaller limit; oversized reads fail before transferring the full file. Remote text, Markdown, image, PDF, audio, and video previews read bounded bytes and size from their source host. Unavailable modification metadata remains unknown. Remote previews do not create an editor, local file watcher, or local directory query, and they do not substitute Project folders or open a remote path in a local editor or Finder. File references and copy-contents actions inside a remote preview retain its host. A failed or retired host read remains an explicit read failure, without a local fallback. Saving a local file copy uses the native destination picker and copies the file directly, without a preview size limit. Repository metadata supplies the configured origin URL, or null when none is configured. On macOS, an existing local file can query its default application (the well-known viewer for its type when installed, otherwise the system default) and up to 20 other compatible applications in system order, with names and icons; Nodex itself is excluded. Opening a file uses either the system default or an explicitly selected application bundle. Other platforms return an empty application list.

The Files viewer chooses its body from the sampled content: images, PDFs, and MP4, WebM, and Ogg video and common audio open in their rich preview; Markdown and SVG toggle between rendered and source views (a file opened at a location starts in source); other text opens in the source editor or, from 10 MB, read only. Other video and audio, archives, office documents, binaries, and files above a preview limit show why they have no preview. Video plays in a player with seek, volume and mute, playback speed, picture in picture, fullscreen, and Save video as. Its header keeps floating controls on one row: the file's breadcrumb, whose ancestor folders hide first when space runs short; copy-path actions for the repo-relative, project-relative, or absolute path; Open in GitHub for a file in a GitHub checkout; and file controls (Search in files, viewer options, Open, and the file-tree toggle) that fold into one menu below 625px. Each breadcrumb segment opens a listing of its folder's contents with that segment selected (the workspace segment lists the workspace root), and choosing a file there previews it. Open uses the preferred editor for text and the default application for documents and media, and its menu lists other applications, Open in folder, Open in GitHub, and Save as. Viewer bodies and the file tree leave room for the floating composer.

Editable text uses the editor header instead: the breadcrumb, Show changes, and file controls (Search in files, View source or View preview for Markdown, the file-tree toggle, and Open). Show changes compares the draft with a Git source and keeps that source for the file; it chooses the first of Unstaged, Uncommitted, and Branch that changed the file. While shown, the header offers the source picker (Uncommitted, Unstaged, Staged, Committed with the branch's commits, Branch), Hide changes, a change navigator that counts change blocks and steps between them without wrapping, and a unified or split layout toggle remembered across files and windows. Live comparisons stay editable; Staged and Committed comparisons are read-only. The palette command Enable Git blame (or Disable Git blame) shows the author, subject, commit, and date of the caret's line in every Files editor; edited lines show none.

In a Git repository, the file tree splits into Changed files and All files once the folder has changes. Changed files lists the folder's changes against the remote base branch when one exists, otherwise its working-tree edits, marking added, deleted, and modified files and the folders that contain them. A filter narrows both sections without removing them. Choosing a changed file opens it showing those changes. In a Session that can show Review, All changes above the tree opens Review for the same repository and comparison. Section and folder collapse persist per host and folder for the window.

Embedded file images in rendered Markdown resolve beside the source document, on that document's host. Absolute file paths and responsive picture candidates use the same host-scoped reads; they never inherit the renderer's filesystem route or opaque resource capabilities. Explicit HTTP(S) and inline image data remain subject to the renderer's resource policy. File images have a 25 MB decoded preview limit, including when metadata size is unknown. Switching documents or hosts discards late results and releases retired image URLs. Refreshing a remote preview reads its current text and image bytes again.
