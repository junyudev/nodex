# Workbench Shell

## Intent

The Workbench has five rail destinations, including Insights: Home for chats, Projects, and Inbox; Space for Pages, Databases, and Canvases; Automations for standing Agent work and its decisions; Plugins (Customize) for plugins and skills. Home presents each Project as a folder in its sidebar. Expanded Projects show durable Project-owned Sessions, but a Project can have zero Sessions until the first ordinary New Chat action ensures its Core-owned default draft. Each Window Session renders an owner-scoped Scene through one shared composition: a Project Scene's protected root is the Project's own Inbox with its Views as ordinary tabs beside it, the singleton Inbox Scene's protected root is the Library Inbox with Library content as ordinary tabs beside it, a Session Scene keeps Conversation as its primary plane, and Space uses the singleton Library Scene to present trusted Library content as ordinary tabs without a protected primary. A Project Agent Dock can observe and send to one real Session without changing the selected Scene. Core-backed domain data remains shared; Scene surfaces, Dock presentation, and panel arrangement do not synchronize across windows.

Permission modes and approval lifecycle are specified in [Agent Permissions and Approvals](./agent-permissions-behavior.md).
Thread Summary content and row actions are specified in [Thread Summary Panel Behavior](./thread-summary-panel-behavior.md). Automations, Inbox, and Settings route behavior is specified in [Automations Behavior](./automations-behavior.md), [Inbox Behavior](./inbox-behavior.md), and [Settings Route Behavior](./settings-route-behavior.md).

### Where the keyboard lands

Opening a chat from the sidebar, chat shortcuts, Search, a notification, a
Readback, or the Agent Dock puts the cursor in that chat's composer. If the chat
is waiting for an answer in place of its composer, focus goes to the request's
primary control. Settle, Snooze, and Archive give the keyboard to the successor
chat, including a replacement draft after archiving a Section. Undo gives it to
the restored chat when it returns to that chat. Opening a chat in a new window,
reopening a side chat, or opening a blank remote side chat focuses its own
composer. Selecting a different Agent Dock target gives focus to the Dock
composer. Escape from its picker returns focus to the picker button.

Opening a Project preserves its active surface and focuses its Inbox composer
when that surface is Inbox Home. Back and Forward restore the chat composer,
Inbox composer, or panel tab that held focus when the reader left the entry, if
that destination is still available. Startup restoration, Agent navigation, and
background refreshes leave the keyboard where it is. A delayed arrival yields
if the reader has moved focus elsewhere.

Closing or cycling a panel tab with the keyboard puts focus on the selected
tab in the same group, or on the Scene's primary landing if the group has no
tab. Hiding a right panel that held focus hands it back to the chat composer.
Closing Settings returns focus within the restored Scene. Closing Find returns
focus to the searched chat, Review, Page, or Browser page. Rename returns focus
to its trigger when available, or to the Scene's chat composer.

## Layout

- Navigation rail: two groups separated by a hairline. Places holds Home, Space, Automations, then Plugins; Insights sits alone below the hairline. Insights sits beside the Home sidebar, as specified in [Insights Behavior](./insights-behavior.md); the others own a contextual sidebar, and Plugins opens Customize, whose sidebar lists Plugins, Skills, and the installed plugins, and whose pages are specified in [Plugins Behavior](./plugins-behavior.md). The rail remains visible when the contextual sidebar is collapsed and while Settings is open. Selection follows the Workbench location, including the return location while in Settings. Every destination previews its sidebar on hover.
- Home sidebar: Projects render as folders with separate navigation and disclosure controls. The visible Project label opens its Project Scene without changing disclosure; the leading marker becomes a chevron on row hover/focus and only folds or expands Session children. A Project's Inbox count and row actions share the same trailing area: the count rests at the right edge, and hover, keyboard focus or an open row menu replaces it with the actions. A collapsed Project adds one status beside that count with the chat row glyphs: waiting when any chat waits on its person, otherwise the unread dot when any chat is unread, otherwise a spinner when any chat is working; an expanded Project shows none. Runtime chats' live state counts toward their collapsed Project and custom Section.
- Chat row status: each Chat row shows at most one status in a 20px slot at its trailing edge, after the title and any resting pin, and hides it while hover, keyboard focus or an open menu reveals the row actions. Each status has its own glyph. A chat waiting on its person, for an answer or an approval, shows the question bubble its reply panel opens with, in the attention tone; otherwise a working chat shows the spinner (muted and slower for background work), and an unread chat shows the unread dot: an 8px accent dot. A native chat asking for approval or input is waiting, not working. With none of these, the row rests on what its person left behind, in the muted description tone: a pencil while its Composer holds unsent text, otherwise a clock while it has a snoozed chat, which a row in the `Snoozed` lane replaces with when the chat returns. A draft is the root Session Composer's text, wherever that Composer is shown; side chats and delegated children do not count. An unread or waiting chat keeps that fact in the row's accessible description even while its spinner shows, as do an unsent draft and the `Snoozed until` label with its absolute time, and the row's accessible name stays its title. An unread chat that came back because its snooze came due shows a clock in the accent tone instead of the dot, named `Back from snooze`, until its Member reads it. The chat hover card repeats the waiting glyph and the unread dot after the chat's age. While the chat works, the card shows what its agent said it would do in the active Run, its [Readback](./desktop-notification-behavior.md#readback), under the title in compact Markdown that scrolls past six lines. It then lists the draft's first line and when the chat wakes. The Chat tab's bubble, the Project Agent Dock's chat picker and a Page's chat activity glyph use the live glyphs only; collapsed Projects and Sections never summarize drafts or snoozes.
- Chat archive: archiving one chat from its context menu, Chat actions menu, the command palette or `⇧⌘A` shows an `Archived chat` toast with the gesture. `Undo` waits for the archive to land, restores the chat in place, returns to it if it was open, and confirms `Chat restored`; `View` opens Settings → Archived chats, which lists every archived conversation; a draft with no conversation isn't listed there, so `Undo` is how it comes back. A failed archive replaces the toast with an error and keeps the row. Bulk archives report a count and offer no Undo.
- Chat lifecycle: every chat is open or settled for each Member, who decides for themselves, as they do their pins. `Settle` is the row's trailing hover action (a check), a context-menu item, a command palette command, the Agent tool `set_session_settled`, and `⌥⌘E` for the current chat; on a settled chat the same control reads `Reopen`. Settling a chat unpins it, ends the Member's snooze, clears their unread dot, shows a `Settled` toast whose `Undo` reopens the chats whose settlement changed, and, when it was the chat on screen, opens the chat that takes its place in the list. A chat stopped on its person, for an answer or an approval, cannot be settled until they answer. A settled chat reopens by itself when its Member sends it a message, marks it unread or pins it, or when its Agent stops and asks for them: a finished reply, a question, an approval, or a snooze ending. A quiet Automation run reopens nothing. Archive is separate and stays in the context menu and on `⇧⌘A`: it removes a chat from every list until it is restored.
- Chat snooze: `Snooze` sets an open chat aside for its Member until a time. It is the clock beside Settle among an unpinned open chat's hover actions, a context-menu submenu, the command palette's snooze commands, which `⌥⌘Z` lists for the current chat, and the Agent tool `set_session_snooze`. Its menu offers the same times as the Inbox's Snooze, each name with the time it brings the chat back beside it, then `Custom`, which opens the same [custom time picker](./inbox-behavior.md#snooze); on a snoozed chat it first says when the chat returns and offers `Wake`. The chat's right-click menu offers the same times by name and time, without `Custom`. Snoozing unpins a chat, so a pinned row shows its resting pin there instead, and pinning lives in the context menu and in dragging to `Pinned`. Snoozing the chat on screen opens the chat that takes its place and confirms the time with `Undo`. A snooze defers what the chat was asking when it was set; a new question, approval or failed Run brings it back early.
- Idle chats: `Settle idle chats` in the Projects header's sidebar options menu settles a Member's chats once they have asked nothing of that Member for 1, 3, 7 (the default) or 30 days, or `Never`. Idle time counts from the chat's attention time. Pinned chats, unread chats, chats with a snooze, chats still working or waiting, and chats that never started a conversation are left alone; a custom Section only arranges chats, so one filed there settles like any other. An open window applies it when it opens and hourly. When a Page moves to Done, its Active chat settles in the same change for each Member using those same exclusions.
- Sidebar arrangement: the header's `Attention view` toggle, lit while it is on, switches Home between two arrangements of the same open chats (`⌥⌘U` toggles them); the Profile remembers the choice. A new Profile starts with it off, showing `By project`. Until the Member has met it, [its tip](./first-run-behavior.md#tips) points at the toggle when two chats ask for them at once. `Attention view` lists the chats in lanes by whose move each chat is: `Pinned`, the Member's standing chats in their own order; `Active`, the chats waiting on them; `Working`, the chats whose Agent is working, in the foreground or background; then `Snoozed`, soonest first; then Projects; then the `Settled` shelf. Each chat sits in one lane only, so a chat filed in a custom Section takes the lane its state puts it in. `Active` leads with the chats an Agent is stopped on and then lists the chat that came back most recently first, by attention time: when its Agent last stopped and asked for the Member, or its activity when that is later. Unread is only the dot on a row, so reading a chat never moves it. The lanes hold still under the Member's eyes. While the pointer is over the sidebar or the keyboard moves through it, every row they saw keeps its lane and place; a chat that came back meanwhile appears once they leave, unless it lands below every row they saw, as a page they asked for does; a chat they pin, unpin, reorder among their pins or snooze moves at once, and a settled chat leaves at once. The chat on screen keeps the lane and place it had when it was opened until another chat is opened, so answering it never sends it to `Working` under their eyes. Each row names its Project after the title, keeping its whole name up to two fifths of the title line; a title or name too long for its place fades out at its end rather than ending in an ellipsis, as Project and Section names in the sidebar do, and says what the chat is about underneath in muted lines: the approval its Agent waits on, otherwise what the Agent said it would do in the Run it is working on, otherwise its latest reply, the final message of its latest settled Run, read as plain text. Rows in `Pinned`, `Active` and `Working` say it in up to two lines, `Previews` in `View options` (`Two lines`, the default, `One line` or `Off`); the lines are reserved whenever the chat has said something so rows line up; a row whose only line is its Page's words keeps one; a chat with nothing to say yet, a draft or a chat run outside the Agent Runtime keeps a one-line row. Snoozed and settled chats ask nothing now, so their rows keep to the title line whatever `Previews` says. The row's actions stay on its title line. A row reads its reply again only when the chat comes back to its person, keeping the reply it shows meanwhile, and the rows a list shows ask for their replies together. Rows in the Project tree stay one line. `Active`'s header offers `Settle N read chats` while it holds chats that are read, ask nothing and are not working; it settles them together, with one `Undo`. A lane with no chats is hidden, except `Active`, which says `Nothing is waiting on you`. A `Snoozed` row ends with when its chat returns, in place of the clock: its time when that is today or within six hours, then `Tomorrow`, a weekday within the week, and a date beyond it. Chats back by the end of tomorrow lead the lane; the ones returning after that step back behind one row that counts them and says when they return, such as `2 later · Mon – Dec 8`, and shows them in a quieter tone until `Show less` folds them again. A single later chat shows without the fold, and the chat on screen always shows. As each day turns and each return comes within hours, the rows read again. `View options` stays beside the view's first heading (`Pinned` when it shows, otherwise `Active`) whether or not the pointer is over it. It shows or hides `Pinned`, `Working`, `Snoozed`, `Projects` and `Settled`; `Active` always shows. Its `Chats from` lists `All projects` and each Project with its Inbox count, its `Previews` sets the preview lines, and `Show everything` restores every list and Project; the Profile remembers each choice. Showing one Project puts a chip beside the toggle, in the title row so nothing below moves, that names the Project and returns to every Project when clicked; the lanes, the `Settled` shelf, the Inbox entry and `New chat` then cover that Project alone, and its rows drop the Project name. Projects follow the lanes as places: a row opens its Project Scene and starts a new chat there, keeps its Inbox count and status, and has no chats to unfold, because every chat is already in a lane. `Pinned` rows drag into a new order as they do in the Project tree, while chats join and leave `Pinned` through their row actions; every other lane keeps its own order. Custom Sections and dragging chats between lists belong to `By project`, the Project tree described here, which lists each Project's open chats beneath it.
- A chat row whose Page is waiting on the reader leads its preview with the same words as the Page's Turn, such as `Ready for your review`, in the attention tone. In review, the row offers `Accept` by name in place of the Settle check; it accepts that episode of work behind the Undo described in [Inbox behavior](./inbox-behavior.md), and the row stops asking at once.
- Every row action names itself in a tooltip above it, with its shortcut when it has one for that chat: `⌥⌘E` and `⌥⌘Z` act on the chat on screen, so only that row's Settle and Snooze tooltips show them.
- Settled shelf: both arrangements end with one `Settled` shelf of the Member's settled chats in the selected scope, most recently settled first. It starts collapsed. It shows ten rows, and `Show more` reveals five more at a time, up to sixty. While the shelf holds chats it does not show, its pager also offers `View all N`, counting every settled chat in scope, which opens the Settled page; past sixty rows it is the only way further back. Once the shelf shows every chat it holds, the pager says `That’s all` beside `Show less`. Refreshing the shelf keeps every row the Member had already revealed, and reading more never stops silently: a read that fails offers `Couldn’t load more · Retry`. The heading's `Open Settled` opens the Settled page at any time. `Snoozed` starts open, since it folds the chats returning later by itself; collapsed, it shows how many chats it holds.
- Settled page: a page over the current Scene, beside Home's sidebar, that lists every settled chat in the shelf's scope, or in the Project its `All Projects` picker names, most recently settled first under `Today`, `Yesterday`, `Previous 7 days`, `Previous 30 days`, then each month. Its heading counts them. Its search matches a chat's title and its first message, ignoring case, and the count follows the search. A row shows the chat's title, when it was settled (the time for today and yesterday, otherwise the day), its Project while the page shows every Project, and its first message; clicking opens the chat, the row's hover `Reopen` reopens it, and its context menu is the chat's own. Scrolling reads older chats until the list ends, where the page says `That’s all N settled chats`, or `That’s all N matches` while searching; a read that fails says so and offers `Retry`. The window remembers the page and its Project, and closing it returns to the Scene underneath.
- Chat travel: `⌥⌘↓` and `⌥⌘↑` open the next and previous chat in the sidebar's order, wrapping at either end, and `⌥⌘A` opens the next chat that is waiting on the Member or unread. Collapsed lanes and folded Projects are skipped.
- Chat snoozes: a chat's context menu and its Chat actions menu offer `Snooze` with four presets: in 1 hour, in 3 hours, the next 9:00 AM at least three hours away (this morning in the small hours, otherwise tomorrow), and Monday 9:00 AM of the following week; a preset that lands on an earlier one's time is left out. The command palette lists the same presets by name and resolves the time when the command runs. Choosing one replaces any pending snooze and confirms the time in a toast; a pending snooze's menu first states when it fires, with `Wake` right below. When the snooze ends, the chat becomes unread again with a desktop notification and returns to the top of `Last updated`. Snoozing unpins the chat. Pinning it, settling it, sending it a message, or a new question, approval, or failed Run can end the snooze early. The Woke marker for a timed return clears on seeing, messaging, settling, or re-snoozing the chat. Pins, their order and snoozes belong to each Member of a Space; in a team Space the host turns the chat unread for the Member who set the snooze, on every Device of theirs, and the chat keeps its place in everyone's activity order. Mark as unread (`⇧⌘U`) is the immediate form: it keeps the dot on the current chat until new activity or direct interaction with its transcript consumes it.
- Space sidebar: Content lists the Library's root Pages, Databases, and Canvases in Library order, including Project resources and the Library Inbox Database. Opening, selecting, or editing content never reorders Content or changes which rows it lists; only creating, moving, reordering, or removing roots does. New content enters at the top, so the first page always shows what was just created. It reads bounded continuation windows whose identity is independent of selection, keeping one row beyond its revealed depth loaded, and an active root outside the loaded rows joins after them. Its first header row, `New page`, creates a root Page and opens it; the row's trailing `New Page or Database` menu creates either root kind. Resource actions and Library reordering remain available; selecting a root opens or focuses its ordinary Space tab.
- Space home: an empty Pages leaf shows the Space home rather than a blank pane or a picker behind another click. It has a `Space` heading with an inline Search and a `New` menu (Page, Database), kind tabs (Recent, Pages, Databases, Canvases), and Library content in last-edited order with Location and Last edited columns. Search filters titles, and Page content when Pages are included, in place; Escape clears it. Opening a row presents it in that leaf. Each kind has its own empty and no-results message, and the list loads more as it scrolls.
- Contextual sidebar: Home, Space, and Automations share a 288px default width, collapse, resize, and floating-reveal behavior. While the sidebar is collapsed, resting on a rail destination for 100ms previews its contextual sidebar without changing the routed content; moving to the other destination switches the preview immediately. The peek begins 4px beyond the rail and 4px below the titlebar, keeps the pinned sidebar’s right edge, and adds no duplicate window navigation. Content-edge movement alone does not open it. The peek stays open while the pointer travels from the rail toward it (an aimed path that lapses after 1s without progress), rests on it or on the rail's destination band, while one of its menus (including native context menus) is open, while focus is inside it, and during a drag that started inside it. Otherwise it closes 100ms after the pointer leaves; Escape, another rail action, or pinning the sidebar closes it at once, and Escape suppresses reopening until the pointer leaves the destinations.
- Project children: each expanded Project lists ordered Sessions. A new Project starts with zero Sessions and still opens its Database immediately. Its first ordinary New Chat action immediately ensures one durable default-draft Session and lists it; repeated actions select the same Session until first Thread link or Archive releases the slot. Every New Chat action, from `⌘/Ctrl+N` (also while typing in a composer or Page), the command palette, the sidebar, or the titlebar, focuses that draft's composer and keeps any text already in it.
- Sidebar pagination: Projects, Project children, Chats, custom Sections, and Space Content show a first page and grow five rows at a time: `Show more` reveals the next five, and `Show less` returns the list to its first page in one press, however far it was revealed. Each press eases the rows' height to its new size over 300ms on the sidebar's disclosure curve, the same motion that folds Projects and sections: `Show more` mounts its rows at once and their edge unfolds over them from the top, while `Show less` keeps its rows in place as the edge folds up past them and removes them once covered. The pager rides that edge and stays on screen throughout, and everything below the list moves with it; when `Show less` is pressed with the list's top scrolled out of view, the sidebar scrolls back as the list folds, so the pager stays where it was pressed and the first page comes into view above it. Rows a list reads from its source join the same motion; reduced motion settles it immediately. A single unselected row left beyond the revealed rows is shown with them rather than behind its own `Show more`, unless the list still has rows to read. The selected row stays visible without taking a page slot: selecting a listed row never changes which rows are listed, and a selected row beyond the revealed rows joins in list order as one extra row. `Show more` appears only while unselected rows are hidden, and `Show less` only when the first page would hide one; after either press, focus stays on the pager, and moving focus there never scrolls the sidebar. Every paginated list (Pinned, Projects, each Project's chats, Chats, custom Sections, and Space Content) remembers how far it is revealed as a Profile preference, like section collapse, so switching destinations, reopening the window, or relaunching restores the same rows; a list that reads its rows in windows reads further until that depth is filled.
- The Chats header menu offers `Sort chats into projects`. The confirmation shows how many unarchived projectless root chats with available working folders would move to each existing or new Project or stay in Chats. Sorting follows [the same folder placement as imports](native-conversation-connection-behavior.md#importing-native-conversations) and moves chats through ordinary Project placement, keeping their history and working folders.
- Sidebar Sections: users may create named custom Sections in Home above the Projects group from a Project or Chat context menu and place Projects and Project Sessions into one mixed ordered list. The Projects header has no duplicate create-Section action. Moving a Project changes only its list placement: the same Project row renderer, disclosure state, marker, actions, hover card, child rows, pagination, and context menu are used in Projects, Pinned, and custom Sections. Moving a Session likewise changes only placement: custom Sections use the same Chat row renderer, title and status presentation, hover card, hover-revealed Pin and Settle actions, rename behavior, and native context menu as Project, Pinned, and Chats lanes. A directly placed Session is a root-level row aligned with the Section content edge; only Sessions rendered as Project children use the grouped indentation, which keeps an empty leading column so their titles align under the Project name; their status uses the same trailing slot as every Chat row. A collapsed custom Section shows the same single status glyph at the right end of its header, with waiting before unread before working. A Session's direct placement overrides inherited presentation from its Project; the Session remains owned by that Project and is omitted from the Project's nested list while directly placed. Pinned and custom placement are mutually exclusive. Project and Chat rows may be dropped onto an empty, populated, expanded, or collapsed custom Section; hovering the Section header or its empty space highlights that whole destination with the sidebar hover background and inserts at the start of its mixed list. The target remains mounted while collapsed and extends through the gap below the Section. Populated Sections resolve the pointer above or below either item kind to one exact mixed insertion boundary with the blue rail and outlined leading dot, without also highlighting the container. Dropping preserves the destination’s disclosure state. Reordering within a Section uses the same mixed boundary and one atomic Core item move. A Project row's narrow top and bottom edges remain mixed-list insertion boundaries while its center and leading target accept a Chat into that Project. While an external Chat is over any whole-Project target, the outer Project group—including its header and children—shows one 2px inset accent ring, 10px radius, and a 10% accent tint; nested row/icon/gutter targets must not add separate gray hover blocks. Custom Sections and their contents support pointer and keyboard organization; `Alt+ArrowUp/Down` moves a focused Section. Collapsed state is a Profile preference, while definitions, placement, and order remain Core state. The header shows aggregate waiting, unread or running state even while collapsed and creates a durable threadless projectless Session directly in that Section. Its overflow menu contains `Edit section` and `Delete section`. It offers `Archive all chats` when the Section has chats; Section order is changed by direct drag or keyboard organization, not duplicate move commands in this menu. Archive all is a confirmed, set-based action over every effective Session, including inherited Project children; when it archives the selected Session, Workbench creates and selects a replacement draft in the same Section. Deleting a Section releases its visible organization without deleting its Projects, Sessions, or Threads and offers Undo.
- Sidebar header: Home, Space, and Automations share one header so switching destinations never moves it: a 52px title row (`Nodex`, `Space`, or `Automations` at 18px semibold, with trailing 28px Search; in the personal Space, `Nodex` leads with the [Nodex mark](./new-chat-home-behavior.md#hero-mark) inside the title, so the title still starts where the others do) followed by the destination's 30px primary rows, which always begin at the same position. Home's rows are `Inbox` then `New chat`; Space's row is `New page`; Automations’ row is `New rule`, and its Search toggles an inline field instead of opening the command palette. The `Inbox` row sits directly above `New chat` and opens the Inbox Scene on its Inbox tab, keeping any tabs opened beside it. Its trailing count is the number of messages still in the Inbox, shown muted; the `⌘/Ctrl+Shift+D` keycap appears only on hover.
- Rail update: an app update appears at the top of the rail foot from the moment it starts downloading until it installs, as a 24px accent disc. While the update downloads the disc fills with its progress, and while it installs it spins. Once the update is ready the disc shows a download arrow, and clicking it restarts Nodex to install the update. Hovering or focusing the disc opens a card with the update's state, its version, the headline its release notes open with, and the lead sentence of its first three changes. A ready update's card also offers `Restart to update` and `Later`, which hides the disc in every window for an hour. Nothing else announces a ready update.
- Rail foot: from the bottom up, the account menu (`Spaces and settings`), the native Codex account control, and one usage meter per reported subscription account sit at the bottom of the navigation rail, so all stay reachable with the contextual sidebar collapsed and while Settings is open. The account menu and enabled account controls keep their order below subscription meters, so subscription meters appearing or disappearing above them never move them. The account menu answers which Space the window shows and who you are: its face is a team Space's avatar, or your Nodex Account in the personal Space, and its menu switches and joins Spaces as [Team Spaces](./team-space-behavior.md) describes, then holds the Nodex Account, Settings and the way to reach the Nodex community. The rail has no other Space control. Nodex identity is independent of native Agent authentication; its menu and Account page follow [Nodex Account Login](./nodex-account-login-behavior.md). A usage meter is the provider's mark inside one ring that shows what is left of the account-wide window that runs out first; a model-only window such as `Weekly · Fable` never drives it. The ring stays neutral, turns amber at 35% left and red at 15%, and draws a red track once a window is used up. The whole arc always reaches the account's longest window's level, such as the weekly. While a shorter window such as the 5-hour has less left, the arc is solid only up to the shorter window's level and continues faintly beyond it: headroom the shorter window holds back until it resets. A used-up shorter window paints only that held-back stretch red, so a wait of hours reads apart from a used-up week. A reading older than 30 minutes stays visible but dimmed; a window whose reset has passed since the reading is unknown, never assumed full; a dotted ring means nothing current is known; an amber dot means the latest read failed and the previous reading, if any, is shown. Hovering or focusing a meter opens its card: provider, plan and signed-in address; one bar per window with what is left and when it resets, where a used-up window says `Limit reached` and counts down to its reset, and a window holding back a longer one counts down too; and a footer that separates the account's limits, which count use from every app and device, from this computer's reading of them: when it was taken, or that it could not be refreshed and which reading is shown. A signed-in Codex account's card adds `Sign out` and any available quota resets, kept behind a disclosure so a passing pointer cannot spend one; Codex refreshes its reading every minute and when its card opens. A personal Codex plan with prepaid credits also lists them below its windows, as whole credits rounded up or `Unlimited`, without a bar, because a balance has no full mark. An account with none shows no row, and a workspace plan never does, because its balance is a pool shared with others. Credits carry a personal account past a used-up window: while the window that runs out first is used up, the row says `In use` and the ring's used-up tone is amber rather than red, turning red only when no credits are left. A Codex API-key account shows an empty ring whose card says no subscription limits apply. A signed-out Codex account shows its mark in an open ring with a plus where the ring opens; its tooltip and the sign-in popover it opens beside the rail both say `Sign in to Codex`, so it is never taken for the Nodex account. While the Codex account is still unknown the slot holds a dotted Codex meter that breathes while the account loads; when it cannot load, it rests with an amber dot and its tooltip gives the reason. Nodex keeps retrying, and clicking it asks again at once. Claude meters show what Claude Code reports when Nodex checks a Claude Agent, through the same check that lists its models, and while it replies; Nodex never asks the account directly. Each reading is dated by when Claude Code fetched it: Claude Code may answer from a reading it stored, including one up to an hour old when it cannot reach the usage service, and such a reading keeps its earlier time. Nodex keeps one Claude reading for every window. While a Claude meter shows and Agent execution is running, it reads again once the reading is five minutes old; while execution is stopped nothing reads on its own and the meter keeps its last reading. Opening a Claude card reads again unless that happened within the last minute, starting Agent execution when it is stopped. Claude readings also follow what Nodex already knows: whenever it lists its Agents, and when Agent settings change, a Claude reply ends or Agent execution becomes available. A failed read, including one where Claude Code answered without the account's windows, keeps the previous reading and marks it as not refreshed; it never hides the meter as an account without limits. A Claude card adds `Sign out`, which signs Claude Code out of that account for every Claude profile the meter covers, as `claude auth logout` would, including outside Nodex; a profile still signed in through its environment, such as an API key or token, says so. ## Scene And Surface Semantics

Each user submission captures its submitting Workbench presentation before asynchronous
submission work begins. Main stamps the Window Session and renderer generation;
the originating Scene, revision, focused target, and selected surface identities
stay attached to that exact submission when another window owns the Conversation. Fresh Session and side-chat
launches retain the same origin through materialization. Queued follow-ups retain
their enqueue origin; editing a queued message replaces it with the editing
submission's origin. Interrupted steering retains its origin if the message later
starts a Turn, and accepted steering replaces the context for subsequent tool calls in that Turn. Already issued observations retain their original evidence. Rejected submissions do not replace accepted context.
Only selected surfaces in visible panels contribute submission context. Context contains bounded resource metadata, never full editor state, favicon payloads, or image collections. Budget limits yield explicit partial coverage; missing or malformed supplemental context yields explicit unavailability without blocking an otherwise authorized message. Sender, target, and explicit attachment validation remain mandatory.
These anchors are transient: cold reopen, autonomous work, and native notification
replies have no inferred presentation. Navigation after submission never retargets
an anchor to the currently selected window or Scene.

Application tools observe the submitting Scene by default. Explicit refresh reads
the submitting window's current Scene; an exact discovered Scene reference may
select another target. Without a submission anchor, discovery returns candidates
and requires an explicit target, even when only one window is available. Missing
renderer replies never establish a unique window. Observations expire after one
minute and are bound to the exact Turn, Profile, backend generation, and renderer
revision. Tab and group continuations retain their original observation and
filters; changed presentations require a new observation.

Tab descriptions verify Page, View, and Canvas identities and titles in Core
before returning them. Tabs expose observation-scoped handles and
presentation state. A submitted target that has since closed or changed retains
its original content identity but has no actionable tab handle. Title or favicon changes alone do not invalidate the resource target. Group
results contain bounded summaries; their tabs use the separate filtered tab list.

Application tab controls use those observation-scoped handles and the same Scene
command executor as pointer and keyboard actions. Commands validate the observed
presentation revision before applying an atomic layout change. Exact retries keep
the original operation ID and revision, returning the retained receipt rather than
applying a second change. Closing saves content and releases view attachments;
opening accepts semantic targets and creates internal runtime identities in Nodex.
Protected primaries and each Scene's permitted surface kinds remain enforced.
Successful changes require a new observation before subsequent commands.

`set_panel_state` accepts optional `side: "left" | "right"` only for a Session's
`right` panel. Bottom panels and Project, Inbox, and Library Scenes reject side
changes with `invalid_placement`. Panel observations expose the saved side when
one is set. `size.fullWidth` and `collapsed` are independent Session presentation
choices:

| `size.fullWidth` | `collapsed` | Session presentation                                 |
| ---------------- | ----------- | ---------------------------------------------------- |
| `false`          | `false`     | Split view with Conversation and content             |
| `false`          | `true`      | Chat only, with content tabs hidden                  |
| `true`           | `false`     | Full view with a content tab selected                |
| `true`           | `true`      | Full view with Chat selected and content tabs listed |

Collapsing the panel preserves `size.fullWidth`. Closing its final content tab
keeps full view with Chat selected when full view is active. A command that hides
tabs and exits full view sends `collapsed: true` and `size.fullWidth: false`.
Physical side is normalized away from bottom panels and non-Session Scenes, just
as panel dimensions that do not apply are discarded. Project, Inbox, and Library
content stacks remain fixed open and full width.

Skill tabs open beside a chat and can also live in Project, Library, and Inbox Scenes.
Reopening the same skill on the same host focuses its existing tab in that Scene.
Renaming it from the skill page keeps its tab and updates the title. Restored tabs
look up the skill in its inventory and show when the skill has moved or disappeared.
Closing a tab saves pending edits, and Skill tabs support the floating composer.
Application tools describe them with the skill name and file path.

Page content reads wait for the exact mounted editor to synchronize before reading
canonical content. Closing, replacing, or reloading that editor during preparation
invalidates the read; a different occurrence cannot complete its preparation.
Page edits retain the returned body validator and preserve Block identities.

Database View content reads distinguish the loaded, viewport, and selected
occurrences and report their coverage. They preserve the surface's effective
shared rules, personal overrides, search, and display state. A complete effective
query runs those captured rules in a new Core snapshot, independently of the
renderer's bounded window. It either returns the requested bounded result or fails
its budget; it does not silently truncate or provide a resumable SQL snapshot.
See [Agent CLI Queries](agent-cli-queries.md) for query and authorization semantics.

The global header shows `Content issues` only while an edit needs attention:
an unconfirmed action, a failed Undo or Redo, actionable Page/Canvas save
trouble, or retained drafts. Its absence makes no all-content-saved claim.
Routine saving stays beside the affected content; a successful edit that cannot
be undone is only a native Undo limitation and does not raise an alert.

The manually opened popover identifies each problem by its original
Library/Project and available Page, View, or Canvas location. Navigation and
recovery preserve that routing context. Separate actions in one scope remain
separate; the same retained draft observed through multiple surfaces appears
once, preferring the live document's recovery controls. Retained drafts stay
separate from the current document's save state and open the shared recovery
review. The header neither follows focus nor replaces Page version history.

Each problem leads with its failure or unconfirmed-result title, followed by
the explanation. Recovery actions have visible button surfaces at rest: the
primary action is filled and alternatives are outlined. The original content
location is one outlined Library/Project path with a navigation arrow; static
context stays plain. An in-progress action stays visible and disabled with a
loading indicator while its owner confirms the result.

`Check again` confirms the exact submitted action. `Retry undo` and `Retry redo`
retry the corresponding failed replay. `Clear undo history` lives in the
secondary actions menu, which names the affected Project or Library, and
requires a root-hosted confirmation describing the affected shared Page and
Database timeline. It changes no content and does not abandon submitted
requests. The confirmation rechecks the history revision, so later edits make
it stale; ordinary submission cannot offer it.

Its config stores `terminalSessionId` plus an explicit Project or Session context. Project context starts from the Project root without inventing a Session. Session context uses the execution folder or Project root. A projectless Session uses its Chat folder, which can be prepared before the first send. Main grants one interactive Window Session lease per PTY; explicit takeover moves the lease, local surface close releases it without killing the process, and explicit kill/backend exit destroys the PTY.
  - Environment: a Terminal describes itself. What describes the process that launched Nodex does not cross into the shell: color policy such as `NO_COLOR`, the launching terminal's identity and size, multiplexer membership, pager overrides, an Agent run's identifiers, and another host's Desktop Tool bindings. Starting Nodex from an Agent or another terminal therefore cannot change how programs render. On macOS and Linux the account shell starts with the login environment and the worktree's saved environment already applied, then runs its own startup files, so anything the user configures there, including `NO_COLOR`, still wins.
  - Output: PTY output reaches xterm byte for byte, complete and in order. Under load the PTY pauses rather than dropping or truncating output. Only the replay tail is bounded, to 16,000 UTF-16 units.
  - Reopening: closing or switching away from a Terminal disposes its xterm view, and reopening rebuilds the display from the replay tail and shows its end. Replay does not answer terminal queries a second time. A full-screen program returns to the alternate screen and redraws at its current size, even when the size did not change. A clear survives reopening while the tail is unchanged.
  - Keyboard focus: asking for a Terminal puts the cursor in it. Opening the bottom panel onto a Terminal, the Terminal shortcut or command, choosing a Terminal tab, and creating a Terminal all focus its input as soon as it mounts, so the first keystroke reaches the shell. Cycling a panel tab focuses its tab control. Restoring a layout, switching Scenes and Agent commands do not enter the Terminal, and a pointer press while the Terminal is still mounting cancels its focus request. Hiding a panel that holds the cursor returns it to the editor it came from, or otherwise to the Scene's composer; a cursor already outside that panel stays put. A shell that exits hands its cursor to the Terminal selected next, the selected tab in the same group, or the Scene’s primary landing.
  - Tab title: the title a program sets names the tab, unless it only repeats the working directory; a fixed title from a run action takes precedence, and the working directory's name is the fallback.
- `browser`: stores optional URL, title, favicon, and device-toolbar restore metadata and renders the Browser feature. Browser surfaces are not Scene singletons; users can create blank tabs to the right, reload, and duplicate existing Browser tabs from the tab context menu. Session re-home is independent of Scene descriptors; targets re-resolve under the new domain scope.
- Browser Profile settings are not Window Session layout. History, downloads,
  site information, password/contact summaries, import capabilities, extension
  capability, local-server preferences, and Browser Use policy are Profile-level
  providers. Import reads supported external profiles through the native helper,
  writes selected cookies into the shared Browser session, and writes passwords
  only into the encrypted Main-owned vault. Unavailable native capabilities
  render an explicit unavailable state rather than a failing action. **Clear site
  data** in Site information applies to the displayed site’s HTTP(S) origin.
  **Clear site data** in Browser options applies to the shared Browser profile.
  Browser options and Downloads both show **Clear download history**.
- File identity: a file surface uses `file:<host>:<canonical absolute path>` across preview, pinning, movement, restore, and window cloning. Canonicalization is lexical and preserves filesystem case; host authorization remains separate. Reopening a file focuses its existing Scene occurrence across groups. Empty Files explorers distinguish Host, Project, workspace root, and working directory. Resource identity excludes panel placement and mutable display state. Chat Markdown file links decode URI-encoded path segments once before opening the file, independently of line fragments.
- Preview tabs: Files and Browser can open as renderer-local previews in either right or bottom panel; panel actions open both as durable tabs. Board/List DB-view Page clicks open `page_stage` as a right-panel renderer-local preview in the nearest right-side group, creating a right-side group first when the right panel is full-width with only the DB group. Image editing opens a right-panel-only renderer-local `image_editor` preview. Each panel leaf has at most one italic preview, so opening another image or ordinary preview in that leaf replaces the previous unpinned preview. Persistable previews remain omitted from the Scene until the user interacts with the body, chooses `Pin tab`, or double-clicks the label. Pinning an image first resolves bounded stable asset locators, then replaces the ephemeral descriptor with one durable `image_editor` surface at the same tab/leaf identity; failure leaves the preview intact. Pinned images follow ordinary reorder, move, split, close, clone, and restore semantics. Files, Browser, and Page Stage previews preserve surface identity when pinned; distinct Browser runtimes have distinct identities. Each ordinary preview has an independent lifetime token, so an asynchronous save or pin cannot clear a replacement preview, including a reopened instance of the same file. Persistence or save failure leaves the preview available for retry. The selected body follows the normal fresh-view lifecycle. Close/delete, image download, and local Open controls are preview-safe and act without first pinning. Image editor behavior is owned by [User Attachment Image Editor Behavior](./user-attachment-image-editor-behavior.md).
- `agents` (Aerial view): one closable, durable tab per Library Inbox, Project, or Session Scene. Space does not offer the tab. The Inbox and Project Scenes place it in their content stack. In a Session Scene it opens in the content panel and expands it if collapsed. The bottom panel also offers Aerial view in its new-tab actions. The Inbox button, command palette, and eligible new-tab actions all focus an existing Aerial view tab in its group and preserve its scope. A new Aerial view tab starts with the Scene's Project, or every Project and projectless chat in the Library Inbox and in a projectless Session. Opening a same-Project chat selects it in the Project Agent Dock when the Dock is available. Other chats open through normal chat navigation. Opening a subagent reveals it beside its root chat.
- [GitHub](github-tabs-behavior.md) tabs show one issue or pull request in a Session, Project, Library Inbox, or Space Scene. The thread's host, repository, and number identify the tab, so opening the same thread again focuses its existing group. The tab remembers its title and selected view. A link to a view or comment reveals that destination when opened. Tabs offer **Open on GitHub** and **Copy link**.
- Side chat tabs: a side chat of an Agent Runtime chat is a durable `side_chat` surface in its source Session's Scene whose config names the side chat's own Session. It is ordered, moved, split, closed, and restored after restart like any durable tab. The tab appears as soon as the side chat is requested and shows its creation until the Session exists: a loading body, then the side chat, or the concrete failure with Retry, which repeats the same request and context capture. Opening a side chat that already has a tab selects that tab; one whose tab was closed reopens in the right panel. A tab whose side chat was deleted shows `Side chat unavailable` with `Close tab`. Default titles are `Side chat`, then `Side chat 2`, `Side chat 3`, and so on, counted among the Scene's open side chats, until the first request names the side chat. Side chats are never pinned or listed as ordinary chats.
- Remote side chat tabs: a side chat of an explicitly attached remote conversation remains a temporary renderer-local tab. It starts as a loading tab (`sidechat-loading:<parentThreadId>:<index>`) in the requested panel. Main resolves the parent before starting the fork and does not hold the parent's non-reentrant causal command lane: creating the child reads but does not mutate its parent. Main then creates and hydrates an app-server `thread/fork` with `ephemeral: true` and `excludeTurns: true`; the invoking renderer attaches through the same owner/checkpoint lifecycle as an ordinary Thread before the tab becomes a closable ready tab (`sidechat:<threadId>`) at the same place. A rejected or timed-out fork/attachment settles as a closable failed tab with the concrete error and Retry action; it never remains a false loading tab or silently disappears. Once ready it moves like any other conversation tab, but it is never persisted or restored after app restart.
- Ready side-chat tabs render the local conversation body and composer without the normal thread-stage title header; the side-chat tab itself is the only top title row.
- Side-chat start input contains only parent conversation identity and optional prompt/settings. Main derives execution context from the parent detail. Project-backed parent navigation remains `project:<id>/session:<id>/thread:<id>`; projectless navigation is `session:<id>/thread:<id>` and never fabricates `project:null`.
- Session-Thread links are the durable local ownership path for Codex Threads. Pages may open as Scene surfaces or mention Threads, but they do not own Codex Threads. A distinct Workspace-owned Linked chat edge can associate a Page with a durable Project Session without changing either owner, changing Page ownership, or depending on a Scene or attached Thread.
- Page Stage exposes a bounded, compact `Linked chats` Property keyed by Project Session identity, including threadless Chats, Chat title, execution state, independent unread state, quiet current-Chat presentation, retry/load-more, and explicit relation removal. Linked Chats use the same wrapping chip grammar as other multi-value Page Properties; activity appears inside each chip, and the trailing value-lane `+` offers `Link to chat`, plus `New chat` when the Page opens in a Project's presentation, since a new Chat needs a Project. Space Pages show the same Property. `Link to chat` lists the Chat whose Scene shows the Page first, labeled `This chat` in place of its Project, then the remaining unlinked Chats in catalog order; a search keeps that order among its matches. When every chat is already linked or the catalog is empty, the menu says `No chats available`. The Property does not expose Thread execution target, CWD, preview, or same-Project metadata. Selecting a chip navigates to that Session. With no relation, Linked chats starts behind the shared `N more properties` disclosure; expanding it reveals the shared `Empty` add/link entry point. A linked Session or actionable error promotes the row, and once shown it stays stable for the mounted Page session even if its last relation is removed. `New chat` uses the same atomic Session-plus-initial-Page operation as Board/List, while linking to a Chat does not send or start a Turn. Removing a relation does not close a Scene or delete, archive, read, or detach the Page, Session, or Thread.
- Project Agent Dock: the single context rail begins with a Project-scoped chat picker whose first option is always `New chat`; it reuses bounded sidebar Session ordering, exposes explicit load-more/retry states, and exact-hydrates the selected Session. Selection changes neither Workbench location nor Browser ownership. The unbound Dock draft stays Window-local until first send, then coalesces through the same Core default-draft ensure used by ordinary New Chat and binds only after Thread start succeeds. Existing targets share the canonical conversation/footer state with their full chat page, and the floating composer expands into the whole chat. Selector rows and the trigger never render status words: a fixed leading slot shows the shared spinner for running, the shared accent dot for unread or attention, and a neutral dot for idle/read. `Open chat` is the only target-row navigation action.
- The unbound `New chat` target has a Window Session Scene-local draft identity and creates no Core row until first send. Duplicate sends coalesce through one default-draft ensure and one Thread start. Ensure or Thread-start failure preserves the unbound draft and its content for retry; only a successful start binds the Dock to the Session, after which the next explicit `New chat` receives a fresh draft identity.
- A worktree start is recovered from the Main-synchronized pending-worktree collection by the bound `projectSessionId`, never from Dock-local memory. Until the exact pending entry resolves to a real Thread, its client identity remains in the same Thread/Composer scope, the target row shows compact setup progress or failure attention, and both composer availability and the action boundary prevent a second start. `View setup details` explicitly opens the existing recovery route; reload, retry, continue, work-locally, and cancellation follow [Codex Worktree Creation Behavior](codex-worktree-creation-behavior.md).
- Dock target and visibility are persisted Scene presentation but are excluded from Back/Forward history. If exact hydration proves that a bound Session was archived, deleted, or moved to another Project, sending is disabled and the Dock returns safely to its retained new-chat draft. A bounded summary window that does not contain the binding is never sufficient evidence.

Plugin apps opened from the rail are routes over the current Scene. A chat app is a
durable surface bound to that chat. A file viewer is a durable surface bound to the
selected workspace file. Restoring an unreachable app keeps its tab or route so the
person can retry or open Customize.

### Link opening

The Desktop Profile owns separate web and local URL destinations plus the
external-browser click shortcut. The shared link decision consumes their
effective values; the Workbench link owner executes Browser presentation in the
Scene captured when activation begins, while Main validates and opens external
URLs. The trusted app-shell popup and main-frame navigation fallback uses the
same decision. Browser pages retain their own navigation and popup policy.

Ordinary web URLs default to the system browser. Local development URLs and
local file URLs default to Nodex. Explicit external destinations and
`useExternalBrowser` take precedence. An exact external shortcut takes
precedence over tab disposition; otherwise a new-tab or background-tab request
selects Nodex. Internal destinations require a Project or Session Scene that can
host a Browser surface, independently of Agent Browser Use permission. Settings
and other temporary routes use their return Scene. Library and Library Inbox
open ordinary web links externally.

A plain primary activation on a GitHub issue or pull request link opens a
[GitHub tab](github-tabs-behavior.md) in the captured Scene when the window
shows the personal Space, a GitHub Source is configured for the link's host,
and **Open issues and pull requests in Nodex** is enabled. This applies in
Session, Project, Library Inbox, and Space. Explicit web destinations,
new-tab requests, and modified activations follow the web-link rules below.

- Plain activation follows the effective destination. Eligible Markdown links
  can request split view beside the chat.
- Primary activation (⌘ on macOS, Ctrl elsewhere) requests a background tab;
  Primary+Shift requests a foreground tab. With the default shortcut, Primary
  HTTP(S) activation opens externally instead. Both Ctrl and Meta together never
  match the external shortcut.
- Middle activation requests a background tab, or a foreground tab with Shift,
  and never matches the external shortcut. Shift alone follows the destination.
- Alt alone saves an HTTP(S) link unless Alt is assigned to external opening.
  Eligible Markdown Primary+Alt activation explicitly opens Nodex in full view.

Default Browser presentation activates a tab whose committed or pending URL
matches, preferring the Agent-active match and otherwise the last match. If none
matches, it creates a foreground tab. Explicit new-tab dispositions always
create another tab. New tabs open in the right panel; background tabs reveal it
without changing its current selection. An empty panel may select its first tab.
Split and full-width intents control the Browser panel's presentation, and
new-window intent uses a detached Browser window.

App-shell native popups are denied. Trusted HTTP(S) popups follow the same link-opening rules.
Electron background-tab disposition becomes a background Browser-tab request,
while other dispositions use default presentation. Permitted non-HTTP schemes
open externally. External URL validation applies regardless of entry point.

### Nodex references

A reference to a Page, Database View or chat (`nodex://pages|views|sessions/ID`)
renders the same way wherever it is read: a chat's messages and the Agent's
replies, tool activity, thoughts and plans, Inbox bubbles, and Pages. A mention,
or a link whose text is its URL or its target's name, shows the target's current
title and icon; a link in its author's own words keeps them. Hovering shows the target: a Page's title,
state and opening lines, a chat's Project, state and latest reply. A deleted,
missing or archived target says so and does not open. Right-click offers Open,
Open in new tab (Pages and Views), Open in new window (Pages and chats) and Copy
link; Pages keep their own editor menu.

Every reference opens through one Workbench router, with the same gestures as
web links. Plain activation follows the surface it is read in:

- In a chat, a Page or View opens as a tab in the chat's content panel, reused
  when it is already open there. From the Project Agent Dock it opens as a
  preview in the Project's active group, and double-click keeps it.
- In an Inbox, it opens as a preview in the group to the Inbox's right, as the
  Inbox's own Pages do.
- In a Page, it opens in the Page's own tab group, as before.
- A chat goes to that chat, and Back returns. A side chat of the chat being read
  reopens its tab instead, and the Agent Dock selects a chat of its Project. A
  reference to the chat being read does nothing.

Primary (⌘ on macOS, Ctrl elsewhere) or middle activation opens a Page or View
as a background tab and Primary+Shift as a foreground tab; Primary+Alt opens it
in Space. A chat is a Scene and never a tab, so Primary or middle activation
opens it in a new window. A link naming another Space opens in a window of that
Space. Outside the Workbench a reference is shown but not offered to open.

### Web links

A web link in read text (a chat's messages and the Agent's replies, tool activity,
thoughts and plans, Inbox bubbles, and Pages, editable or not) shows where it goes
before its words:

- Sites Nodex draws itself (GitHub, Linear, Figma, Notion, Slack, Gmail, Google
  Calendar and Drive, Salesforce) show their mark. Nothing leaves the device.
- Other public sites show their favicon. Nodex asks Google's icon service for it,
  from the app rather than the page, sending only the site's domain, and keeps it on
  this device, about a month when found and a day when not. **Website icons for
  links** in Settings → General turns this off, and on, at once everywhere; while
  it is off such sites show a globe. A see-through favicon drawn in the
  background's own tone, such as a black mark in dark mode, sits on a small plate of
  the other tone.
- This device and private networks (`localhost`, `*.local` and similar names,
  single-label hosts, private, shared and link-local addresses) show a globe. Their
  names never leave the device.

A globe holds the place while an icon loads, so text never shifts. A link written in
its author's own words shows its address on hover; a link written as its own URL
needs no hover. The icon belongs to the link: it is not selected or copied, and a
copied link keeps its address.

A link to a GitHub issue or pull request reads as the thread. Its state glyph takes
the GitHub mark's place once known: an open, draft, merged or closed pull request, an
open, completed or not-planned issue. Written as its own URL it shows the thread's
number and live title, as a mention does; written in its author's words it keeps
them. Hovering shows `owner/repo#N`, the state and the title. Titles and states are
read in batches, only for links on or near the screen, with the account connected in
Settings → GitHub, and shared with [GitHub tabs](github-tabs-behavior.md). Without a
connection, in a team Space, or for a thread GitHub does not show, the link keeps the
GitHub mark and reads `owner/repo#N`. It opens as any GitHub link does.

### Links inside a Browser page

A link in a Browser page behaves as it does in a desktop browser, with tabs in
place of windows. Nodex never opens a separate window for a page.

- A plain link navigates its own tab.
- A link or script that asks for a new tab or window opens a Browser tab directly
  after the tab that asked, in the same group, and selects it. Primary-click (⌘ on
  macOS, Ctrl elsewhere) and middle-click open that tab in the background and keep
  the current selection.
- The tab opens in the Scene that owns the asking page even when that page is not
  showing: a background tab, a hidden panel, another Project or chat in the same
  window, or a page an Agent is driving.
- The new tab loads the address alone. The asking page gets no handle to it, so a
  page that waits to script its popup, or a sign-in window that reports back to its
  opener, does not complete; a request for an empty window opens nothing.
- Mail, phone, message and VS Code links open their app after the site's
  external-app permission allows it, and leave no tab behind.
- `chrome://downloads` and `chrome://history` open the Browser's downloads and
  history.
- A tab opened for an address that turns out to be a download closes when the
  download completes, in Project and chat Scenes alike. It stays if the download
  fails or is cancelled, and a tab that has already shown a page is never closed by
  a download.
- While an Agent controls a page, these requests follow its
  [navigation restriction](../SECURITY.md).

### Browser shortcuts

A focused Browser page gives New Chat, New Window, Focus Address, New Tab and
Close Tab to Nodex. Address and tab actions use the Browser that has focus.
The page gets first refusal on the command palette, Page search, Workbench Find
and its match navigation, and chat navigation. Nodex defers to page handlers
in the top-level document and same-origin frames. Configured shortcuts apply
to the focused page. Text editing and Back/Forward stay with the Browser page.

### Browser annotations

Annotate selects an element, text, or region and opens a comment editor beside it,
or below or above it when neither side has room. Entered from the toolbar, the
shortcut, or the page menu's Annotate, Enter saves the annotation and
Cmd/Ctrl+Enter sends it as its own chat message. Entered from the page menu's
Quick annotate, which starts at the clicked target, the two are swapped. The
editor shows both actions and their shortcuts. Shift+Enter adds a line. Escape
cancels an editor or gesture first, then leaves annotation mode when neither is
open. Escape and hold-Space apply when focus is in that Browser or its annotation
editor. Focused menus, dialogs and Find handle Escape first. Hold Space to
temporarily interact with the page while annotating. Region selection follows
the held primary pointer. Returning to the page after releasing outside it,
losing focus, or leaving the page cancels the region.

Saved notes have numbered pins and chat composer attachments. The Annotate
control shows the saved count. A pin reopens its note for editing or removal.
Leaving annotation mode, switching tabs or Scenes, and reopening the Browser
panel retain saved notes. Pins follow their targets and appear only on their
original page; a toolbar control hides or shows them. Discard asks for confirmation.
Closing the Browser tab removes its annotations.

Notes are saved before screenshots are captured. Capture failure retains the note
and its chip says `No screenshot`. Direct sends wait for capture to settle and use
the chat's ordinary admission path, including steering or queueing a running Agent.
The person's composer text and attachments stay intact. Quick notes do not leave
pins after a successful send, and quick mode ends. If admission is unavailable or
refused, the note becomes a saved annotation and Nodex explains what happened.
The toolbar can send all saved annotations in one message. Admission consumes only
the included set; notes created during that send remain pending.

A Session Browser delivers to that chat, including before its first message. A
Project Browser targets its Agent Dock's selected chat or existing new-chat draft.
If no destination exists, Annotate explains that a chat or Agent Dock is needed.
A direct handoff without an available composer falls back to saved notes.
Removing a composer attachment removes its saved note and pin. Ordinary chat sends
include their saved annotations as text with any available screenshots.

Cmd/Ctrl+Shift+. toggles annotation mode and can be rebound in keyboard shortcuts.
Holding Space over the page temporarily restores ordinary page interaction;
releasing it resumes annotation. An Agent controlling the page temporarily disables
annotation interaction and the control explains why. The requested mode and draft
resume when control ends.

Element and text targets retain their selectors, open shadow-host chain, and
same-origin frame path. Text selections retain UTF-16 offsets, direction, and a
text quote used to refuse a changed target. Scroll-container positions and fixed
positioning keep regions aligned as the page scrolls. The Agent receives the frame,
selector/path, role/name, nearby text, and selected text with the comment.
Cross-origin frames and closed shadow roots remain opaque.

### Page dialogs

A page's `alert()` and `confirm()` appear inside its own tab, over the page, titled
with the site that asked (`example.com says`) and, for an embedded frame from
another site, the page it is embedded in. Nodex never shows them as a system dialog.

- The page is stopped until its dialog is answered. The rest of the app stays
  usable, including other tabs.
- `OK` answers either kind and `Cancel` declines a confirmation. Return chooses
  `OK` and Escape chooses `Cancel`; an alert has only `OK`.
- The dialog takes the keyboard only from its own page. It never moves focus out
  of a chat or another surface the person is working in.
- A dialog in a tab that is not showing waits there until the tab is shown. Its tab
  carries a dot on its icon for as long as the page waits on the person, for a dialog
  or a permission request alike.
- From a page's second dialog on, `Don’t let this page open more dialogs` lets the
  person stop it; later dialogs from that site are declined without appearing until
  the tab loads another page.
- Going to another address, reloading, going back or forward, stopping, or closing
  the tab declines the waiting dialog first.
- An Agent controlling the page answers the dialog with its own Browser tools. The
  person sees the same dialog when the tab is showing; whichever answer comes first
  applies and the dialog closes for both.
- When a page asks to confirm leaving it with unsaved changes, the tab the person
  is looking at asks `Leave site?` with `Leave` and `Stay`. A page an Agent controls
  leaves without asking, and a page nobody is looking at stays.
- `prompt()` is not available to pages.

## Storage Ownership

- SQLite owns shared Project Session domain data:
  - `project_sessions`: nullable Project id, `no_thread_fallback_title`, order, and pin/archive/unread state.
  - `project_session_threads`: optional Session-to-Thread attachments; canonical Thread metadata lives in `codex_threads`.
  - `project_session_pages`: non-owning, non-authorizing Page–Session Linked chat edges; Page access, Session ownership, optional Thread state, and presentation remain in their existing authorities.
  - Session lists return a derived `displayTitle`; attached Sessions prefer `codex_threads.thread_name`/preview and only fall back to `no_thread_fallback_title`.
  - Session rename commits its title through Core before updating a live conversation or backend. Attached Codex conversations synchronize the current committed title without another durable title mutation; a rejected rename has no conversation-side effects.
  - Session commands serialize per Session through commit and backend synchronization. Archive and restore commit Core state first, then reconcile only the attached Thread identified by that receipt. Backend or descendant cleanup uses the host lifecycle owner. A synchronization failure retains the committed operation identity for retry and does not imply that the Session change was rolled back.
- Core Workspace owns the atomic default-draft role and its Project/projectless uniqueness and graduation rules; renderer callers receive only the ensured Session. Main's revisioned Window Session catalog persists the canonical layout: the selected Workbench location, the previous stable Home location, Project-keyed Database search, and strict `WorkbenchSceneSnapshot` values keyed by canonical owner key. Project, Inbox, and Session Scenes own semantic primaries; the singleton Library Scene deliberately owns none. Every Scene owns right/bottom panel trees, stable sizes, selected leaves/surfaces, MRU, collapse/full-width, and persisted descriptors; Project Scenes additionally own Agent Dock target/draft state. Writes use ownership validation, compare-and-swap `layoutRevision`, bounded codecs, atomic replacement, and fsync.
- An Aerial view tab saves its selected Project scope in its Scene descriptor. Live Agent work stays with the Agent Runtime, and the tab body follows it only while selected in a showing group in a visible window.
- Clone retains canonical file resource identities and remints other surface/tree/Browser identities plus the unbound Project draft identity, while retaining bindings to real Sessions, image asset locators, and Composer visibility. Malformed owner/primary, Pages Library identity, Agent Dock, image locator, or kind/config combinations fail closed.
- Profile preferences are separate from Window Session layout. Per-Project view presentation, DB view preferences, sidebar collapse/width/disclosure, and bounded recent Pages persist through the focused profile-preference Adapter; they do not add another active Scene or server-data owner.
- App-window Back/Forward history and previews remain renderer-local because they are live interaction state, not cold-restore authority.
- Renderer server-state cache owns exact Project/Session detail, bounded summary windows, and bounded Page Chat projections. Sidebar rows come from Project/projectless windows, but an active restored Project or Session owner is hydrated by exact identity and never inferred missing from a bounded list. Mutations that return a full Session seed its detail cache. Board/List activity is a batched join with visible Page IDs rather than per-row hydration or Database state. Full Project Session list reads are reserved for slow domain paths and never carry Scene layout.
- Renderer presentation mounts exactly one selected owner Scene and one selected body per panel leaf. Switching disposes the previous React view; scoped renderer state restores explicit presentation, while Query and the Codex/Browser/Terminal/Document Modules preserve their own data and runtime continuity. The existing Session renderer receives a leaf compatibility projection from Scene, but there is no second writable `sessionViewsBySessionId` store.
- Renderer-local side chat state owns only what a durable side chat tab shows before its Session exists: the creation request, its status and failure, and the draft or opening message it hands to the side chat once. Runtime side chats are Sessions attached to their source, with its captured context, Agent settings and working directory. They never execute before a new submission, show only their own messages, and persist until they or their source are deleted; their tab placement is ordinary Scene state. Context capture, provider behavior and lifetime follow [Agent Runtime behavior](agent-runtime-behavior.md). Remote side chats retain their own temporary-thread lifecycle.
- Core schema v90 removes historical `project_session_tabs`, `panel_state_json`, and `left_pane_collapsed`. It preserves Session/Thread/Project/content data and extracts at most one valid Database View target into `initial_database_view_id`; the old shared arrangement is intentionally discarded because no Window Session owner can be inferred. Historical schema v93 replaces that pointer with `database_starter`, and historical schema v99 removes the field after v98's Yjs-integrity migration: it deletes only unthreaded marked starter Sessions and preserves threaded marked rows as ordinary Sessions. Fresh Project creation creates no Session.
- Old stage-rail/window layout snapshots are best-effort migration inputs only; after decode, owner-scoped Scene state is authoritative for presentation and Core never owns it.

## Navigation

- Home restores the window's last stable Project, Session, Inbox, or empty location; leaving Automations through Home returns there rather than reopening Automations, even after Automations presented a run or Heartbeat chat. Space restores its existing Library Scene, including tabs, splits, and selection; the Inbox likewise restores its Inbox Scene. Switching destinations enters the same app-window navigation history as other Workbench navigation. Cold reopen retains both the selected destination and the previous Home location; removing its Project or Session repairs the checkpoint and history through the normal missing-owner transition.
- Scene switching synchronously unmounts the previous owner route and mounts the selected owner's Scene composition: a Session primary plus its panel groups, a Project's root-bearing full-width surface stack plus bottom panel and Agent Dock, or the primary-free Pages full-width stack. Exactly one owner route and one route header exist. Project selection never selects a first Session, and sidebar disclosure never changes location.
- Scene switching reuses exact cached Project/Session detail and authoritative Module state without calling the full Project Session list solely because the owner changed. Returning to an owner or panel surface creates a fresh React view and restores only explicitly owned presentation such as Composer drafts, transcript state, and registered viewport snapshots; ephemeral component-local state resets. ## Keyboard Model

- Existing global command palette, settings, and editor shortcuts remain in force. Undo/redo is local to the focused editable surface; the shell owns no Project-wide history stack.
- Native Zoom and Undo/Redo target the frame that currently owns input focus. Hidden retained pages and standby interactive responses cannot take those commands from Workbench; a focused embedded page keeps its own commands.
- The previous stage-order shortcuts (`View -> Card -> Thread -> Diff`) are retired as primary shell semantics.
- Project/Session/surface keyboard shortcuts follow the hierarchy: Project disclosure control, Project navigation control, Session row, owner primary, and right/bottom panel groups.
- `Cmd/Ctrl+J` executes the shell-global `toggleBottomPanel` command and shows or hides the selected Scene's bottom panel. Toolbar, command palette, Browser-runtime keyboard handling, and desktop application menu share the same shell executor; Electron owns the desktop accelerator so one keypress cannot toggle twice. It works from editable and desktop Browser surfaces, preserves explicit user unassignment, and safely no-ops only when no Scene is active.
- `Ctrl+\`` focuses an existing eligible Terminal surface or creates one in the selected Scene's bottom panel. `Alt+Cmd/Ctrl+S` starts Side chat only in an eligible Session Scene. The global terminal drawer is not part of the Scene model.
- `Cmd/Ctrl+Shift+[` and `Cmd/Ctrl+Shift+]` cycle the previous/next tab for the focused right or bottom panel tab group in the selected Project, Session, Inbox, or Library Scene. Cycling resolves the nearest split leaf or the last focused leaf from the native menu route, wraps within that leaf, works from Page editor content in that leaf, no-ops for zero or one tab, and does not replace plain `Cmd/Ctrl+[` / `Cmd/Ctrl+]` app-window Back/Forward.
- `Cmd/Ctrl+W` closes the active closable tab in the focused right or bottom panel tab group through the owning Session or Scene tab adapter, with the same close semantics as tab chrome. It works from Page editor content in that leaf, ignores input fields and dialogs, no-ops for non-closable tabs, and must not close the app window. Closing an inactive tab preserves the current selection. A Browser tab created or duplicated to the right records its opener in an ephemeral, generation-scoped tree. Closing an active current-generation child selects the nearest right descendant of the same opener tree, then the nearest left descendant, then its opener. Selecting an unrelated tab or moving/reordering a tracked tab invalidates that affinity. Without a valid opener result, selection stays within the same split leaf and follows physical order: the right neighbor first, then the left neighbor at the row edge. Visit recency does not override either rule. Close-button and middle-click single-tab closes use the same routing. On macOS, Close Window uses `Cmd+Shift+W`.

### Workspace Files search

Local file comparison and blame reads follow the [Files Git data contract](workspace-file-git-data.md).

File results and references open in the active Session, Project, Library, or Inbox Scene without creating a chat. Reopening a matching file focuses its existing tab and reveals the requested one-based line and UTF-16 column. Pinning or restoring a file keeps its host and path. Replacing a preview saves its edits first; failed saves retain the current preview, and a superseded opening request cannot replace it.

Files search shares the host-scoped native fuzzy-search session with Composer and Command Palette. Query, root, and runtime changes fence stale results; closing its consumer releases the session. Directory browsing retains the selected host, including home-directory expansion, and fences remote results by connection generation and capability source. Local directory browsing reads entries asynchronously and sorts in yielding batches so wide folders do not monopolize Main. Local imports and folder manifests apply their entry budgets while traversing, before sorting.

Files tabs identify each file by its host and canonical absolute path. Preview, pinning, switching groups, and reopening a saved Scene preserve that host; equal paths on different hosts are distinct files. Content samples identify text, image, PDF, audio, video, archive, or other binary content and its detected MIME type independently of the filename. Previews have a 256 MiB size ceiling. Local audio and video stream through the renderer's protected media route with byte-range seeking. Base64 reads, including remote media, default to a 128 MiB limit and can request a smaller limit; oversized reads fail before transferring the full file. Remote text, Markdown, image, PDF, audio, and video previews read bounded bytes and size from their source host. Unavailable modification metadata remains unknown. Remote previews do not create an editor, local file watcher, or local directory query, and they do not substitute Project folders or open a remote path in a local editor or Finder. File references and copy-contents actions inside a remote preview retain its host. A failed or retired host read remains an explicit read failure, without a local fallback. Saving a local file copy uses the native destination picker and copies the file directly, without a preview size limit. Repository metadata supplies the configured origin URL, or null when none is configured. On macOS, an existing local file can query its default application (the well-known viewer for its type when installed, otherwise the system default) and up to 20 other compatible applications in system order, with names and icons; Nodex itself is excluded. Opening a file uses either the system default or an explicitly selected application bundle. Other platforms return an empty application list.

The Files viewer chooses its body from the sampled content: images, PDFs, and MP4, WebM, and Ogg video and common audio open in their rich preview; Markdown and SVG toggle between rendered and source views (a file opened at a location starts in source); other text opens in the source editor or, from 10 MB, read only. Other video and audio, archives, office documents, binaries, and files above a preview limit show why they have no preview. Video plays in a player with seek, volume and mute, playback speed, picture in picture, fullscreen, and Save video as. Its header keeps floating controls on one row: the file's breadcrumb, whose ancestor folders hide first when space runs short; copy-path actions for the repo-relative, project-relative, or absolute path; Open in GitHub for a file in a GitHub checkout; and file controls (Search in files, viewer options, Open, and the file-tree toggle) that fold into one menu below 625px. Each breadcrumb segment opens a listing of its folder's contents with that segment selected (the workspace segment lists the workspace root), and choosing a file there previews it. Open uses the preferred editor for text and the default application for documents and media, and its menu lists alternate applications, the platform’s reveal action, and Save a copy. Open in GitHub appears in the menu when the header has no separate GitHub button. Viewer options group Copy file contents, preview/source and word wrap controls, and Refresh files. Viewer bodies and the file tree leave room for the floating composer.

Editable text uses the editor header instead: the breadcrumb, Show changes, and file controls (Search in files, View source or View preview for Markdown, the file-tree toggle, and Open). Show changes compares the draft with a Git source and keeps that source for the file; it chooses the first of Unstaged, Uncommitted, and Branch that changed the file. While shown, the header offers the source picker (Uncommitted, Unstaged, Staged, Committed with the branch's commits, Branch), Hide changes, a change navigator that counts change blocks and steps between them without wrapping, and a unified or split layout toggle remembered across files and windows. Live comparisons stay editable; Staged and Committed comparisons are read-only. The palette command Enable Git blame (or Disable Git blame) shows the author, subject, commit, and date of the caret's line in every Files editor; edited lines show none.

In a Git repository, the file tree splits into Changed files and All files once the folder has changes. Changed files lists the folder's changes against the remote base branch when one exists, otherwise its working-tree edits, marking added, deleted, and modified files and the folders that contain them. A filter narrows both sections without removing them. Choosing a changed file opens it showing those changes. In a Session that can show Review, All changes above the tree opens Review for the same repository and comparison. Section and folder collapse persist per host and folder for the window. Collapsing a folder keeps the expansion of the folders inside it, so they are open again when it reopens. An expanded folder shows a loading row until its entries arrive. All files reads Loading… while the folder itself loads and Refreshing… while entries already shown are read again, which happens when a folder is shown again more than five seconds after its last read. Clicking a folder selects it until another file opens. A row focused from the keyboard shows its full path in a tooltip and as its accessible description.

Embedded file images in rendered Markdown resolve beside the source document, on that document's host. Absolute file paths and responsive picture candidates use the same host-scoped reads; they never inherit the renderer's filesystem route or opaque resource capabilities. Explicit HTTP(S) and inline image data remain subject to the renderer's resource policy. File images have a 25 MB decoded preview limit, including when metadata size is unknown. Switching documents or hosts discards late results and releases retired image URLs. Refreshing a remote preview reads its current text and image bytes again.
