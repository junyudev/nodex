# Workbench Shell

## Intent

The Workbench presents each Project as a folder in the left sidebar. Expanded Projects show durable Project-owned Sessions, but a Project can have zero Sessions until the first ordinary New Chat action ensures its Core-owned default draft. Each Window Session renders an owner-scoped Scene through one shared composition: a Project Scene places the Project's current default Database View at the root of a fixed full-width surface stack, a Session Scene keeps Conversation as its primary plane, and the singleton Pages Scene presents all trusted Library content as ordinary tabs without a protected primary. A Project Agent Dock can observe and send to one real Session without changing the selected Scene. Core-backed domain data remains shared; Scene surfaces, Dock presentation, and panel arrangement do not synchronize across windows.

Detailed Auto-review preset, config, and approval-lifecycle rules are specified in [Auto-review Behavior](./auto-review-behavior.md).
Thread Summary content and row actions are specified in [Thread Summary Panel Behavior](./thread-summary-panel-behavior.md). Scheduled and Settings route behavior is specified in [Scheduled Route Behavior](./scheduled-route-behavior.md) and [Settings Route Behavior](./settings-route-behavior.md).

## Layout

- Left sidebar: Projects render as folders with separate navigation and disclosure controls. The visible Project label opens its Project Scene without changing disclosure; the leading marker becomes a chevron on row hover/focus and only folds or expands Session children.
- Project children: each expanded Project lists ordered Sessions. A new Project starts with zero Sessions and still opens its Database immediately. Its first ordinary New Chat action immediately ensures one durable default-draft Session and lists it; repeated actions select the same Session until first Thread link or Archive releases the slot.
- Sidebar Sections: users may create named custom Sections between the Pages and Projects groups from a Project or Chat context menu and place Projects and Project Sessions into one mixed ordered list. The Projects header has no duplicate create-Section action. Moving a Project changes only its list placement: the same Project row renderer, disclosure state, marker, actions, hover card, child rows, pagination, and context menu are used in Projects, Pinned, and custom Sections. A Session's direct placement overrides inherited presentation from its Project; the Session remains owned by that Project and is omitted from the Project's nested list while directly placed. Pinned and custom placement are mutually exclusive. Project and Chat rows may be dropped onto an empty, populated, expanded, or collapsed custom Section; hovering the Section header shows the first exact mixed insertion rail directly below that header, never a broad gray background, border, or trailing line around the Section. Populated Sections resolve the pointer above or below either item kind to one exact mixed insertion boundary, and a successful cross-Section drop expands the destination. Reordering within a Section uses the same mixed boundary and one atomic Core item move. A Project row's narrow top and bottom edges remain mixed-list insertion boundaries while its center and leading target accept a Chat into that Project. While an external Chat is over any whole-Project target, the outer Project group—including its header and children—shows one 2px inset information-blue ring, 10px radius, and a 10% information-blue tint; nested row/icon/gutter targets must not add separate gray hover blocks. Custom Sections and their contents support pointer and keyboard organization; `Alt+ArrowUp/Down` moves a focused Section. Collapsed state is a Profile preference, while definitions, placement, and order remain Core state. The header shows aggregate running or unread state even while collapsed and creates a durable threadless projectless Session directly in that Section. Its overflow menu contains exactly `Edit section`, `Archive all chats`, and `Delete section`; Section order is changed by direct drag or keyboard organization, not duplicate move commands in this menu. Archive all is a confirmed, set-based action over every effective Session, including inherited Project children; when it archives the selected Session, Workbench creates and selects a replacement draft in the same Section. Deleting a Section releases its visible organization without deleting its Projects, Sessions, or Threads and offers Undo.
- Sidebar footer: a compact Settings button remains available without workspace switching controls.
- Active Scene header: a Session Scene uses the active thread title row without a separate session title, project-name subtitle, or empty toolbar row. A Project Scene renders the Project marker and name at the start of the root surface tab strip; it does not add a `Home` label or a second title row. The Pages Scene renders `Pages / <root>` and appends the selected child title when the active surface is below that root; its resource tabs remain the only content-level title row. Project identity, tabs, surface actions, and the Database toolbar are all outside the Electron drag region. The fixed global header owns the left chrome (`Sidebar`, `Back`, `Forward`, and collapsed-only `New chat`) plus the top-right bottom-panel control. Session Scenes also expose the right-panel control, while Project and Pages Scenes omit it because their surface stacks are structurally full-width. Bottom-panel surface creation plus the plain `Close` X action belong to the bottom-panel tab header. There is no attach/detach thread toolbar button.
- Owner root: a Session Scene hosts its Conversation on the primary plane and shows the new-thread composer when no Thread is attached. A Project Scene places its current default Database View as the first, non-closable tab in the full-width right surface stack. It cannot be moved, split away, or sent to the bottom panel. Other Project surfaces retain normal tab and split behavior. Pages has no owner root: every Page, Database, View, and Canvas is an ordinary closable surface, and closing the final surface reveals the empty Pages chooser. Database `Ask agent` reveals and focuses the Agent Dock only in a Project Scene; it does not create a Session or a Conversation surface.
- Pinned summary: attached-thread pages show a summary button at the right edge of the thread header, immediately before the right-panel boundary. While the right panel is collapsed, the button is labelled `Toggle pinned summary` and controls the 300px pinned summary panel, which renders below the thread header and never over the top toolbar buttons. Opening the regular right panel hides the pinned overlay, makes the global header slot reserve the right-panel width, and switches the thread-header button to a separate `Toggle summary` popover trigger; that popover dismisses on outside click and does not change the saved pinned-open preference. Section content and actions follow [Thread Summary Panel Behavior](./thread-summary-panel-behavior.md).
- Right panel: a Session right panel renders Window Session-local ordered surfaces and split groups and can be collapsed, regular-width, or expanded to the full Scene content area. Newly materialized Session Scenes start collapsed. Hiding and showing that panel preserves regular/full-width mode. Project and Pages Scenes use the same panel tree and tab implementation as fixed-open, full-width surface stacks; their collapse and restore-width operations normalize to no-ops. A Project may activate the initial Welcome Page while retaining Database as the first protected tab. Pages may be empty. When the sidebar is collapsed and a surface stack is full-width, the tab header reserves the measured left titlebar rail so `Show sidebar`, Back, Forward, and compact `New chat` never overlap the tabs. The persisted layout shape supports split leaves; header start reservation applies only to the top-left group and trailing expand/restore controls apply only to eligible Session groups.
- Composer overlays: full-width Session right panels render the shared root Composer as a fixed floating bottom overlay for `review`, `browser`, `db_view`, `page_stage`, `canvas_stage`, and root-targeted `image_editor` tabs. Image editing may bind this overlay before New Chat has a Thread; a side-Composer target never projects into the root overlay. A Project Scene renders the same footer-only conversation connector as a controlled Agent Dock on every active surface, including `New chat` and blank Session targets. A body portal mirrors the full-width pane rect, follows zoom and `--app-shell-bottom-panel-height`, and scopes pointer input to the centered composer group. Both owner kinds persist manual overlay visibility in their Scene without adding Back/Forward history; switching tabs or owners, leaving full width, and restoring the window preserve it. Hiding removes the reserve while leaving chat and Main-owned runtimes active, and an accessible reveal handle restores and focuses the composer. Normal floating surfaces preserve 118px pane scroll clearance while visible. Browser owns its zero-reserve compact presentation, 384px idle/hover width, focus expansion, and transient document-bottom auto-hide; that automatic state composes with but never overwrites the persisted manual preference. Empty and fitting overlays use a 44px auto-single-line composer beneath one context rail: its leading chat selector is followed by mutable new-chat runtime context or connected latest-turn controls. The shared adaptive footer compares the prompt's measured longest unwrapped line with the compact input width left by its actual controls. Visual wrapping, explicit line breaks, attachments, errors, or dictation promote the normal Session composer shape with a full-width prompt row and the standard split control row—context and permission left, model, dictation, and submit right—while scrolling remains owned only by the capped prompt editor; side-chat, Terminal, Files placeholders, blank Session homes, and resuming Session pages stay on their existing non-overlay paths.
- Bottom panel: the bottom panel renders one tab group below the primary/right-panel row and spans the full active Scene width. It has a top-edge resize handle, defaults to 280px tall, and can be shown or hidden from the fixed global `Toggle bottom panel` button. Opening a collapsed empty bottom panel creates and selects Terminal when the active owner has an eligible Terminal workspace; reopening a non-empty panel preserves its existing tabs and selection, while owners without Terminal capability keep the empty chooser. Empty panel choosers and panel new-tab menus use owner- and panel-specific capabilities. Attached project-backed Session bottom panels order Terminal, Browser, Files, Side chat; attached projectless Session bottom panels order Side chat, Browser, Terminal. Threadless Sessions omit Side chat. Project bottom panels offer Terminal, Browser, and Files with explicit Project context and never create a Session to host them. Review remains right-panel-only at creation. Pages panels expose only the shared Library picker for Page, Database, and Canvas content.
- Browser surfaces: `browser` is a real multi-surface kind backed by the Main-owned Browser Platform. The renderer supplies navigation chrome and stable body-attached host geometry; it never imperatively navigates the guest. Every route is identified by canonical Scene owner key, owning Window Session, and Browser tab, while its opaque storage identity links the shell to atomically persisted URL/title/favicon and Chromium back/forward history. A manually opened Project Browser has no agent owner. Every Browser Use runtime tab instead carries its own exact `codexSessionId`; target selection never rewrites it. Starting an idle turn awaits capture of the owning Session presentation route, with a real Session materialized before a Project Dock draft starts and a newly created Thread promoted before its first turn. A visible Browser Use request creates or activates the Browser surface in that Session Scene before selecting the task; background and hide requests update it without navigation. Every live Browser Use tab in the Window Session receives a retained body host from the renderer-wide runtime projection regardless of which Project or Session Scene is selected; Scene-owned panel and background hosts may supersede it only for the same exact route identity. Ordinary reopen preserves identities; duplicate, new-window clone, and fork copy presentation but remint runtime/storage identities. Switching panels, Dock visibility, full-width presentation, and retained Browser Use hosting preserve the live page; explicit surface close performs generation-fenced descriptor removal, Main teardown, guest destruction, and acknowledgement. A 32-page detached budget suspends only unprotected pages and restores them from the durable snapshot when selected again.
- Browser chrome includes back/forward, reload/stop, address and connection state, find, open external, annotations, page options, the full zoom ladder, printing, image screenshots, responsive/fixed device emulation, Profile-wide data clearing, download status, and Browser settings. The app-shell Browser tab icon is live runtime chrome: it shows a double-circle throbber alone while waiting for the first response, clips an available favicon inside that throbber after response, and completes its 250 ms favicon transition before removing the throbber when loading settles. Stop, failure, blank, detached, restored, and suspended states are settled; they never retain a hidden loading animation. The resolved app reduced-motion preference keeps the same readable phases while removing throbber animation and completion transition. Waiting/loading truth remains transient Browser runtime state and is never persisted into Scene configuration. Blank tabs show bounded local-server discovery and thumbnails. DNS, offline, refused, timeout, certificate, policy, renderer-crash, and generic failures retain the tab and expose a safe recovery action. Browser tab context menus put `New tab to the right`, `Reload`, and `Duplicate` before generic close/move/split actions; page context menus add policy-checked navigation, copy/edit, image attachment, annotation, and inspect actions.
- Downloads are Profile-level durable history with progress, pause/resume/cancel, open/reveal, removal, and collision-safe save paths. An agent download requires a short-lived one-use grant for the exact route and URL chain. Annotations support element, selected-text, and region anchors, multi-selection, comments and constrained design previews, original view, discard, and bounded screenshot evidence added through the shared composer attachment model. In non-Electron runtime Browser renders an explicit desktop-only unavailable state.
- A Session right panel has a left-edge resize handle in regular mode. Full-width mode collapses the thread viewport to zero width, removes the resize handle and inner left border, hides the fixed header center surface, and exposes `Restore panel width` from the tab header. Project and Pages surface stacks have neither resize nor restore-width controls because full width is their structural layout.

## Scene And Surface Semantics

- Primary surfaces are fixed for Project and Session owners. A Project Scene's `db_view` primary resolves the Project's current default Database View, occurs exactly once at the start of its full-width right stack, and cannot be closed, moved, split, or reordered behind another tab. A Session Scene's `conversation` primary resolves that exact Session outside its panel trees. Pages has no primary; its Library-authorized surfaces all live in the panel trees and may close, move, split, and reorder.
- `db_view`: renders one durable View through shared effective-presentation and data authority. A canonical Status Board retains the established Board Column/Card presenter; List uses the dense task-row presenter; capability-specific Board configurations use the advanced fallback. A Scene can have one panel surface per explicit View target; selecting an already-open target focuses that surface, while switching Board/List preserves the View identity, Filter, selection, and Page context. The Project Scene primary uses the semantic `project-default` target so a default-View change does not rewrite presentation identity. The toolbar's adjacent `Canvas` destination opens or focuses that Project's deterministic primary `canvas_stage` in the same panel group; it does not alter Database config or personal presentation preferences.
- `canvas_stage`: renders the generic scene-native Canvas surface for `{ accessContext, canvasBlockId }`. The public Canvas Block ID is the target; the surface never persists `documentId`, scene state, or Page host coordinates. Opening the same Canvas again focuses the existing target where the owner Scene and access context match. The live Canvas target updates the surface title, resolves host-Page grants, and provides explicit missing/deleted/error states with normal close behavior. Within one renderer, inline Page Canvas and Canvas Stage share one Document session/provider/outbox only when their Core-authored `libraryId + accessContext + documentId` identity matches, while retaining independent Excalidraw bindings, camera, undo/tool state, asset resolver, and presence participant.
- `page_stage`: reuses Page Stage for `{ projectId, pageId }`. A single-click from a Board or List DB View opens or replaces a renderer-local preview; double-click, command-palette results, Thread Page links, and explicit pickers open a durable Scene surface. The selected Scene supplies placement context while config Project identity supplies authorization. Cross-Project surfaces label that context explicitly. If the DB surface's group has a sibling to the right, new Page surfaces open there; if a full-width right panel contains only the DB group, opening a Page first creates a right-side group. Page references, breadcrumbs, backlinks, Canvas references, and other content navigation invoked inside a Page Stage or Canvas Stage open in that source surface's existing tab group, even when another group is active; an already-open matching target is focused in its existing location. Only the selected body mounts. Every live Page Document session publishes its authoritative Y.Text title through one renderer-lifetime `(libraryId, pageId)` presentation overlay, so all matching Session, Project, and Pages tab handles, the Sidebar Pages row, and the Pages breadcrumb update together for local or remote edits. A durable Page surface retains that publisher with its editor session while React detaches the selected body; independent surface leases prevent one surface from clearing another. After the final session retires, the overlay retains its last observed title until canonical state either presents the same title or causally follows the exact durable Document head that acknowledged it. An unrelated head advance is never settlement proof, while a later remote title or Document-generation reset can still take over. Canonical Page and Library projections remain the committed fallback, while Window Session and Scene title snapshots are cold-start fallbacks and are not rewritten per keystroke. A transient Core deadline during the initial Document read keeps the Page in a `Core is busy` state and retries twice with short bounded backoff; a non-retryable failure stops immediately, and an exhausted transient failure exposes one explicit retry action without rendering the raw Core error. Unmounting the surface cancels the retry chain. Shell, exact Project/Page hydration, missing-target states, retained Page model, preview promotion, and close cleanup follow the shared Page Stage lifecycle.
- `terminal`: reuses the Main-owned Terminal lifecycle with a Window Session-local descriptor and defaults to the bottom panel. Its config stores `terminalSessionId` plus an explicit Project or Session context. Project context starts from the Project root without inventing a Session. Session context uses attached Thread cwd or Project root; a projectless Session requires an attached Thread with a non-empty cwd and never falls back to user home or process cwd. Main grants one interactive Window Session lease per PTY; explicit takeover moves the lease, local surface close releases it without killing the process, and explicit kill/backend exit destroys the PTY.
- `browser`: stores optional URL, title, favicon, and device-toolbar restore metadata and renders the Browser feature. Browser surfaces are not Scene singletons; users can create blank tabs to the right, reload, and duplicate existing Browser tabs from the tab context menu. Session re-home is independent of Scene descriptors; targets re-resolve under the new domain scope.
- Browser Profile settings are not Window Session layout. History, downloads,
  site information, password/contact summaries, import capabilities, extension
  capability, local-server preferences, and Browser Use policy are Profile-level
  providers. Import reads supported external profiles through the native helper,
  writes selected cookies into the shared Browser session, and writes passwords
  only into the encrypted Main-owned vault. Unavailable native capabilities
  render an explicit unavailable state rather than a failing action.
- Preview tabs: Files and Browser can open as renderer-local previews in either right or bottom panel. Board/List DB-view Page clicks open `page_stage` as a right-panel renderer-local preview in the nearest right-side group, creating a right-side group first when the right panel is full-width with only the DB group. Image editing opens a right-panel-only renderer-local `image_editor` preview. Each panel leaf has at most one italic preview, so opening another image or ordinary preview in that leaf replaces the previous unpinned preview. Persistable previews remain omitted from the Scene until the user interacts with the body, chooses `Pin tab`, or double-clicks the label. Pinning an image first resolves bounded stable asset locators, then replaces the ephemeral descriptor with one durable `image_editor` surface at the same tab/leaf identity; failure leaves the preview intact. Pinned images follow ordinary reorder, move, split, close, clone, and restore semantics. Page Stage previews keep a persisted-compatible client surface id so pinning preserves identity even though the selected body follows the normal fresh-view lifecycle. Close/delete, image download, and local Open controls are preview-safe and act without first pinning. Image editor behavior is owned by [User Attachment Image Editor Behavior](./user-attachment-image-editor-behavior.md).
- Side chat tabs: Side chat is a renderer-local Session Scene action/tab family, not a persisted `WorkbenchSurfaceDescriptor` kind. Side chat actions create renderer-local loading tabs (`sidechat-loading:<parentThreadId>:<index>`) in the requested panel. Main resolves the parent before starting the fork and does not hold the parent's non-reentrant causal command lane: creating a temporary child reads but does not mutate its parent. Main then creates and hydrates an app-server `thread/fork` with `ephemeral: true` and `excludeTurns: true`; the invoking renderer attaches through the same owner/checkpoint lifecycle as an ordinary Thread before replacing the tab with a closable ready tab (`sidechat:<threadId>`). A rejected or timed-out fork/attachment settles as a closable failed tab with the concrete error and Retry action; it never remains a false loading tab or silently disappears. Side chat titles are `Side chat`, then `Side chat 2`, `Side chat 3`, and so on for that Session Scene. They can move between the right and bottom panels in renderer memory, but they are never persisted, pinned, archived, listed as normal Project Threads, or restored after app restart.
- Ready side-chat tabs render the local conversation body and composer without the normal thread-stage title header; the side-chat tab itself is the only top title row.
- Side-chat start input contains only parent conversation identity and optional prompt/settings. Main derives execution context from the parent detail. Project-backed parent navigation remains `project:<id>/session:<id>/thread:<id>`; projectless navigation is `session:<id>/thread:<id>` and never fabricates `project:null`.
- Session-Thread links are the durable local ownership path for Codex Threads. Pages may open as Scene surfaces or mention Threads, but they do not own Codex Threads. A distinct Workspace-owned Linked chat edge can associate a Page with a durable Project Session without changing either owner, granting Page access, or depending on a Scene or attached Thread.
- Page Stage exposes a bounded, compact `Linked chats` Property keyed by Project Session identity, including threadless Chats, Chat title, execution state, independent unread state, quiet current-Chat presentation, retry/load-more, and explicit relation removal. Linked Chats use the same wrapping chip grammar as other multi-value Page Properties; activity appears inside each chip, and the trailing value-lane `+` offers `New chat` and `Link to chat…`. The Property does not expose Thread execution target, CWD, preview, or same-Project metadata. Selecting a chip navigates to that Session. With no relation, Linked chats starts behind the shared `N more properties` disclosure; expanding it reveals the shared `Empty` add/link entry point. A linked Session or actionable error promotes the row, and once shown it stays stable for the mounted Page session even if its last relation is removed. `New chat` uses the same atomic Session-plus-initial-Page operation as Board/List, while linking to a Chat does not send or start a Turn. Removing a relation does not close a Scene or delete, archive, read, or detach the Page, Session, or Thread.
- Project Agent Dock: the single context rail begins with a Project-scoped chat picker whose first option is always `New chat`; it reuses bounded sidebar Session ordering, exposes explicit load-more/retry states, and exact-hydrates the selected Session. Selection changes neither Workbench location nor Browser ownership. The unbound Dock draft stays Window-local until first send, then coalesces through the same Core default-draft ensure used by ordinary New Chat and binds only after Thread start succeeds. Existing targets share the canonical conversation/footer state with their full chat page and project the latest turn into the same rail. Selector rows and the trigger never render status words: a fixed leading slot shows the shared spinner for running, the shared blue dot for unread or attention, and a neutral dot for idle/read. `Open chat` is the only target-row navigation action.
- The unbound `New chat` target has a Window Session Scene-local draft identity and creates no Core row until first send. Duplicate sends coalesce through one default-draft ensure and one Thread start. Ensure or Thread-start failure preserves the unbound draft and its content for retry; only a successful start binds the Dock to the Session, after which the next explicit `New chat` receives a fresh draft identity.
- A worktree start is recovered from the Main-synchronized pending-worktree collection by the bound `projectSessionId`, never from Dock-local memory. Until the exact pending entry resolves to a real Thread, its client identity remains in the same Thread/Composer scope, the target row shows compact setup progress or failure attention, and both composer availability and the action boundary prevent a second start. `View setup details` explicitly opens the existing recovery route; reload, retry, continue, work-locally, and cancellation follow [Codex Worktree Creation Behavior](codex-worktree-creation-behavior.md).
- Dock target and visibility are persisted Scene presentation but are excluded from Back/Forward history. If exact hydration proves that a bound Session was archived, deleted, or moved to another Project, sending is disabled and the Dock returns safely to its retained new-chat draft. A bounded summary window that does not contain the binding is never sufficient evidence.

## Storage Ownership

- SQLite owns shared Project Session domain data:
  - `project_sessions`: nullable Project id, `no_thread_fallback_title`, order, and pin/archive/unread state.
  - `project_session_threads`: optional Session-to-Thread attachments; canonical Thread metadata lives in `codex_threads`.
  - `project_session_pages`: non-owning, non-authorizing Page–Session Linked chat edges; Page access, Session ownership, optional Thread state, and presentation remain in their existing authorities.
  - Session lists return a derived `displayTitle`; attached Sessions prefer `codex_threads.thread_name`/preview and only fall back to `no_thread_fallback_title`.
- Core Workspace owns the atomic default-draft role and its Project/projectless uniqueness and graduation rules; renderer callers receive only the ensured Session. Main's revisioned Window Session catalog persists canonical layout v7: one discriminated Project/Session/Pages/empty location, Project-keyed Database search, and strict Scene-v7 `WorkbenchSceneSnapshot` values keyed by canonical owner key. Project and Session Scenes own semantic primaries; the singleton Pages Scene deliberately owns none. Every Scene owns right/bottom panel trees, stable sizes, selected leaves/surfaces, MRU, collapse/full-width, and persisted descriptors; Project Scenes additionally own Agent Dock target/draft state. Writes use ownership validation, compare-and-swap `layoutRevision`, bounded codecs, atomic replacement, and fsync.
- Layout v1-v6 and Scene v1-v6 are decode-only. Existing Project and Session migration preserves semantic primaries, panel descriptors, trees, selection, MRU, collapse, sizes, full-width state, and Project Dock state. Layout v6 migration converts only the active per-resource Scene into the singleton Pages Scene, promotes its former primary into an ordinary panel tab, rewrites Resource locations and return locations to Pages, and drops dormant per-resource presentation owners. Compatible Library-authorized content siblings remain up to the Scene bound, with the promoted primary taking precedence; Browser, execution-only, and Project-scoped siblings are discarded. A missing active Resource Scene is materialized with deterministic bounded identities. Canonical saves emit layout v7 with Scene v7 only. Clone remints every surface/tree/Browser identity plus the unbound Project draft identity, while retaining bindings to real Sessions, image asset locators, and Composer visibility. Malformed owner/primary, Pages authorization, Agent Dock, image locator, or kind/config combinations fail closed.
- Profile preferences are separate from Window Session layout. Per-Project view presentation, DB view preferences, sidebar collapse/width/disclosure, and bounded recent Pages persist through the focused profile-preference Adapter; they do not add another active Scene or server-data owner.
- App-window Back/Forward history and previews remain renderer-local because they are live interaction state, not cold-restore authority.
- Renderer server-state cache owns exact Project/Session detail, bounded summary windows, and bounded Page Chat projections. Sidebar rows come from Project/projectless windows, but an active restored Project or Session owner is hydrated by exact identity and never inferred missing from a bounded list. Mutations that return a full Session seed its detail cache. Board/List activity is a batched join with visible Page IDs rather than per-row hydration or Database state. Full Project Session list reads are reserved for slow domain paths and never carry Scene layout.
- Renderer presentation mounts exactly one selected owner Scene and one selected body per panel leaf. Switching disposes the previous React view; scoped renderer state restores explicit presentation, while Query and the Codex/Browser/Terminal/Document Modules preserve their own data and runtime continuity. The existing Session renderer receives a leaf compatibility projection from Scene, but there is no second writable `sessionViewsBySessionId` store.
- Renderer-local side chat state owns temporary tab identity, loading/ready/failed/expired status, failure presentation, and panel placement. The backing app-server thread stays in the main-process conversation cache only while live and is discarded when the tab closes. Failure after main created the fork compensates that temporary thread before surfacing the failed tab.
- Core schema v90 removes historical `project_session_tabs`, `panel_state_json`, and `left_pane_collapsed`. It preserves Session/Thread/Project/content data and extracts at most one valid Database View target into `initial_database_view_id`; the old shared arrangement is intentionally discarded because no Window Session owner can be inferred. Historical schema v93 replaces that pointer with `database_starter`, and historical schema v99 removes the field after v98's Yjs-integrity migration: it deletes only unthreaded marked starter Sessions and preserves threaded marked rows as ordinary Sessions. Current schema v100 adds normalized Relation Property authority, and current schema v101 adds the persisted projectless permission-mode scope without changing Session behavior. Fresh Project creation creates no Session.
- Old stage-rail/window layout snapshots are best-effort migration inputs only; after decode, owner-scoped Scene state is authoritative for presentation and Core never owns it.

## Navigation

- Scene switching synchronously unmounts the previous owner route and mounts the selected owner's Scene composition: a Session primary plus its panel groups, a Project's root-bearing full-width surface stack plus bottom panel and Agent Dock, or the primary-free Pages full-width stack. Exactly one owner route and one route header exist. Project selection never selects a first Session, and sidebar disclosure never changes location.
- Scene switching reuses exact cached Project/Session detail and authoritative Module state without calling the full Project Session list solely because the owner changed. Returning to an owner or panel surface creates a fresh React view and restores only explicitly owned presentation such as Composer drafts, transcript state, and registered scroll snapshots; ephemeral component-local state resets.
- App-window Back/Forward controls are available as titlebar buttons, command palette commands, `Cmd/Ctrl+[` and `Cmd/Ctrl+]`, desktop mouse Back/Forward buttons, and the macOS application menu; all routes enter the same shell-owned navigation executor. The command ids are `navigateBack` and `navigateForward`, labels are `Back` and `Forward`, and the disabled state follows the shell-local back/forward stacks.
- Each history snapshot stores the exact Workbench location plus all owner-keyed Scene snapshots, including primary target where applicable, right/bottom active surfaces, collapse state, and right-panel full-width state. Presenting a Library target and selecting Pages commit as one transition. Settings routes, command palette state, task search, and Browser webview history stay outside this stack.
- Tab switching persists only through the owning Window Session Scene's panel leaf layout.
- Browser-sidebar webview navigation remains separate from app-window history. Browser tab `canGoBack` / `canGoForward` and `webContents.goBack` / `goForward` must not drive the top-left workbench Back/Forward buttons.
- Review is a Session Scene singleton kind across both right and bottom panels and is available only after that Session has an attached Thread. Project and Pages Scenes cannot own Review. DB View is deduped by exact target and Canvas Stage by `(accessContext, canvasBlockId)` within its owner Scene, so repeated opens focus rather than duplicate the same target. Browser is deliberately multi-surface; creation affordances keep showing Browser even when Browser tabs already exist, and Browser tab context menus add `New tab to the right`, `Reload`, and `Duplicate` before the generic close actions.
- Tab context menus append generic close actions after feature-provided items: `Close`, `Close other tabs`, and `Close tabs to the right`. `Close other tabs` is enabled only when another closable tab exists in the same leaf; `Close tabs to the right` is enabled only when at least one closable tab follows the current tab. Cross-panel move and split actions remain below the generic close block when available.
- Tab reorder mutates only the owner Scene's panel tree; no Core Session mutation or cross-window invalidation occurs.
- Closing a persisted local panel surface removes that descriptor from the owner Scene. Every panel surface is closable independently of how many siblings exist; if it was the panel's final persisted surface, the local reducer collapses the panel and retains the final empty group as its fallback. Project and Session primaries are not closable panel surfaces; Pages has no protected primary and permits an empty tablist. Terminal backend exit removes matching descriptors after Main publishes exit; local Terminal close releases its Window Session lease without killing the PTY. Browser close tears down its Main runtime, Files/Page/Canvas close flush their owning lifecycle before removal, and closing a Conversation surface never archives/deletes its Session. Closing a preview drops only renderer-local preview state.
- Closing a side-chat tab removes the tab immediately and sends a best-effort discard request in the background. If the backing temporary thread is missing, the tab renders an expired panel with `Start new side chat`, which recreates from the saved parent thread id. Failed and expired tabs both preserve that parent identity and retry in place; another failure remains explicit and retryable rather than returning to a permanent loader.
- Owner routing changes are synchronous so route cleanup/setup and header ownership complete in one deterministic lifecycle. Lower-priority data refreshes may still use transitions, but routing itself must not have warm/cold branches.
- React keys should reset only the active Scene/surface body that changed; switching owners must not force unrelated global stores to remount.
- When a full-width right-panel tab collapses the primary viewport to zero width, the selected route and owning runtime stay active. In a Session Scene, Composer, footer, and lifecycle coordinator remain active while transcript children unmount. Restoring regular width remounts primary content from its explicit runtime state.
- Only the selected Scene may register shell side effects such as global header actions, summary panels, composer overlay targets, panel measurement refs, or visible Browser webview ids.

## Keyboard Model

- Existing global command palette, settings, and editor shortcuts remain in force. Undo/redo is local to the focused editable surface; the shell owns no Project-wide history stack.
- The previous stage-order shortcuts (`View -> Card -> Thread -> Diff`) are retired as primary shell semantics.
- Project/Session/surface keyboard shortcuts follow the hierarchy: Project disclosure control, Project navigation control, Session row, owner primary, and right/bottom panel groups.
- `Cmd/Ctrl+J` executes the shell-global `toggleBottomPanel` command and shows or hides the selected Scene's bottom panel. Toolbar, command palette, Browser-runtime keyboard handling, and desktop application menu share the same shell executor; Electron owns the desktop accelerator so one keypress cannot toggle twice. It works from editable and desktop Browser surfaces, preserves explicit user unassignment, and safely no-ops only when no Scene is active.
- `Ctrl+\`` focuses an existing eligible Terminal surface or creates one in the selected Scene's bottom panel. `Alt+Cmd/Ctrl+S` starts Side chat only in an eligible Session Scene. The global terminal drawer is not part of the Scene model.
- `Cmd/Ctrl+Shift+[` and `Cmd/Ctrl+Shift+]` cycle the previous/next tab for the focused right or bottom panel tab group in the selected Project, Session, or Pages Scene. Cycling resolves the nearest split leaf or the last focused leaf from the native menu route, wraps within that leaf, works from NFM editor content in that leaf, no-ops for zero or one tab, and does not replace plain `Cmd/Ctrl+[` / `Cmd/Ctrl+]` app-window Back/Forward.
- `Cmd/Ctrl+W` closes the active closable tab in the focused right or bottom panel tab group through the owning Session or Scene tab adapter, with the same close semantics as tab chrome. It works from NFM editor content in that leaf, ignores input fields and dialogs, no-ops for non-closable tabs, and must not close the app window. Closing an inactive tab preserves the current selection. A Browser tab created or duplicated to the right records its opener in an ephemeral, generation-scoped tree. Closing an active current-generation child selects the nearest right descendant of the same opener tree, then the nearest left descendant, then its opener. Selecting an unrelated tab or moving/reordering a tracked tab invalidates that affinity. Without a valid opener result, selection stays within the same split leaf and follows physical order: the right neighbor first, then the left neighbor at the row edge. Visit recency does not override either rule. Close-button and middle-click single-tab closes use the same routing. On macOS, Close Window uses `Cmd+Shift+W`.

## UI Contract

- Surfaces should use the generated theme layers and token classes before adding local CSS.
- Left titlebar navigation uses one grouped toolbar rail. Back renders lucide `ArrowLeft` with `icon-xs`; Forward reuses the same icon with `icon-xs -scale-x-100`. Each button has matching `aria-label`, `title`, tooltip text, command palette title, and disabled styling. On macOS the collapsed sidebar titlebar reserves `208px` total and renders the compact `New chat` edit/new-chat glyph after Forward.
- Tabs are dense, use hover-revealed close actions, support pointer reorder through the shared tab strip, and scroll horizontally when the user wheels over an overflowing tab row. Tabs share equal responsive widths regardless of title length, growing together from 90px up to 160px before the row overflows. Direct close-button clicks and middle-click closes enter a rapid-close mode that temporarily locks the whole row to the target tab's current width until the pointer leaves the tab row, so repeated closes stay under one pointer position. Rapid close affects only tab-row measurement and pointer stability; the revealed tab after any single-tab close still follows same-leaf physical order. Each tab item exposes a hover tooltip with its full title; cross-project Card Stage tooltips include both the card title and the content project.
- Empty-panel action choosers use the Codex row-stack layout: `p-2` host, centered `max-w-xl` stack, `gap-1 px-panel`, full-width `min-h-10` rounded rows with secondary background, `icon-xs` leading icons, `text-sm font-normal` labels, and right-aligned compact shortcut labels. Attached project-backed Session option order is Review (`Ctrl+Shift+G`), Terminal (`Ctrl+\``), Browser (`Cmd/Ctrl+T`), Files (`Cmd/Ctrl+Shift+E`), and Side chat (`Alt+Cmd/Ctrl+S`), with eligible project-native destinations following. Project Scenes omit Session-only Review and Side chat and order Terminal, Browser, Files, then eligible project-native destinations. Threadless Sessions omit Review and Side chat. Pages instead uses a search-first combobox backed by the bounded Library catalog; it opens or focuses Page, Database-default, and Canvas targets and offers New Page and New Database. Search is capped at the shared 256-character Library boundary, Arrow keys move the active option, Enter accepts it, and Escape closes the picker. If no generic action is eligible, the generic `+` trigger is omitted rather than opening an empty menu.
- Side chat entry points are available from the empty-panel action chooser, panel new-tab menu, attached-thread header overflow menu (`Open side chat`), composer slash command (`/side`), and the thread selected-text `Ask in side chat` overlay. Explicit prompt entry points such as `/side <prompt>` submit the prompt into the temporary side chat; selected-text overlay entry points create the side chat and prefill the side composer without submitting. Creating a side chat from within a side chat is blocked with `'/side' is unavailable in side chats. Return to the main thread first`.
- Keep `Timeline` hidden until Nodex has a first-class tab kind and eligibility model for it.
- Project/Session rows should be information-dense and shallow.
  A Project row keeps one optically inset fixed leading slot: it shows the Project marker at rest and replaces it instantly with the independent disclosure chevron while the row is hovered or focused.
  That optical inset must not move the Project label from its Session-aligned position.
  The disclosure toggles nested Sessions without navigation, while the aligned Project label opens the Project Scene.
  Right-side chrome is reserved for row actions; disclosure must not consume a second trailing slot or shift the label.
  Session rows use their derived `displayTitle` and a subtle Thread-attached indicator.
  They do not render relative age in the row.
  An attached Thread's rich hover card shows its live relative conversation recency, sourced from the durable app-server recency clock; opening, reading, renaming, pinning, archiving, reordering, status changes, and execution-location changes do not refresh it.
  A Threadless draft has no conversation age and its hover card shows no relative time.
- Project folders are sortable with pointer and keyboard input. Pointer drag starts after 6px of movement from the project-label activator; `onDragMove` and `onDragOver` both refresh intent so crossing the same target row's midpoint resolves a precise before/after boundary, while keyboard sorting uses the translated active-row midpoint. During drag, the source stays in its original slot as an inert 20% ghost, sibling folders do not live-shift, and a compact body-level folder preview follows the pointer. The final insertion boundary is shown without changing list layout by a 2px link-blue rail with an outlined leading dot. Normal and pinned lists persist through their separate project-order APIs, unchanged boundaries do not write, acknowledged order remains visible until canonical Project props render it, and failed writes clear only their matching optimistic projection before surfacing the shared reorder error. An empty Pinned target reveals its indicator only while actually hovered.
- Project and projectless chat rows use their bounded Core Task windows as the canonical display order.
  Same-lane regular-row sorting persists the complete Session order, so a durable pre-thread `New chat` is draggable like every attached Chat and keeps its chosen position when its first Thread links.
  Cross-lane moves remain one relative move of an attached Thread; when the destination already uses Session order, Core inserts the moved Session without replacing that order.
  Returning to the original insertion boundary is a silent no-op that installs no optimistic mutation and sends no command.
  The initiating window keeps a real operation's optimistic placement through command acknowledgement and query-cache installation, releasing it only after the affected canonical lanes have committed the placement in React or a later projection supersedes it.
  Late older projections cannot replace newer installed windows, and a same-revision nonterminal first-page response cannot trim an already loaded window.
  During the gesture the source stays in its original slot as an inert ghost, sibling rows do not live-shift, and the insertion rail paints from a zero-height boundary without changing list or scroll geometry.
  Releasing the pointer paints the final row position immediately and never replays a source-to-target layout transition.
  Pinned rows retain their dedicated pinned-order owner and use the same render-aware handoff.
- Sidebar sorting is one end-to-end row/composition contract, not a visual wrapper. Every lane that presents or moves a Project or Chat must keep the shared row renderer inside the existing gesture owner and sortable context, with its semantic container, stable row or placement identity, canonical ordered item identities, and exact next-item boundary. Source and destination eligibility, center-versus-edge hit targets, insertion indicators, pointer and keyboard movement, optimistic handoff, and Core persistence change together. A row that only enables HTML dragging or `useSortable` is not integrated. Adding or reparenting a lane requires focused behavior coverage for same-lane reorder and every supported inbound and outbound move, including empty and collapsed destinations.
- Desktop Project and Chat sidebar menus use one declarative action model rendered by the operating system for both row context-clicks and matching overflow triggers. The browser build retains the existing app-owned Project dropdown fallback. Project order is Pin, Edit, organization actions, chat actions, then Remove; Chat order is primary actions, Project/Section organization, sharing/copy actions, then window actions. Unsupported conditional capabilities are omitted rather than shown as inert substitutes. Every top-level action uses its dedicated app-owned geometry, selected custom Sections use the native `✓` label convention, displayed shortcuts are not registered a second time, and `Open in` includes only detected applications with their color application icons.
- The thread page content frame keeps the shell top border but forces the frame top offset to `0px`, so the thread title row starts at the top instead of below an empty toolbar band. The global top-right controls are reserved inside that title row through the thread header right-reserve area.
- Do not reintroduce the stage rail, a hard-coded Project Home, or fake host Sessions as compatibility layers. Database, Page Stage, Canvas Stage, Conversation, Review, Files, Browser, and Terminal remain reusable bodies behind the closed owner-scoped Scene surface union.
