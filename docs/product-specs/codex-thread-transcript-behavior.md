# Codex Thread Transcript Behavior

## Intent

This document is the source of truth for visible Codex Threads transcript behavior in Nodex.
It defines what appears in chat, what stays internal, how transcript state is projected, and how live and restarted threads stay consistent.

Other product specs should link here instead of restating transcript behavior.
Detailed Auto-review preset and approval-lifecycle rules are specified in [Auto-review Behavior](./auto-review-behavior.md).

## Scope

This spec covers:

- canonical transcript projection and entry ordering
- pending prompt projection and authoritative echo reconciliation
- visible item kinds and transcript rendering rules
- turn bucketing and composer-shell request rules
- transcript-only UI behaviors such as request-user-input rows, plan follow-up prompts, exploration summaries, searchable content units, and agent-body collapse
- v2 mixed-family activity classification, grouping, summaries, leaves, and agent-body collapse
- persistence and restart recovery rules
- internal bootstrap/context visibility rules

This spec does not cover:

- general workbench shell layout
- thread auth/account flows
- worktree creation, environment setup, and the client-only initialization item,
  which are specified in
  [Codex Worktree Creation Behavior](codex-worktree-creation-behavior.md)
- managed-worktree availability, restore, retention, and execution-location
  movement, which are specified in
  [Codex Managed Worktree Lifecycle Behavior](codex-managed-worktree-lifecycle-behavior.md)
- approval policy configuration outside its visible transcript effects

## Canonical Model

- Thread metadata carries the current configured model and reasoning effort when available. Metadata-only reads update those settings without loading history; unavailable model metadata preserves known settings, and explicit settings remain authoritative. These fields describe configuration, not the model that executed each past Turn.
- Resume adopts the effective native collaboration mode when provided, preserving Plan mode and its settings across reconnects.
- The visible transcript is an ordered projection of `CodexTranscriptEntry` values from the canonical conversation document. That document keeps sparse ordered Turn history and separate live overlays. Its participating Main or window owner publishes revisioned patches; Main's native transport and durable authorization do not create a second canonical writer. See [owner/follower streaming](codex-thread-owner-follower-streaming.md#canonical-document-and-patches).
- Canonical conversation context lives directly on the document: unread state, hydration, model settings and goals are not nested in a secondary state object. Pending requests and unread state remain available independently of loaded history.
- Activity status, subagent parent authority and terminal completion cleanup resolve resident canonical Turns by native identity. Legacy values may supplement identities absent from canonical history, but cannot override canonical completion or become a separate activity authority. Turn metadata checks use resident references; they do not materialize transcript presentation or item bodies.
- Ordinary Codex transcript rows consume a normalized read subscription derived from the manager's canonical document. Sparse slots retain their original indices; item identity includes its Turn entity. Streamed text updates the addressed item leaf without rebuilding unrelated rows or rescanning the body model's resident Turns. Existing item and fragment projections retain their identity when slots append or equal lifecycle metadata is serialized again. A hidden assistant prefix becoming visible creates its leaf during streaming; internal startup-prewarm input remains hidden even when only retained params survive. The manager also publishes lightweight history generations and pagination references for recovery controls; text-only changes retain those references and their history revision. Chunked resets remain invisible until commit, and the last view subscription releases cached transcript content. Backend-specific and inherited presentations retain explicit semantic Adapters; JSX does not establish a second transcript authority.
- A first submission keeps one explicit launch presentation until the normalized transcript acknowledges the same client message identity. Canonical acceptance can precede RPC reset commit; that gap must not remove or duplicate the pending user bubble. The launch presentation remains a UI overlay, and never installs its content into the canonical document.
- Canonical Turn timestamps use milliseconds. Projection back to the generated protocol converts `startedAt` and `completedAt` to seconds, preserving fractional and null values; `durationMs` remains milliseconds. Repeated hydration and projection must preserve these values.
- Renderer derives turn-scoped view models from that canonical transcript (`thread detail -> turn buckets -> render blocks`), but transcript merge/reconciliation stays outside the JSX layer.
- A canonical turn projects its params-sourced user input before its raw items. A matching raw `userMessage` echo is suppressed when it carries the same client identity or the same structural text/image input, provided that only permitted metadata items precede it. The params-owned row retains its stable display identity and the proven native opening-message alias, including while that raw item is not resident. Explicit opening metadata takes precedence; a confirmed absence prevents inference, and an incomplete suffix cannot establish opening identity from matching input alone. Persisted search addresses this native alias rather than guessing ownership from displayed text. A blocked submit remains visible with `not sent` delivery semantics and no sent timestamp.
- A submitted prompt is represented by that params-owned turn occurrence, not by a synthetic transcript item. `CodexTranscriptEntry.source` distinguishes live, bootstrap, and replay projection only; it has no optimistic source variant.
- Every nullable optimistic Turn carries a stable local occurrence identity through server-id binding. Renderer row keys, search keys, lifecycle projections, and motion placement use that occurrence identity before the protocol id, so binding `null -> server turn id` updates data without remounting or replaying the latest-turn placement animation.
- Fresh thread creation, pending prompt submit, live runtime updates, resume, and restart recovery must all feed the same projection rules and produce the same visible transcript shape.
- Paginated resume and ordinary paginated reads hydrate a bounded tail. Older-history requests reveal one page at a time, and partial Turns retain per-Turn item cursors plus their params-owned opening user input so the visible leading user row and identity remain stable before all raw items are resident. Explicit complete-history loading may extend the owner's canonical document. Export streams are a separate operation and do not populate the resident snapshot merely by exporting it.
- Turn-list and timeline cursors belong to separate native APIs. Continuations carry their explicit history source; a cursor without that source is rejected. Early tail reads keep history visible while resume preparation is pending. After native adoption, the final snapshot refreshes from that resume's Turn cursor, or from the newest null-cursor timeline page when timeline history is enabled; it never substitutes a pre-resume page for the adopted tail.
- Runtime item normalization is an internal parse layer only. It may help extract tool metadata or streaming content, but it is not the renderer-facing transcript contract.
- Every user-visible agent turn requests the app-server's readable reasoning-summary stream with the Electron-compatible `concurrent_reasoning_summaries` capability and `detailed` default; an explicit per-turn summary override remains authoritative. The owner, follower, canonical optimistic state, and resumed thread settings use the same resolved policy.

## Visibility Rules

- Only actual conversation and visible tool/reasoning state belongs in the transcript.
- Internal bootstrap/context content such as `AGENTS.md`, developer instructions, and other session setup wrappers is not part of the visible transcript.
- Raw rollout `response_item.message` rows are not themselves visible transcript truth.
- Restart must not reveal transcript rows that were hidden in the live session.

## Ordering and Identity

- Transcript order is owned by the projection layer, not inferred ad hoc in the renderer.
- Projection assigns one canonical sequence order for visible entries.
- Params-owned submitted prompts and later authoritative user-message entries must reconcile into one visible row instead of rendering twice.
- Transcript identity and duplicate reconciliation operate at the transcript-entry layer, not by mixing raw rollout ids directly into renderer state.
- Sparse history positions, canonical Turn entities, and native search occurrences retain separate identities. Virtual rows join the canonical history position, while item subscriptions and search units retain their original entity and native item identities. A gap stays between its adjacent resident islands; a missing historical position cannot silently move its content to the transcript tail. Inserting a page preserves the visible native content anchor before subsequent measurement callbacks run.
- The detailed turn-level classifier, conditional assistant-promotion rule, and post-classification lane order are specified in [Codex Thread Turn Ordering And Assistant Promotion](./codex-thread-turn-ordering-and-assistant-promotion.md).

## Bounded History and Search

- On a non-durable execution host, a resumed paginated Thread initially owns only its metadata, latest five Turns, and a shared maximum of 500 hydrated items. Interactive pages use item counts rather than rejecting valid tool output by an estimated byte multiplier. Paginated history does not drain automatically after resume.
- A durable execution host resumes with inline Turns and separately reads a five-Turn history page from the beginning of the descending list. Each fetched Turn loads all its items in ascending pages of up to 500, using five fixed worker sequences and a 30-second default request timeout. Oversized item responses halve the request limit at the same cursor; unrelated failures and repeated cursors fail the load. The inline resume supplements the fetched page without reopening completed work or replacing its completed output with an older running snapshot. Continuation state comes from that page, while its oldest-Turn anchor includes the merged inline Turns even when the page is empty. Durable history does not acquire paginated-item cursor state or drain its remaining Turn pages automatically. Rejoining an active durable Thread keeps its native history identity and uses full access with automatic approval.
- Resume retains the history contract selected during preparation, even when the response reports a newer history mode. An inline legacy page installs both its canonical boundary and continuation metadata. On an ordinary legacy endpoint, a tail resume may load the remaining history after its completed snapshot is published and the current goal hydration settles. A failed goal read or a newer goal value does not suppress that load; a superseded hydration, retired manager or connection, reconnect recovery, durable host, or enabled paginated-history policy does. Complete-history demands coalesce within the admitted entity, native connection and ownership lifetime. Replacing the entity or losing ownership invalidates pending page acceptance and publication, even if that manager later regains ownership. Canonical history can load without an installed presentation snapshot.
- Reopening a paginated Thread merges its new tail with resident Turns and items. Each Turn retains its newest snapshot item identity. Opening-message metadata distinguishes an unknown value from a confirmed absence: failed or inconclusive opening reads leave the identity unset, while a completed empty prefix records null. Confirmed opening messages retain their client correlation id. Turn hydration prefers this opening metadata; otherwise it skips compaction items and uses a leading user message only when the oldest item is loaded. A user message at the beginning of a partial suffix is not inferred to be the original prompt. If the new tail contains the previous anchor, item paging resumes at the previously retained older cursor; otherwise a reconnect interval bridges the old and new snapshots. Reconnect pages insert at that interval, switch back to the old cursor when they reach its anchor, and preserve items changed by live updates during the read. A stale in-progress snapshot does not reopen a terminal paginated Turn.
- Resume inherits nonpermission Turn settings from the latest resident Turn with a native id. Presentation overlays and unassigned submissions cannot replace that authority. A saved working subdirectory survives metadata lookup and resume when it remains within the returned workspace root; a different returned root replaces it. The executing owner, follower document, hydrated settings and durable Thread retain the same resolved directory. A prepared renderer receipt and Main acceptance carry the actual requested directory through retries and persistence.
- Resume also retains its caller's service-tier selection through queued preparation, owner admission and native retry. A non-null caller tier requires configuration preparation even for an idle Thread; absent or null caller tiers do not force a reload. Resident Thread settings and assigned-Turn tiers keep precedence over the caller's fallback, including an explicitly retained null tier. The renderer receipt retains the resulting request unchanged across retry identities.
- Native resume always uses full access and automatic approval. Historical approval policy, reviewer, sandbox and profile fields remain observed transcript facts; they cannot override execution. Preparation retains the requested working directory for result reconciliation and retries keep the same prepared nonpermission controls.
- Configured workspace directories remain factual execution metadata. Their paths use the executing directory's path family. Windows drive, UNC and WSL mount aliases compare consistently without treating ordinary Linux paths as case-insensitive or conflating different WSL distributions. They do not limit Profile content access.
- Reconnect restoration uses interactive request priority and an explicit 30-second native resume deadline; timeout recovery stays with the restoration controller instead of expanding the ordinary resume timeout budget. Ordinary resume retains its critical priority and default retry policy. Metadata, history pages, item pages and opening-message probes preserve the admitted request priority. A requested goal confirmation inherits resume priority; background goal hydration inherits it during reconnect recovery and otherwise uses the native request defaults.
- Interactive and critical item recovery bypass the two background-preview slots, including when unrelated previews are still awaiting native responses. The selected Turn's opening-message probe retains that foreground priority; background previews continue under their own admission and pagination lifetimes.
- Resident opening-message metadata is sampled after the Turn-list response and reused for partial history. A known opening identity, including confirmed-null, suppresses the optional ascending probe. Unknown identity may still be probed; failure preserves the resident input and client identity. Fully loaded Turns use their actual opening items instead of carrying partial-history metadata. Interactive opening probes run alongside subsequent Turn hydration and settle before the page returns; canceling the page releases unfinished probes. A caller may bound items per Turn independently of the shared page budget; ordinary history leaves that per-Turn limit unbounded.
- Resident history is a sparse set of ordered islands separated by explicit gaps. A gap with a current server cursor may request exactly one adjacent page; page admission requires the original island and boundary progress to remain current, and physical Turn-page responses must advance their cursor; an unproven boundary is opaque and inert until a stable server boundary is available. A delayed Turn-item recovery intent must still match the current topology generation, requested edge, anchor and history source before any native read. Request coalescing and stopped-page state use that topology identity: a stale read cannot block a current recovery intent that reuses the same physical cursor. Unrelated live text does not retire that intent; connection and page-ownership fences still govern acceptance after the read. Empty content is never used to pretend that missing history is complete.
- Canonical Turns directly own their parameters, lifecycle timestamps, hook runs and item lifecycle metadata. Reducers update these fields on the Turn; transcript rows are derived projections. Turn context is not stored in a nested `sidecar` object. Turn identity, status, error, duration and item view also live directly on the Turn; generated app-server projection explicitly selects protocol fields and excludes app-only state.
- Turn-list completeness and item completeness are independent. A complete Turn list may contain partially loaded items. An explicitly incomplete Turn list remains incomplete when no usable cursor exists; ordinary resident-item or metadata updates preserve that state. Boundary paging may establish completeness only after all intervening gaps and outer boundaries are exhausted.
- Turn and item pagination are independent. Every partial Turn carries its own older-item cursor, completeness state, opening user-message identity, and opening user input. Each physical item segment retains exact cursors for both edges; adjacent reads use the requested edge segment rather than the most recently fetched page. App-server cursors may re-include resident anchors. New items are inserted before the next resident anchor, existing values win on resident identity overlap, and unanchored incoming occurrences retain their supplied order. Renamed final answers with identical text retain their existing identity and citation; the resolved alias applies to every incoming occurrence. Empty or duplicate-only pages with advancing cursors advance normally; a repeated cursor or an item belonging to another Turn is rejected. Physical request size is not a maximum retained history size.
- Loaded Turns and item segments remain resident while the conversation owner is retained. Paging merges all loaded history and overlapping islands without evicting the opposite edge. Viewport geometry and estimated history bytes do not control data retention.
- Ordinary inactive owners are retained for up to three hours, with at most ten eligible ordinary owners retained per renderer; excess owners unsubscribe in oldest-inactivity order. Ephemeral side conversations do not count toward ten but still expire by age. Failed unsubscribe retries after 15 seconds. Active views and followers prevent eligibility. Runtime-active conversations, an in-progress latest Turn without a pending interaction request (or in an ephemeral side conversation), a proven empty conversation without a persisted rollout, and steering messages awaiting their authoritative server echo remain loaded. Becoming eligible after protected execution starts a fresh inactivity interval.
- Successful unsubscribe releases only that conversation's stream. Metadata and pending questions survive; runtime status reflects the remaining question, and the next interaction resumes the stream. Reopening during an in-flight unsubscribe preserves visible history but does not keep a stream the server has already unsubscribed. Replaced owner epochs ignore stale completions. Ephemeral side conversations preserve their content and become not loaded.
- Whole-conversation history release clears every loaded island and retires outstanding history loads, with unknown pagination boundaries for the next resume. A passive conversation without a stream or active view can release substantive history after activity ends; explicit history reads, running hydration, pending requests, protected execution and ephemeral side conversations retain their content. Fork-origin metadata alone does not trigger a release. This passive release does not change runtime status.
- The shared transcript requests a page when a loadable gap comes within 800 pixels of the viewport, through the current conversation owner's history capability. Only one gap request runs at a time. After each page, measured viewport demand determines whether another page is needed; loading stops when the gap moves out of reach or is exhausted. A failed gap stays visible with a local retry and does not fail the conversation attachment. In a native Codex conversation, these requests install in the viewing manager's canonical history, including when it follows another window. Ordinary page and item recovery use requester-local native reads under the admitted entity, connection, role and topology lifetime; they do not request complete history or wait for a remote mutation revision. A failed current item-page request also exposes a local retry; retries coalesce while loading, and stale or retired boundaries cannot be revived.
- Persisted search navigation hydrates the viewing manager’s local canonical history, including when it follows another manager. It uses native reads and local island insertion without taking ownership or waiting for a remote mutation revision. Persisted search requests 250 occurrence identities, then reads up to five Turns in each direction around the selected occurrence with a 500-unique-item preload budget per direction. The selected Turn continues in 100-item requests until the exact item is found or its cursor is exhausted; item count, payload bytes and physical request count do not cut navigation short. Advancing empty or inclusive pages remain valid, and optional opening-user probes may fail without discarding a valid match. Occurrence shape and generation are validated at the boundary. A partially resident Turn uses the same target-complete hydration path; navigation never treats an unrelated loaded page as success. The view waits for the selected projection rather than a fixed frame count, and cancellation settles even while rendering is suspended. Navigation may introduce a new island without bridging unloaded ranges.
- The prompt rail lists every Turn the conversation owner can index, through the same history capability that loads its pages, so a long conversation is navigable before its older history loads. Index and preview reads never install history; selecting an unloaded Turn asks that owner to make it resident, then scrolls to its message. Resident messages outside the index keep their conversation position. A replacement history reader keeps the current index until its own arrives; an owner that cannot index the conversation leaves the rail on resident messages.
- A native Codex index holds at most ten metadata-only pages of 100 Turn shells and reloads with each new history topology. A preview resolves its ordinary-history native cursor and reads one Turn with at most 30 items without installing history. A later timeline policy change cannot reinterpret that captured ordinary cursor. Clicking a preview hydrates the selected message through persisted-search navigation before scrolling. Native host lifetime fences retire stale results; the shell index has no separate byte quota. Agent Runtime conversations index their own Runs as described in [Agent Runtime behavior](./agent-runtime-behavior.md).
- The viewing conversation manager qualifies persisted search from its canonical `historyMode` and current native search capability. Main routes the typed occurrence read through the Library-scoped Thread host and independently validates native capability and generation; a Main conversation replica is not required. A legacy Thread, an older host, or an unproven version yields typed feature unavailability. Search results and navigation require the originally admitted conversation, host, peer role and topology generation; stale reads cannot install into a replacement conversation with the same Thread id. An installed presentation snapshot is not required. Prompt navigation continues over resident Turns, and transcript search continues over resident entries, without repeatedly requesting unsupported persisted history.
- Selecting an occurrence already present as an exact native item in the admitted resident Turn needs no further history read or publication. A summary placeholder with that identity still hydrates through the ordinary selected-occurrence path.
- Find centers the exact active highlight through native smooth scrolling. History-page growth and Composer resizing preserve their normal viewport compensation while the current search destination continues to completion. The destination follows the current query and its mounted highlight, including a brief highlight remount. While positioning remains active, at most one destination row remains connected outside the ordinary bounded render window at its actual layout position; an aborted query, retired view, user scroll gesture, message navigation or submission cancels that continuation. Compensation cannot resume a retired search or scroll another matching occurrence.
- Full transcript export is an explicit cancellable job that yields one fully hydrated Turn at a time. Complete canonical history, including live overlay updates, exports without an installed presentation or a native connection. Turn-list completeness alone is insufficient when a resident Turn still has unloaded items. Incomplete paginated history uses separate native page reads under host-generation, item-count and byte budgets; each fetched Turn is projected directly, independently of resident history islands. Incomplete legacy history is reported as unavailable rather than exported as complete. Export never installs fetched history or a presentation in the live conversation. Clipboard export has a separate final allocation cap; exceeding it leaves the resident transcript unchanged and reports honestly that copying could not complete. Nodex does not advertise a file export until one exists.
- Runtime conversation Copy reads the exact bound Session and selected Thread through paged history, including captured fork ancestry. Omitted output uses explicit addressed detail reads. Imported native history uses its passive history query. Neither route resumes an obsolete native execution owner. Export retains one bounded source page and at most 16 MiB of Markdown, keeps late background fragments with their original Turn, and leaves the resident transcript unchanged. Cancellation, a changed binding, an unavailable item or a stalled cursor stops the export without copying an incomplete document.

## Mixed persisted history

- A root paginated Thread whose recorded native version supports timeline history uses canonical mixed-history metadata; forked Threads, unknown versions and development sentinels do not acquire that qualification. This describes persisted history format independently of microphone availability or private runtime assignments.
- Any resident native timeline owns its presentation order, including timelines containing only ordinary items. Turn fragments retain their native opening-message and last-work context; a fragment's local first item cannot become the opening prompt. Input and completion extras each appear once, and fragment completion status remains presentation state rather than changing canonical Turn status.
- Realtime session boundaries and transcript segments render directly from keyed timeline records without fabricating ordinary canonical Turns. Each native promotion receipt keeps its own identity and recorded position; distinct receipts may reference the same raw item or visualization index. Ordinary item receipts are suppressed when promoted, while a work fragment presents each canonical item once. A promotion whose raw item is still unavailable retains its pending position without ending the active work fragment. Promoted Markdown and interactive HTML retain their native file, source-Thread and receipt identities.
- Native whole-item image presentations own a separate measured receipt row and subscribe only to their addressed generated-image item. Repeated receipts keep distinct display positions, while preview and editing share one asset per native image identity. Pending state follows the item’s status even after its Turn completes; unavailable raw history shows no synthetic generation state, and hydration restores that receipt without adding ordinary work output. Unmounting one receipt preserves other mounted receipts and canonical history assets.
- Assistant messages, promoted Markdown and assistant realtime transcripts retain rich Markdown regardless of message size. Growing responses do not switch to a source viewer or acquire a nested message viewport. Interactive documents retain their state and focus as text grows and the response completes, and Find can highlight and reveal the rendered message text.
- These assistant surfaces use the same conversation Markdown grammar. Ordinary assistant and promoted Markdown search uses normalized authored source labels; voice transcript units retain native raw text. Catalog names, target controls and color swatches do not rewrite those search sources. Unknown directives remain literal, ordinary HTML remains literal apart from authored line breaks, and incomplete display directives cannot create interactive content. Streaming hides unfinished registered inline syntax until it can be displayed. Code preserves its authored whitespace and Unicode separators for rendering and copying; display preparation never rewrites canonical history. Voice user messages retain their independent user-message rules.
- Authored file links, file citations and inline-code file references open through the existing Files owner on the message's execution host, with their parsed path and supported line/column range. Resolved native paths are not decoded again, and a UNC authority does not select an execution host. Relative references require the message's workspace context and resolve once in the Files native-path model. Opening, copying contents or paths, and system actions use that same absolute target without decoding its native spelling again. Thread links use an explicit host when provided and otherwise the message host; nested detail links retain their owning root Session. Mounted source retirement withdraws pending menu, clipboard-read and navigation publication, while shared resource reads may settle for another consumer of the same resident source. Native commands already admitted by their owner retain that owner's execution contract.
- Skill mentions use the current catalog for the message's host and workspace. Only a unique, available local definition provides a file action; unavailable, ambiguous and remote definitions remain text. Inline code recognizes a native file reference before a complete authored link, Skill or six-digit color. Links do not recursively decorate their children. Color swatches are supplementary and hidden from accessibility text; issue references and numeric pull-request contexts remain ordinary text.
- Suggested tasks open a new chat draft in the message’s captured Project; a projectless source stays projectless. The title is display text, while the authored raw body replaces the prompt exactly, including an empty body that clears an existing draft. Accepting the new intent focuses the actual Composer once; unrelated updates do not take focus back. Using a suggestion never starts, queues or steers an Agent Turn. The mounted source and native item must remain current through draft preparation, and a retired source cannot publish late navigation or prompt text. Read-only child and side-chat messages use the same Project-scoped draft action without acquiring provider execution capabilities.
- Embedded media uses the same captured message source on ordinary assistant, promoted Markdown and assistant voice surfaces. Native file reads retain their execution host and resident source authority; an unknown or retired source cannot acquire file access. Local audio and video use the existing range-capable file stream, while admitted remote files use the bounded binary reader. Authored media classification precedes file-link decoding; ordinary HTTP image syntax stays an image regardless of its filename extension. Image queries remain fresh with a 15-second unused lifetime; audio and video queries are released when unused.
- A media-only paragraph widens one image or groups multiple images into a wrapping gallery; mixed prose or audio/video retains ordinary paragraph layout. Image preview follows the currently mounted images in DOM order and their resolved current sources. An unavailable outer preview opener returns control to the message's own dialog. Preview downloads and pending reads revalidate their selected source after asynchronous work. Audio and video controls use the native media element; completion preserves that element, while source replacement releases its decoder even when the playback URL is unchanged. Video initializes on demand within the message’s loading and unavailable states; delayed or failed initialization does not replace the surrounding chat. A data-backed video retains its decoder-owned playback source until that consumer retires.
- Loaded message images offer opening in a new tab and downloading, with address copying, image copying, adding to chat and revealing a local file when their required capabilities are available. Menu actions do not also open the preview. Adding an image preserves existing prompt text and attachments and does not submit; a destination known to reject images cannot accept it. Cross-host additions transfer readable image content rather than treating the source path as a destination path. Pending actions retain both the mounted source and the captured destination, and cannot publish after either retires. Web image content actions require readable bytes; a failed read reports failure and never tries a same-named local file.
- Opening a message image in a new tab uses an independent read-only image page with zoom and download controls. File and temporary image sources are materialized as managed assets before opening, so message unmounting does not revoke the page's image. Web images retain their web address. The tab follows the existing preview policy: pinning makes its image identity and read-only mode persistent across reloads. Read-only pages do not acquire editing or submission controls.
- Native voice user messages retain their complete Markdown in the shared user-message occurrence, with the same 20-line disclosure and clipped-focus policy as ordinary user messages and without Turn actions. Find delegates expansion to the owning disclosure before highlighting a folded tail; expansion preserves the existing content and native search identity. Updating that native segment resets its disclosure for the new text without materializing an ordinary Turn.
- Voice work borrows addressed native items without changing canonical Turn status or slots. Session changes, matching session close, spoken transcript and later user input end only the currently active work; these boundaries do not acquire completion timing or Turn extras. A Turn completion supplies timing, error, diff and hooks only to its current active work. Stale session close does not alter the current session. Actual started but unfinished Turns with resident metadata retain a pending work occurrence after the final timeline boundary, even before an item arrives.
- Active voice work shows its tools and Thinking state, hides assistant messages and child-agent activity, and has no ordinary worked timer. Terminal voice work retains its native assistant content, stays unfolded and omits ordinary Turn actions. When both segment timestamps exist it shows a worked duration, or a stopped duration for an interrupted Turn completion; unavailable timing is not fabricated. Complete voice delegation envelopes do not create user bubbles, and transcript-tail flush handoffs remain internal. Active work retains its Turn-scoped requests; terminal work retains only requests addressed to its selected native item, preferring the item target over a call target.
- Completed response resources come from output-purpose file citations and the last assistant message's supported document links. Source citations and legacy file references remain references; editing a file alone does not make it an output resource. Widget source files and scratch paths are excluded. File existence is queried on the Thread's execution host; loading hides unconfirmed files, missing files are removed, and a failed query retains candidates. The same filtered result owns cards, covered diff suppression and duplicate image suppression. Timeline resources appear once at the completion receipt, independently of earlier work fragments.
- Resource lists show all rows through four items, or the first three above four. A single Show more action reveals the remainder. File actions retain host and path identity, and remote files never fall back to a local opener. Resource expansion preserves bottom follow or the reader's existing history anchor.
- Interactive HTML is read through the semantic visualization query on the source Thread's actual execution host. Saved local HTML remains readable while the app-server reconnects; remote resource reads require a ready native connection and retain its generation fence. Bare lowercase HTML slugs resolve only in that Thread's UUID-derived UTC visualization directory under configured host roots; normalized absolute files additionally require the source Thread's workspace, writable-root or explicit temporary-root policy. In an Agent chat the source is the chat's Codex thread on this device, and absolute files must lie in the chat's workspace. Its responses stay resident while you are in another chat, because Agent execution, not a native resume, holds the chat's history. Attached native history that is read without a resume keeps its responses resident the same way until a reconnect invalidates that history. Reads inspect the file and at most 64 parent directories without following descendant symlinks and accept at most 5,000,000 UTF-8 bytes. The isolated guest receives HTML bytes and no filesystem or native-tool capability; tool calls and resource reads are denied. Widget clicks and display-mode changes preserve the current follow or reading mode; Thread scroll gestures own changes to that mode. Ordinary inline visualizations with `mode="wide"` offer fullscreen preview; narrow documents, a dedicated live HTML role and unfinished HTML updates remain inline. The preview covers the full window and centers a bordered, padded content surface with an 80% width limit and the document's intrinsic height. Intrinsic-height and fullscreen changes preserve the same guest and affect presentation only. Completing a response or adding its actions and output keeps the existing assistant document, guest state and focus mounted. External links require credential-free HTTPS plus an unexpired, single-use native user gesture from that attached guest and owning window; a document-provided gesture claim cannot authorize navigation.
- Interactive HTML follow-up messages use a single-use native guest gesture or an explicit editable review. Cancelling review sends nothing; reviewed messages discard app-supplied structured context. Accepted app text and structured context retain visualization provenance as untrusted tool output, separately from trusted user prose. Transcript display and search use the validated app request text; model instruction text, transport placeholders and structured context stay hidden. Running Threads queue the whole captured submission until idle. Queue persistence, recovery and editing preserve that provenance; editing updates the message text without promoting widget context into user instructions.
- Interactive HTML inherits the active host palette and typography. Appearance and accent changes update the attached document without restarting it; chart colors follow the accent while success, warning and danger colors retain their semantic roles.
- Interactive HTML includes document tooltips, keyboard-operated tabs, variant carousels and icons. Authored calendars validate dates, time ranges and up to 200 events, preserve overlap lanes and emit the selected event identity; invalid data remains visible and can be corrected. Tooltips do not contribute to document height. Ordinary documents retain internal scrolling; height reports preserve fractional CSS pixels, while the host rounds content height up and allows 5 pixels of paint overflow on each side. Inline placement uses content height; fullscreen measures its own content without changing that placement. Available document width excludes paint overflow. Fullscreen navigation keys are forwarded only after document handlers run, when they have not prevented the event; Escape can close a preview from an editing control. The surrounding Markdown Turn does not change the HTML role, file-cache lifetime or preview permission; ordinary inline files retain a 15-second inactive resource cache. A dedicated live HTML role and unfinished HTML updates have their own preview gates.
- Authored `Tweak` bindings declare range, color, toggle and select controls for specific document elements. Accepted declarations expose nonmodal **Adjust visualization** controls; ordinary clicks do not create annotations. Editing previews accepted values in the same guest and intercepts target clicks while allowing carousel navigation. Inline color fields accept authored HEX transparency; the compact popup previews opaque colors and commits three- or six-digit HEX on blur or Enter. Saturation dragging temporarily folds the other color controls while retaining the popup’s top position; keyboard color changes use the same declared target. The nonmodal panel supports primary header dragging and side/top resizing within the window, with ten-unit keyboard steps and Home/End limits. Closing clears its manual placement while retaining its size and changes. Moving focus outside or pressing Escape while composing does not dismiss it. Reset all restores accepted values without clearing the selected variants or request text. Inactive and fullscreen presentations close editing while retaining changes. Send changes submits the host-authored request with an explicit untrusted context attachment, independently of guest follow-up gesture/review authorization. The captured Thread’s execution provenance chooses immediate delivery or queuing; ordinary Threads queue. Immediate delivery uses the current native Turn for steering or prepares a new Turn after it becomes idle. Context requiring confirmation while a Turn is active places the same captured input in the local queue, retaining its identity and provenance; native text without that requirement can use the server queue. The originating host, Thread, Project or explicit projectless destination remain fixed while preparation awaits, and a retired conversation owner cannot admit late delivery. Failed submissions retain the open controls and changes.
- Validated adjustments and carousel variants persist for the displayed host, Thread and absolute file identity in the shared Profile state owner. A model attachment contains only target labels, changed control labels/references/values and selected variants; it excludes selectors, geometry and author object internals. Interaction JSON is limited to 32,768 formatted characters and 100 files per host/Thread. Request text remains transient. Clearing absent context is a no-op; clearing an existing file preserves an explicit clear. Confirmed model context injection precedes native submission, and matching explicit attachments deduplicate passive interaction context.
- File widgets restore validated JSON state for the same displayed host, Thread and file when their document is rebuilt. The source Thread used to read HTML does not select the state bucket. State is limited to 16 KiB of UTF-8 JSON and 100 files per host/Thread; image references are not supported. Each run reads the current state, and each update is fenced by the document's widget identity and attempt. Private state is never promoted into trusted user prose.
- Interactive HTML occurrences belong to their renderer window. Thread navigation retains the guest, JavaScript state and last inline body height, independently of the 15-second file-query cache. Returning to that occurrence binds the retained document to its new visible anchor, including when anchor restoration completes asynchronously; selecting the Thread alone does not remove parked occurrences. Two simultaneously connected consumers still use distinct guests. Height reuse requires matching document contents and never substitutes for fresh startup or measurement readiness. Inactive occurrences close preview, editing and review, revoke pending actions and suspend native gesture/capture authority without retiring their ports. Rebinding in the same commit preserves the occurrence; actually removing an anchor in its current Thread, accepted Thread deletion, an inactive detached Thread that needs resume, and final window teardown release it. Before acknowledging native window close, the window stops preparation and detaches all active, parked and unused guests while the renderer bridge is still available. Cached body height excludes paint overflow and fullscreen height. A new document generation rejects late measurements and actions from its predecessor.
- Accepted Thread deletion carries the execution host and Thread identity. The window releases that host's active and parked interactive occurrences from the application deletion event, even if history metadata was already removed. A same-id Thread on another host remains available.
- Each window prepares at most one unused, inactive interactive guest after its first visible paint and a background delay. A ready guest matching the current locale can be claimed once without navigation or HTML execution during preparation; the window then prepares one replacement. A warming, unavailable or mismatched guest never delays message rendering. Locale changes retire only the unused preparation, and explicit document retries use a fresh guest. Preparation cannot take focus or grant gesture, capture or action authority; claimed guests follow their occurrence's lifetime independently of the unused slot.
- Widget downloads accept only Blob content from a user-activated blob/data download link, a matching attempt capability and a single native guest gesture. Filenames are trimmed and limited to 255 characters. Inline and fullscreen actions can copy the current response as an image; captures verify the attached guest, owner and init identity, then crop using the actual screenshot pixel scale. Retiring a document immediately removes its interactive guest and releases Main admission; best-effort resource teardown never retains a retired document for interaction or a late capture.
- Accepted history and completed native artifact receipts automatically try to restore missing items. Automatic recovery remembers attempted receipts, permits at most two older timeline pages per attempt, stops when the target resolves or its cursor stops progressing, and fences late results after host/Thread release. Unresolved or failed recovery can be retried explicitly; exhausted history has no further load action. Missing raw items retain their receipt position and do not imply image-generation status.
- Eligible live timelines apply native started, text-delta and completed records by their keyed identity. Completion preserves the receipt position; duplicate starts and late deltas cannot reopen a completed record. Ordinary lifecycle and realtime receipts share timeline identity without creating synthetic Turns.
- Incoming timeline pagination replaces ordinary pagination and clears ordinary reconnect state. Extending older timeline history prepends older same-Turn items while preserving resident item values. A non-resume extension preserves proven completeness; a fresh resume adopts its new timeline completeness.

## Prompt and Turn Behavior

- Sending from a new-chat composer creates a session-owned thread; editor/card send-to-chat flows keep focus in the originating surface.
- Every durable new Thread requests `historyMode: paginated`. Before Session binding or any other durable Thread projection, Main fences the exact creating host generation and validates the returned empty paginated metadata shell. That concrete response proves the accepted storage contract; a version-derived capability flag is required only before optional history RPCs. A non-conforming response fails before Core state is mutated.
- Resuming through a current host generation always requests a metadata-only Thread shell. Host version comes from the server-version token in `initialize.userAgent`; the client-controlled originator prefix is not a capability allowlist. When independent history RPCs are unproven, resume also requests an inline page of the latest five Turns with full items. The returned page retains all supplied Turns and items, including partial item views; the requested page size is not an admission quota. This page proves only its own contents, not support for further history RPCs; unloaded history remains an inert gap. If the inline page is absent, resume reads authoritative history with `thread/read(includeTurns: true)`. A failed read fails resume; an empty successful history response establishes an empty conversation only when no resident Turns exist. Ordinary resume merges its returned Turns into resident history: an empty page does not erase local work, and correlated nonempty input survives an empty hydrated input. Results must still belong to the requested Thread and current host generation.
- Keyboard and pointer submission share one draft-transfer transaction. Renderer admission synchronously allocates one `launchId` and `clientUserMessageId`, publishes a Session-owned first-submission row, and only then clears the old new-chat composer or begins Project/Session/worktree/backend materialization. Admission immediately replaces the New Chat Home with the Thread surface; the Home hero and an admitted user row are mutually exclusive. The immutable presentation owner follows Session retargeting and a later real Thread without inventing a placeholder Thread. Main preserves both identities through first-Turn preparation. A matching renderer-optimistic row deduplicates the provisional row, but its nullable Turn id is not a completion boundary: only the matching app-server Turn with a server id may retire the fallback after the final transcript presentation commits. Generic reopen/resume must not compete while that fresh owner exists. Failures retain the submitted row, and progress from another `launchId` cannot replace the active attempt. The destination may never expose an intermediate empty surface, duplicate user row, or Stop/follow-up shell without the submitted row. Optional prompt-rail or persisted-search initialization may not delay, hide, or fail that transition.
- As soon as submit begins, the transcript projects the submitted user prompt from a nullable in-progress turn's params and keeps that row above the pending turn-body `Thinking` state until live response items arrive. The nullable turn contains no synthetic raw user item. In an active owned thread, the renderer owner appends and publishes that params-owned occurrence, calls `turn/start` through the owner-scoped app-server facade with the same `clientUserMessageId`, then rebinds the occurrence to the app-server turn id and publishes that rebind revision. A local conversation with no stream role resumes into renderer ownership before appending it; there is no direct main-owned submit branch. Follower submits wait for the owner revision before resolving.
- The owner-visible optimistic append is committed synchronously before native dispatch. Fresh Session creation separates native Thread response delivery from durable acceptance: the initiating manager installs the raw Thread shell, completes Session attachment, then prepares and publishes its first optimistic Turn. Window or host retirement releases unclaimed launch resources; only the admitted message identity can execute the first Turn.
- First-turn title work is scheduled at the first-turn-ready boundary, before the transport request is awaited, and never delays turn acceptance. When the Thread is untitled, Nodex first projects a local-only provisional title, then asynchronously asks an ephemeral structured-output helper Thread for structured metadata using `gpt-5.6-luna` at `low` reasoning effort with a 30-second deadline. The helper disables fanout, hooks, multi-agent execution, plugins, shell snapshots, tool suggestions, and web search. It runs without provider pinning and permits provider-model fallback. Pasted-text sources contribute bounded excerpts of at most 2,000 characters to generation context, including when the pasted text is the only meaningful input. Threads materialized from metadata without a first-turn callback use the same workflow: root Threads use their preview, while subagent Threads use the spawn prompt that created them only when that parent context is available; missing parent context produces no guessed title input. The generated write is conditional on the provisional title still being current; a manual rename wins, an explicit `skipAutoTitleGeneration` flag disables the workflow, and generation failure restores the provisional title rather than clearing the Thread name.
- Automatic title helpers use full access and automatic approval. Their prompt requests only structured title and description output; it does not authorize performing the task described by the source prompt. They do not install an app-tool allowlist, denylist or separate content-access policy. A helper without a bound product Session does not receive the Nodex Session execution bridge.
- Thread titles are compact display labels at canonical and presentation boundaries. Stored/native names are trimmed and projected from Markdown to visible text, with the original nonblank name retained when projection produces no visible text. Derived preview titles additionally unwrap delegation prompts, strip the final request-context prefix, and cap the visible label at 60 characters. Search keeps its own fallback order: projected name, raw trimmed preview, working directory, then Thread id. Durable transport metadata remains raw until it crosses one of these title boundaries.
- The structured title result contains a title of at most 36 characters and a nonempty retrieval description. The description is whitespace-normalized and capped to 100 characters after structured parsing. Nodex persists it in the shared `thread-descriptions-v1` local state only after the generated title wins its conditional write; `list_threads` exposes it as `summary` when available and otherwise falls back to a distinct Thread preview. A description write failure never rolls back a committed title.
- Canonical conversation state records whether the current title is the last successfully generated title. Manual title changes clear that ownership. A completed root, non-ephemeral Thread becomes eligible for automatic title reconsideration only after two consecutive assistant Turns emit the standalone `::thread-purpose-changed{}` checkpoint and all pending continuation work has settled. Reconsideration forks the source Thread with prior Turns excluded, uses the same full-access, automatic-approval execution policy, and is deliberately conservative: a null structured result preserves the current title. A replacement commits only while the current title still equals the generated title observed at the checkpoint, so a concurrent manual rename always wins; its description is persisted only after that conditional title write succeeds.
- When the live user-message item later arrives, its canonical raw item remains in turn state for protocol identity. It is deduped against the params-owned user row only when its `clientId` matches the submitted `clientUserMessageId` or its input is structurally equal and only the reference-approved metadata prelude precedes it. A user message after actual turn work projects as a `steered` lifecycle marker even when the client id matches. Incremental item notifications must apply the same whole-turn duplicate policy as resume, rebind, paged hydration, and export projection.
- A user message that represents a thread-goal submission carries a canonical `goal: true` transcript marker, including locally synthesized `/goal ...` rows and app-server `userMessage` items. The user bubble renders a persistent footer status, `Sent as goal`, with the goal target icon. This marker must survive normalization, transcript projection, duplicate merge, owner-published patches, and restart recovery; it is not inferred from the current saved goal alone.
- Editing a sent user message executes at the current conversation owner for persistent paginated history. The owner resolves the exact Session and stable edited Turn, then uses identity-based `thread/revert` before that Turn. The response updates history cursors and removes the reverted suffix, the edited Turn and every later Turn, from the owner document before the replacement is submitted through the ordinary native start path. Replacement input preserves non-text attachments and the prepared turn context; followers send the edit request to the owner and observe its stream.
- Forking starts from a stable Turn identity. The initiating manager sends the admitted native fork request, installs the returned child shell, and completes the durable Session attachment before resuming the child through ordinary ownership discovery. It then adds the fork marker to the child document. The parent can be a follower; forking does not transfer the parent conversation or reconstruct child history in Main.
- Active-thread actions execute through the current conversation owner and native request client. The owner mutates and broadcasts canonical state locally. Main retains product authorization and durable attachment ownership without projecting a second owner state. Followers forward source method payloads through the conversation peer service; returned stream revisions fence visibility when required.
- Follow-up prompts steered into an already-running turn insert an optimistic `steeringUserMessage` transcript bubble without an extra lifecycle label. Every user message renders its own attachments, including image-only steering, and remains visible with those attachments when Agent activity is collapsed. That bubble participates in the turn's canonical item order from creation, so later assistant output cannot render above the steer. Matching backend `item/started` `userMessage` notifications are treated as server echoes and must not accept or duplicate that bubble. When the matching authoritative backend `item/completed` `userMessage` arrives for the same target turn and equivalent input, the runtime accepts the bubble and appends a separate ordered `steered` lifecycle marker immediately after it. `steeringStatus` and the `steered` marker remain canonical state for ordering and queue recovery, but neither renders `Steering conversation` or `Steered conversation` in the transcript.
- While a turn is already running, composer submit intent resolves to an explicit action before submission: empty draft keeps `Stop`, non-empty primary submit is `Steer` or `Queue` based on the queue-follow-ups preference, and the alternate shortcut carries the opposite explicit action for one submit.
- Stopping an ordinary turn is immediate and leaves its latest turn `interrupted`. Once the thread is idle, the circular composer action becomes `Resume` only when the composer is completely empty, the latest turn remains interrupted, no saved thread goal or request surface owns continuation, and no other submit blocker is present. The Resume control keeps the ordinary 28px action geometry, uses a filled play glyph with `aria-label="Resume"`, has no ordinary tooltip, and shows the shared spinner while its request is pending. Typing or attaching anything replaces it with the ordinary Send action.
- Resume is an explicit owner-routed userless turn start. A no-role renderer first resumes and adopts thread ownership; a follower forwards to the current owner. The owner revalidates that the latest turn is still interrupted and no runtime, goal, request, steer, or duplicate Resume is active, appends one nullable in-progress turn with `input: []`, and sends app-server `turn/start` with that empty input plus the thread's current settings. It never replays the prior prompt, inserts `continue`, or creates a user-message row. A failed Resume removes its userless optimistic placeholder and restores the interrupted state so the action can be retried.
- `Queue` captures the complete Composer input under a stable message identity. When the selected execution host exposes an enabled native Thread queue, the app server owns its order and mutation through `thread/queue/*`. Captured app input requiring confirmation remains in the local peer-owned queue. Both queues stay visible together, with native rows first and local rows after them; a correlated native client-message receipt is shown once while its local row remains. The current local owner removes an ordinary captured copy after matching native acceptance, without consuming confirmation-bearing app input or later edits. Each action resolves the targeted row's real owner, and reordering preserves the order within each owner. Followers send local replacements and named remove/clear actions to the current owner, who persists and publishes them. Native add/update and queue resume require the owner; native reorder and manual send allow a stable follower, with Turn delivery routed through its owner. Each awaited mutation remains bound to its admitted host and owner incarnation. Ephemeral Threads use the local queue.
- Local automatic delivery first settles an unresolved dispatched message, even after reordering; otherwise it uses the FIFO head. It waits for an idle, ready conversation with an unpaused message. Confirmation-bearing app input additionally waits for the enabled native queue to load and drain before its current untrusted context is injected and acknowledged. An unsent ordinary local message keeps subsequent ordinary input local; a local app message alone does not prevent new native text from queuing. Manual native and local sends share the same cross-window admission and cannot dispatch concurrently. Hosts without native queue capability retain the complete local path.
- Durable native queue admission requires matching current host and nonpermission execution settings and input that needs no local preparation. Ordinary local and SSH hosts do not inherit those durable-only restrictions. Native durable rows have no manual `Steer`/`Retry` action; captured local rows retain their normal actions. A retired native host or changed admission cannot publish a late queue mutation. An authoritative matching native receipt settles an unknown add without sending that same client identity again.
- A selected row remains visible while its native request is pending. Native queue `start` removes the admitted server row only through the app-server queue contract; local queue delivery removes only the unchanged complete captured message after acceptance. Failure retains recoverable input and retry state at the owning queue boundary. Submission admission and owner routing prevent concurrent delivery of the same message across windows, and retries reuse the same client message identity.
- Successful native steering accepts its canonical message immediately. Unknown delivery retains the pending message until correlated native evidence settles it. Terminal completion does not fabricate a failed queue row or delete an unaccepted steering bubble. A queued message may fall back from an inactive-steer rejection to an ordinary start using the same captured message; the direct steering command and question replies never start a new Turn implicitly.
- Interrupted completion never starts queued work. `Queue paused because you interrupted` is shown while any such pause remains, and its `Resume` action clears only interruption pauses before reevaluating FIFO; it neither clears genuine failures nor starts the separate userless interrupted-turn Resume.
- Sending a fresh ordinary message while idle and an interruption-paused queue exists opens `Send message?`. `Send message` preserves the old rows and removes their interruption pauses only after the fresh start succeeds; `Clear queue` removes the old rows only after that success. Failure, Escape, and dismissal preserve both draft and queue. If the turn becomes active while the dialog is open, current Queue/Steer rules win and the stale idle policy is not committed. A fresh steer never resumes, clears, or drains the existing queue.
- Queue editing preserves the captured message identity and position. Replacements and removals are submitted through the current queue owner and persisted in FIFO order. A failed submission preserves the original message and recoverable draft.
- Automatic queue confirmation applies only to a proven dispatch of the same complete captured message. A matching client identity or visible native row alone cannot remove an unsent message or a later edit, including edits to captured execution settings. Late native acceptance retains its actual accepted input for reconciliation. Owner-only cleanup rechecks ownership and retirement after storage waits, before writing and confirming. Native delivery retains a later edit of the same row instead of removing it after an older send completes. Accepted native steering keeps its send admission and exact native receipt if queue deletion fails; the owner retries cleanup without sending the message again. Owner changes and admitted history restoration preserve that cleanup. Explicit unfinished history cannot confirm delivery; later completion advances the same item and older pages cannot undo it. Confirmed cleanup retires its native correlation so a late echo cannot recreate it. Outcome-unknown local delivery blocks automatic retries and remains removable or editable until matching native acceptance settles it.
- Dictation is a separate Electron-only authoring path, not realtime voice. Streaming updates editor-owned ranges while preserving selection, user edits, and IME composition. Finalization reconciles those ranges or passes the resulting draft through the ordinary submit path; it does not author a transcript item or bypass prompt reconciliation. Capture, recovery, global paste, and Voice behavior are owned by [Dictation Behavior](dictation-behavior.md).
- If a turn is active and no visible response item has arrived yet, the renderer may show a pending `Thinking` fallback at the bottom of that turn. It is render-time activity presentation and never a synthetic raw or bucket item.

- Resuming a conversation preserves its existing goal while native history loads. Background goal hydration applies only to the same manager lifetime and hydration attempt, and only if a newer goal has not replaced the captured goal. Unrelated transcript changes do not discard a valid goal response. A failed goal read leaves the existing goal intact.
- Native runtime status is an observation. An idle notification updates the conversation state without reactivating its goal, scanning subagents, or starting another Turn. The app-server owns autonomous goal execution; explicit goal controls remain available.
- Setting a goal objective or activating a goal waits for pending next-turn settings, or applies the supplied settings first. Other status changes do not update next-turn settings. An accepted status command dismisses its resume confirmation, and an empty goal response clears the current goal. Command responses leave completed-goal bookkeeping to native goal notifications; a newly completed goal notification retains the completed value and requests goal clearing.

## Server Request Lifecycle

- Canonical pending-request state stores each complete app-server request envelope in arrival order. Repeated deliveries are retained as repeated entries; request state is not timestamp-sorted, deduplicated, or rebuilt from method-specific view fields.
- `RequestId` remains its original `string | number` scalar across app-server, main, owner/follower transport, response routing, and server withdrawal. Numeric `73` and textual `"73"` are distinct. A type-tagged string may be derived only for UI/map identity and never replaces the scalar protocol id.
- Every stored request ingress raises the conversation's request-side `hasUnreadTurn` flag. Request completion, local response, and withdrawal do not lower it; only the separate explicit read-state flow may do so.
- Command/file approvals, direct user input, and private picker requests require a present, non-empty-string thread id; invalid ingress creates no state or response. Valid command/file and private picker requests are pending envelopes without synthetic transcript items. Permission, user-input, and supported MCP elicitation requests retain the pending envelope and may also upsert their request-caused synthetic item. Ordinary dynamic tool calls dispatch without entering the pending queue; every delivered occurrence with a truthy thread id executes and receives a response independently, including equal-ID occurrences, while a falsy thread id produces neither dispatch nor response. That guard is downstream of classification: validated picker/setup/onboarding variants remain stored request-plane rows in an isolated waiter lane even with an empty thread id, so a generic dynamic completion or owner transition cannot consume or reject them.
- `serverRequest/resolved` is a server-side withdrawal, not a client response. It selects the first request whose scalar id strictly matches, completes that request's permission/user-input/MCP synthetic item with the family-specific empty response state when applicable, then removes every pending envelope with the same strict scalar id. A missing match creates no synthetic item or value-level request change, but still publishes the reference's filtered-array structural transition. Empty-string thread ids remain valid for withdrawing previously stored specialized occurrences.
- User-input and MCP form replies carry their owning Thread id and select an exact pending occurrence in that Thread and request family before changing canonical state. They never infer a Thread by globally scanning request ids or consume a same-id occurrence from another family. Within the selected Thread, the canonical reducer requires the expected first strict-ID non-plan envelope; a local plan request is skipped, but a wrong-family non-plan collision blocks the action. Missing, already-resolved, and wrong-family responses are ordinary no-ops and do not force owner recovery. User-input replies complete their synthetic item before removal. MCP replies do the same: `accept` defaults omitted content to `{}`, while `decline` and `cancel` carry `content: null`; accepting a connector-auth elicitation responds to every arrival-ordered equivalent connector request before removing them. Native command, file, and permission approval requests are settled automatically by the provider owner and expose no manual response action.
- Specialized onboarding/setup/picker replies inspect the first strict-ID envelope without excluding plan requests, so a leading same-ID plan entry blocks the action. Direct option/setup pickers return their typed response payload. Dynamic option/setup variants return a successful input-text wrapper containing the JSON payload; onboarding verifies only the stored method/tool at reply time and wraps its normalized `answers`; setup-step replies must match the original `role`, `task`, or `context` request and wrap the response without its `step` discriminant. Stored duplicate requests receive at most one real protocol response while all same-ID canonical envelopes are removed.
- `currentTime/read` bypasses resume and thread-start request buffers, replies immediately with integer Unix seconds, and never enters conversation state. Attestation is claimed by the Endpoint before generated request-payload decoding, ignores request parameters, and never enters renderer request state; if its handler crosses a reconnect, completion targets the currently active physical session. Auth-token refresh and legacy approval request methods likewise create no conversation state and intentionally produce no renderer-owned response; unsupported MCP elicitation is declined immediately without storage.
- Pending request-card placement, blocking/bucketization, and raw-request-to-renderer projection are downstream view concerns. They consume the canonical queue and synthetic history but may not redefine request lifecycle or identity.

## Conversation Read State

- Request ingress can only raise `hasUnreadTurn`; explicit read/unread actions are the only user control that lowers or restores it. The thread unread registry is durable independently of project-session rows, while every linked session derives its sidebar unread state from the thread.
- Selecting an unread conversation in the sidebar or command palette, opening its visible transcript in a focused window, or interacting with that transcript by pointer, keyboard, or wheel marks it read. Prevented interactions and modifier-only key presses do not count. The session/thread context action toggles `Mark as read` and `Mark as unread`. Archiving clears unread state.
- A visible transcript continuously observes unread membership, the latest request and Turn, and accepted read activity. Desktop window focus is authoritative even when an embedded Browser owns DOM focus. Hidden transcripts and unfocused windows do not consume unread activity; returning to a focused transcript consumes activity received in the meantime. Accepted completion and new questions are acknowledged even when the local unread projection has not caught up, so reading a chat never requires leaving and reopening it to clear its blue dot.
- Manually marking the current chat unread survives unrelated renders and a simple blur/refocus without new activity. A new request, Turn, terminal outcome, or direct transcript interaction consumes it. Hiding and reopening the transcript starts a fresh read observation. Saved unread membership is usable before native history loads; an execution snapshot is not a second owner of Session unread state.
- Explicit read-state changes synchronize loaded conversations, thread summaries, linked sessions, and other windows through a standalone message. They do not call the app server or advance the revisioned conversation stream; an in-flight owner cursor rebases locally without a corrective publication. Repeated same-state changes are no-ops, an older owner publication cannot restore the superseded value, and archive eviction rejects late request/unread/dynamic resurrection.

## Request User Input

- Question shortcuts defer to active editors, dialogs and suggestion lists. Escape dismisses an accessible popup before the question; hidden or inert background popups do not intercept the question's shortcuts.

### Asynchronous questions

- An Agent can ask optional questions while continuing its current Turn. A live asynchronous assistant message opens a separate question panel above the ordinary Composer. In chats run by Agent execution, the question belongs to the Agent's request under [Agent Runtime Behavior](agent-runtime-behavior.md). In native conversations it belongs to its source message and Turn; ending that Turn does not end its answerability. Both choices and freeform questions are supported; a missing structured list falls back to one freeform question using the message text. These messages never create a blocking server request or mark the Agent's output as a final answer.
- The Question header and transcript answer action share the 16px speech-bubble question icon from the shared icon library. The panel uses the secondary elevated surface, square numbered choice markers and a hover arrow. Its custom-answer row keeps the pencil icon, rich editor, dictation and Skip/Next/Send actions on one line; questions without choices use a standalone bordered editor above the actions. Multiple questions show an `n of N` counter and fade between questions unless reduced motion is enabled.
- The panel shows one question at a time, preserves per-question drafts, and appends newly arriving questions without stealing selection. No option is selected or submitted automatically. Activating a choice acknowledges it for 180ms, then advances or sends; typed answers use Next/Send. Number shortcuts apply only outside an editor; the slot after the last option focuses the custom editor. Arrow keys navigate choices and the custom editor, and Enter confirms a selected choice with the same activation delay. Forward navigation requires an answer. Composition Enter never submits. Option selection preserves the separate custom draft, and a typed answer matching an option label remains editable as custom text. Standalone editors receive focus when the incoming question mounts, without modifying an outgoing question during its exit animation. The reply uses the shared rich Composer editor, including file and skill mentions, without slash commands.
- Skip clears only the current answer and advances. On the last question it sends any other nonempty answers or closes an empty batch. Close and Escape preserve drafts; unanswered questions can be reopened from their transcript row after the source Turn stops or finishes. Answering part of a batch leaves its omitted questions available for later answers. The panel temporarily hides while the ordinary Composer shows context suggestions.
- An unattended live panel closes after 30 seconds; Skip shows the remaining seconds only during the final 20 seconds. Editing, selecting a question, or interacting with its controls cancels that question's deadline; automatic standalone-editor focus does not. Expiry never sends an answer. Loading history does not open a panel; only an admitted live item-start event or its contiguous owner patch does so. A follower opens newly arrived questions, while hydration and resynchronization snapshots never reopen a closed panel.
- Authored non-secret question drafts and panel selection use Profile-backed state scoped by execution host, Thread and source question identity. They survive view release, transport reset and application restart without making presentation the owner of pending requests or accepted answers. Private text stays in memory. A source entity correction preserves its drafts, while a genuinely different source cannot inherit them. Accepted canonical user or steering messages are the answer authority, including replies in later Turns. Reconciliation updates untouched drafts while preserving local edits and rejects pending or unknown steering as accepted answers. History hydration makes existing questions answerable without presenting them as new live arrivals.
- Responses carry stable source question identities and one submission identity per answer batch. Main validates each source independently of its execution status, then routes the reply to the current running Turn or starts the next Turn when idle. Replies preserve service-tier and collaboration settings. Empty answers are omitted; one accepted subset never consumes its unanswered siblings. Each successful request is acknowledged before the next request in a multi-request batch, so a later failure retries only unacknowledged work. Success closes only answers still matching the submitted text, preserving new questions and edits made during delivery. Different batches can revise an earlier answer without reusing the first batch's receipt.
- Failures retain drafts and report through the global error toast. An explicitly inactive native target may be routed to the next Turn, but an unknown native or peer transport outcome retains its exact message and attempt identity until correlated evidence arrives. It never silently resends or becomes an ordinary recoverable follow-up. Late success, failure or echo cannot consume a replacement source or duplicate an accepted answer. A known native Turn-ID correction retries the same input once and preserves the source entity, selection and submitting state.
- Transcript projection expands structured questions into stable per-question identities while retaining their canonical source item. Pending and answered questions keep their authored position before their replies and later Agent output, and remain readable while surrounding work is collapsed. Automatically opened questions show Asking question(s); closed unanswered questions show Answer question. Question actions remain visible without expanding the Turn's work group. Accepted replies render paired question/answer content, including when an answer opens a later Turn. Opening-message, ordinary-message, steering and export projections share this readable presentation; copy/search never expose the transport envelope.
- Desktop question notifications follow the existing question preference and visibility policy. Clicking one opens its specific question only if the same Turn remains active; no inline notification reply starts a new Turn. Accepted answers and Turn completion dismiss matching notifications.

### Synchronous questionnaires

- `request_user_input` waits for a server-request response in both blocking and non-blocking modes; `isBlocking` controls inactivity resolution, not immediate tool completion. The asynchronous question tool instead returns immediately and receives later answers through steering. `item/tool/requestUserInput` presents a questionnaire in UI; selecting a preset answer is itself an explicit submission action rather than the first half of a select-then-confirm flow.
- While unanswered, `request_user_input` does not render inline in the scroll body. It appears in the composer shell above the input editor.
- After resolution, answered `request_user_input` remains visible as a compact `Asked N question(s)` disclosure row.
- That answered row stays collapsed by default and expands to reveal the question/answer pairs.
- A preset option is initially selected for roving keyboard focus but is never submitted without deliberate activation. Click, `Enter`, `Space`, and number keys `1`–`9` share one activation path. Ordinary user-input cards hold the activated option for a 180ms acknowledgement, then advance to the next question or submit on the last question. Setup-task suggestions use the same advance/submit contract without the acknowledgement delay. Approval, permission, authorization, and private option-picker forms remain explicit select-then-submit surfaces.
- Multi-question `request_user_input` cards preserve keyboard continuity: `Left` / `Right` moves to the previous or next question and restores the equivalent answer-control focus, `Up` / `Down` moves through preset options, `ArrowDown` from the last preset option can enter the free-form row, and `ArrowUp` from the start of that free-form field returns to the preset options. In free-form controls, unmodified `Enter` advances or submits, `Shift+Enter` keeps a textarea newline, and composition `Enter` is ignored.
- Ordinary questionnaire drafts are Profile-backed authored state keyed by execution host, conversation, exact request identity and source/question signature. Interleaved requests retain independent answers and question selection through navigation, remount, reconnect and restart. A different source or changed question signature cannot inherit a draft. Successful submit, explicit dismissal, timeout and server withdrawal clear only the matching request. Connection loss clears private text without discarding non-secret authored answers. Secret text and submission-in-progress state are never persisted.
- Native custom-answer restrictions, secret intent, explicit initial answers and required questions reach the shared questionnaire without being replaced by renderer defaults. Required unanswered questions cannot be skipped or submitted, and private questions disable dictation.
- Non-blocking user-input requests participate in main-hosted inactivity resolution; blocking requests wait indefinitely for an explicit response and cancel any earlier non-blocking request countdown in the same conversation. A non-blocking request presented in a focused window waits for 60 seconds of activity-free time before beginning a 90-second countdown; one not presented in a focused window begins the 90-second countdown immediately. A mounted task whose request surface is fully hidden behind another full-width panel is not presented. The visible badge is limited to the last 60 seconds. General pointer/keyboard activity resets only the initial inactivity wait, while any interaction inside the request card—including Dismiss or Escape intent—permanently snoozes auto-resolution for that request before the manual outcome is selected. Timeout first makes the request terminal, then sends an empty answer object through the ordinary response lifecycle and never chooses the preselected option.
- A supported MCP elicitation may provide integer `_meta.autoResolutionMs` from 5,000 through 300,000 milliseconds. Valid metadata starts that countdown immediately and timeout sends the ordinary MCP `decline` response with `content: null`; fractional or out-of-range values do not opt into this path. Snoozing an explicitly timed MCP request restarts the same explicit duration instead of permanently disabling resolution. Later presentation changes still use the ordinary foreground/background reevaluation rules for the tracked request.
- Browser-origin access elicitation is automatically accepted when the matching Turn disables approval prompts and runs with full filesystem/process access, for the browser-use connector's origin-access tools. The bundled Messages empty-form send path is automatically accepted only for a user-reviewed Turn with the matching in-progress Messages send call. A follower does not emit a duplicate automatic response.
- In an owned live stream, request-user-input and MCP elicitation request ingress is reduced by the renderer owner and published as revisioned stream-state patches. Main keeps the app-server JSON-RPC pending response only; it must not emit a competing source-null request patch for these rows.
- Native application MCP calls execute through Main's verified invocation owner. Retired local application dynamic calls fail before renderer forwarding or pending storage; historical results remain readable. Other supported dynamic requests retain their renderer-owner relay and original pending-request response boundary. Private picker requests remain canonical request-plane rows.
- URL-mode MCP elicitation requests that are not renderable as a supported HTTPS URL action or Codex Apps auth failure are declined immediately and do not create request cards.
- Genuine question and form responses remove their pending request and publish the completed item immediately. Responses route through the owning conversation identity, including when a follower missed the request patch. Native execution permission decisions use the fixed automatic provider response; their raw envelopes remain diagnostic history and do not own manual response controls. Scalar request identity controls resolution, and later duplicate resolution notifications are harmless.

## Plan Mode Follow-Up

- `item/plan/delta` streams incremental proposed-plan text only for an existing plan item; it must not create a proposed-plan card by itself.
- The final `item/completed` plan item `{ type: "plan", id, text }` is the authoritative proposed-plan content and overwrites any streamed draft text.
- `turn/plan/updated` remains the source for structured todo/checklist progress and must not be bucketed as a proposed-plan card. In an owned live stream, it is reduced by the renderer owner and published as a conversation patch.
- Every completed-plan signal type-scans and replaces prior same-turn `planImplementation` rows before appending one fresh item/request, even when its trimmed plan text is unchanged. The fresh request raises unread state and remains at the request tail.
- Removing a plan-implementation request completes every matching same-turn item without changing its existing timestamps and removes every same-turn canonical request. Starting another turn completes older plan-implementation items and globally removes stale or orphan request entries, including entries whose turn is outside the loaded page.
- When a completed turn’s latest visible plan item is non-empty, the composer swaps into an `Implement this plan?` request surface.
- That surface offers `Yes, implement this plan` and `No, and tell Nodex what to do differently`.
- Only the active parent `implementPlan` request exposes one request-owned intelligence footer below the rounded questionnaire card. It reuses the normal composer’s model, effort, and speed selector; background requests may remain above it, while every other request family continues to hide all composer controls.
- Accepting the plan waits for the displayed intelligence selection to commit, then starts one `Default`-mode follow-up turn prefixed with `PLEASE IMPLEMENT THIS PLAN:` using that exact model, effort, and speed. Starting the turn owns stale request cleanup so a settings or turn-start failure leaves the plan available for retry. Dismissal switches to `Default` before removing the request; freeform feedback preserves the current collaboration mode.

## Turn Rendering

- The renderer groups transcript entries by `turnId`, projects a flat renderer-item stream, bucketizes that stream, and then renders each turn in fixed block order:
  - `modelChanged`
  - `userMessage`
  - selected `modelRerouted`
  - tool activity blocks (`commandExecution`, materialized `patch`, `mcpToolCall`,
    `dynamicToolCall`, non-empty `webSearch`, `multiAgentAction`,
    completed `mcpServerElicitation`, completed `userInputResponse`, and
    `contextCompaction`) and the [Thoughts](#thoughts) among them, plus auxiliary
    subagent activity state
  - `systemEvent`
  - `assistantMessage`
  - post-assistant artifacts such as trailing automatic approval review
  - inline incomplete `mcpServerElicitation`
  - `proposedPlan`
  - render-time live activity fallback when the current open activity slice resolves to `thinking`
  - completed inline `turn diff`
  - trailing status markers (`remoteTaskCreated`, `personalityChanged`, `forkedFromConversation`)
- The parent activity resolver computes global state, the main activity-slice
  state, and one mutually exclusive fallback owner. The latest open group owns
  the thinking status only while that group is the latest visible unit, the slice
  remains open, and global state is `thinking`; otherwise an eligible fallback is
  standalone or absent. The fallback is not a canonical item, bucket entry,
  search unit, or persisted transcript row.
- Exploration, incomplete proposed plans, blocking requests, safety buffering,
  pending generated output, and final assistant output participate in the parent
  state machine instead of being leaf-level exceptions. A trailing visible
  assistant commentary closes the main slice; before final-answer output, the
  parent may still derive a post-assistant standalone fallback when no later unit
  owns the space. Commentary followed by later tools is not treated as trailing
  commentary for that later slice. The fallback uses the current Thought's
  status line. An active tool always keeps its concrete family label and never
  displays a Thought in that label.
- Raw item lifecycle uses one shared decision contract in main fallback and renderer-owner flows. A started item replaces the first same-ID slot or appends; an authoritative completed item does the same only after an existing same-ID/same-protocol-type row is found, except that commands, user messages, hook prompts, and subagent activity may complete without a start. Rejected orphan work completions can still establish turn timing, but never materialize a transcript row.
- The first raw work item in a turn stamps `firstTurnWorkItemStartedAtMs`; only `userMessage` and `hookPrompt` are excluded, so an `agentMessage` start counts as work and independently stamps `finalAssistantStartedAtMs`. Later events do not overwrite the first-work stamp, while duplicate agent starts may refresh the final-assistant stamp.
- Statusless reasoning, assistant-message, and plan items retain a lifecycle ledger
  in the canonical Turn. One occurrence is identified by item ID plus
  protocol type: duplicate lifecycle events are idempotent and delayed starts
  cannot reopen a terminal occurrence, while a later item of another protocol
  type may reuse the ID as a new occurrence. Owner/follower snapshots carry the
  ledger through checkpoint recovery.
- Command lifecycle timing is turn-owned. `item/started.startedAtMs` overwrites the command ID's observed start, while completion with a non-null duration backfills only a missing value from `completedAtMs - durationMs`. Final command payloads replace provisional raw state instead of resurrecting fields absent from the authoritative completion.
- Ordinary generated lifecycle items retain their raw protocol identity. Image-generation rows add normalized `src`; collaboration rows emit receiver-thread hydration and add ordered receiver metadata with an empty Turn list, without traversing receiver history; context-compaction rows add completion/source state. Review-mode markers remain hidden raw identities, so they count when resolving placeholder turns without creating transcript rows. Pending steering comparison uses the shared exact non-comment text plus image-count key, excludes comment-attachment label/placeholder inputs, and consumes a matching steer only on authoritative user completion.
- Active running turns with `firstTurnWorkItemStartedAtMs` project a first-class `workedFor` block before the first non-user item. That visible block renders as a plain `Working` label for sub-second elapsed time, then `Working for Xm Ys`, followed by a `border-current/20` divider. It is not a button and has no hover background or chevron. It is presentation-only timing and must not participate in the live-activity eligibility decision.
- Completed turns with first-work timing project the same internal block before the final assistant boundary, but completed collapsible agent bodies extract it as the single collapse-label input and remove it from both collapsed and expanded body rows.
- Only genuine user-input questions and MCP forms own interactive pending-question surfaces. Native execution permission envelopes remain diagnostic history.
- Unknown replay/app-server tool payloads do not render a generic transcript tool row. The mounted transcript only renders supported tool families with dedicated surfaces (`exec`, `patch`, `mcpToolCall`, `dynamicToolCall`, `webSearch`, `turnDiff`) and keeps any remaining raw tool metadata internal to the canonical conversation state.

## Thoughts

- A Thought is one reasoning item: a Codex reasoning summary section, or another Agent's thinking block or thought segment. Every Agent's Thoughts share one presentation that depends only on the Thought's text, never on the provider.
- A Thought's status line is its latest heading, meaning a whole line of bold text or a Markdown heading, including one that is still streaming; without one it is `Thinking`. Prose never becomes a status line. A status line is one line truncated at the Thread width wherever it appears: an activity group's thinking header, the Turn's standalone thinking row, and subagent rows.
- Thoughts are groupable activity in the order they happened. A streaming Thought is not running work, so an open group whose newest work is a Thought, or that has no running tool, is `thinking`.
- While a Thought without a heading streams as the newest item of a collapsed thinking group, its text streams in place under the status line in a preview of about five lines at the current chat font size that follows the newest text. The preview folds away when the Thought ends or work begins. A Thought with a heading shows only its heading. An expanded group shows the streaming Thought in the same bounded form.
- In an expanded group, a settled Thought is one line, its latest heading or the start of its prose, that opens to the whole Thought in a bounded scroll.
- A settled Thought on its own, such as one between work and the reply, reads `Thought for {time}`, or `Thought` when its time is unknown, and opens to the whole Thought.
- Agent Runtime Thoughts report when they started and how long they took. Native app-server reasoning reports no time.

## Collapse and Search

- Agent-body collapse applies after a renderable final-answer boundary has started, or after a settled turn has subagent activity. The turn must not be interrupted and must have a renderable agent body or auxiliary subagent activity. Collapse never hides user messages or final-answer messages, so a reply written as several messages stays visible in full. Codex reports each assistant message's phase; other Agents derive it as described in [Work and reply](agent-backend-behavior.md#work-and-reply), so every Agent's turns collapse the same way.
- Every eligible turn, including the newest completed turn, defaults to collapsed. A persisted disclosure state overrides that default, while active subagent activity prevents automatic collapse.
- In-progress turns without a final-answer boundary, interrupted turns, and turns without renderable activity do not expose an agent-body collapse toggle. Auxiliary null-anchor subagent activity may establish turn semantics, but it never creates an empty wrapper or toggle when there are no visible agent-body units.
- Collapsed historical agent-work labels resolve in this order: explicit completed worked-for timing, completed turn `durationMs`, then `X previous messages`.
- The completed historical `Worked for ...` row uses an inline left-aligned toggle button with no hover highlight, nested muted label spans, `aria-expanded`, a rotating `icon-2xs` chevron, and a separate `border-token-border-light` divider row. The chevron transitions between zero and ninety degrees over the semantic 150ms basic duration with the standard transition easing.
- Expanding a completed historical agent body animates height from zero to auto, fades from zero to full opacity, and translates from -8px to zero over 220ms with `cubic-bezier(0.33, 1, 0.68, 1)`; overflow becomes visible only after entry settles. Collapse keeps the body mounted while it reverses height, opacity, and translation over 150ms with `cubic-bezier(0.23, 1, 0.32, 1)`, then unmounts it. Reduced motion keeps a 120ms entry fade and 150ms exit fade while leaving height auto and translation at zero.
- The completed historical toggle is intentionally different from the active running divider, which is non-interactive.
- Search is modeled as explicit content units, not generic DOM scraping.
- `Find in thread` indexes visible user-message and every assistant-message content unit, including collapsed commentary. Rich text is projected through the shared Markdown-to-text contract; tool output, transport metadata, hidden markup and interactive widget documents are excluded. Native realtime transcript segments retain their literal text, and promoted inline Markdown contributes its visible text through the same search owner without inventing canonical Turns.
- `Find in thread` stays hidden until explicitly requested, normally through `⌘/Ctrl+F` while the Threads stage is focused.
- Searchable units preserve native item aliases and their canonical order across intermediate assistant messages, steering and later answers. Assistant unit identity does not change when another answer becomes latest. Resident search counts all literal occurrences while retaining a bounded match list. Persisted results establish native history order, reuse an already resident occurrence's local reveal identity, and append distinct resident matches, including voice-only history. A successful empty native result cannot discard resident matches.
- Search results reveal collapsed or virtualized content before highlighting the exact owning unit and occurrence. Realtime targets address the projected timeline entry directly; they neither require native Turn hydration nor write Turn disclosure state. Highlighting stays within explicit content units, does not traverse widget documents, and never substitutes the first visible match for a removed or unavailable target. Search caches reuse unchanged native item values and retire released or removed entries.
- An already mounted exact match centers directly without repeating whole-row placement. Every concrete Find activation first holds the viewport and establishes programmatic navigation, including resident matches that skip row placement; latest-turn following and delayed layout work cannot return that navigation to the bottom. Folded content still reveals through its owning unit before centering. Highlights carry only retained result identities and limits; query-preserving content changes, hidden boundaries and virtual row remounts refresh them in one 80ms batch without issuing another history search. Closing Find, changing its query/source or leaving the thread retires pending highlight work and clears its marks.

## Viewport, History, and Navigation

- Existing Codex Chat navigation starts measurement at Session selection, before its Thread view mounts. Back, Forward and deep-link route changes use the same Window owner, and route entry preserves the pending trace. Hydration, history readiness and visible paint have separate marks; supersession, route departure and application close settle the measurement. Pages, unknown or unbound Sessions, other Agent backends and Side Chat panels do not start a Codex navigation span.
- Metadata and the first bounded paginated history can become readable while execution resume is still pending. Reading that history does not authorize sending a Turn; execution readiness keeps its own state and failure handling.
- Timeline reads and active item retention are separately configured capabilities. Timeline pages preserve their own source-bound cursors and Turn boundaries. The retention policy protects all mounted views, blocks release during historical reading or pending navigation, and releases only recoverable completed prefixes. Older prefixes reload through an exclusive retained-item anchor, or the same Turn's tail page when that Turn was released completely. Ordinary background loading leaves released prefixes absent; explicit search and complete-history operations can restore them.
- History gaps expose loading and a local retry action on failure. Retry applies only while the same boundary still exists; replacing or leaving the view retires its failed requests. Search caches retain current item identities and text units and prune removed or released content.

- Long Chats virtualize complete turns. Unmeasured history rows temporarily reserve their estimated height; measured rows keep natural content inside a rounded measured wrapper. The latest row and a pending navigation target remain unconstrained while they are measured.
- Consecutive native voice segments share one measured transcript row, named by its first segment. Each segment keeps its own native identity and text subscription; Find mounts the shared row and highlights the addressed segment. Visible session boundaries, ordinary content, promotions and unloaded history gaps end the group. Receipts that produce no presentation, including a close for another session, do not split it. If a prepend or retained-prefix release renames the row, the transcript's content anchor resolves a still-resident native segment after the new rows and their measurements commit. It preserves that segment's viewport position, including when content is also appended below it; ref replacement on a retained row does not trigger restoration.
- The viewport scrolls natively from the top, and every position is expressed as distance from the bottom. Following the latest turn stays at distance zero, older content extends away from that anchor, and all rail, Find, restore, catch-up, and measured-height compensation paths use the same scroll controller rather than maintaining independent scroll modes.
- Content that grows or shrinks below a reader in history, including response space and Composer clearance, leaves the reader's native position unchanged. The mounted transcript retains one visible content anchor across row layout, gap changes and height measurements, including when older messages prepend inside the same Turn. Growth before that content, or before the reader's focused content, is compensated so it stays in place. Scrolling up after a submit therefore travels the full wheel, momentum or keyboard distance while response space shrinks below the reader, and space that leaves the visible area is released.
- Reading current viewport geometry does not publish a scroll position or consume pending user movement. The scroll owner compares native displacement with the last observed position, so even a small upward gesture can leave bottom-follow mode. Reapplying an unchanged position does not issue a native scroll command or interrupt an ongoing gesture.
- Scrolling into history pauses latest-turn following. Scrolling back near the bottom resumes it once response space is also nearly consumed; the catch-up action explicitly resumes it. A saved position within 24 pixels of the bottom restores at the bottom. A new submitted Turn establishes its own placement, and a position event without movement does not change user intent.
- The catch-up button floats above the Composer as a 32px circle with a 20px arrow, a subtle border, and no shadow. Its opaque surface fill stays unchanged on hover and press so transcript content never shows through it.
- Turn-height measurements follow the bottom only while the reader is still following there and no response space remains. Composer clearance changes keep a reader near the bottom at the bottom. Otherwise layout reconciliation preserves the history anchor, including while a native smooth navigation is already moving away from the bottom. Repeated measurements of unchanged clearance do not issue another scroll command.
- A latest-turn size change and the response space it consumes settle together, with viewport compensation accounting for the space change. Starting work after submit consumes response space and resumes following when that space is filled, without returning to a stale history position.
- Ordinary paginated resume loads the five most recent complete turns plus older-page metadata; an enabled timeline policy selects its separately bounded item timeline instead. Older history comes from the app-server turns API, not local slicing. Descending server pages are reversed into Nodex's oldest-to-newest timeline; live/latest turns win identity conflicts, and older pages prepend only missing complete turns or upgrade their recorded placeholder.
- Paginated resume leaves older history unloaded. Approaching the loaded-history boundary or explicitly navigating history triggers the guarded loader; legacy automatic completion follows the conditions in [Bounded History and Search](#bounded-history-and-search). Concurrent demands deduplicate, and prepending older turns preserves the user's measured visible anchor.
- Renderer-session memory restores one Chat's distance from bottom, measured virtual window, and latest-turn-follow state. Each mounted turn list captures the latest saved snapshot once; later updates cannot restart that restoration. Hiding the transcript or temporarily showing history-resume state preserves the reading position for the next mounted list. An empty viewport cannot overwrite it. Measurement, search and cleanup read committed presentation inputs. A suspended or abandoned render cannot replace the mounted Chat's restore identity or follow state. This is presentation memory, not SQLite or transcript authority.
- The user-message navigation rail is derived from visible canonical user-message occurrences. Stable occurrence keys include empty-text and attachment-only messages, while text search continues to index only non-empty content.
- The rail appears only when the thread shell has enough physical room. Activating a row reveals a collapsed or virtualized target before scrolling to its message surface; click navigation is smooth and pointer scrubbing is immediate.
- Find reveal is cancellable and two-phase: it first expands/mounts the target, then owns highlighting and final centering. Selecting another result aborts the earlier reveal so delayed long-history work cannot steal focus. A match crossing formatted text uses several highlight fragments with one result identity; navigation centers its first fragment without replacing the document's formatting elements.
- Latest-turn follow, response spacing, submit placement, and the catch-up affordance share one footer/viewport contract. Reduced motion snaps the presentation without changing follow state.
- Embedded Side chats reuse the connected conversation stage but omit the root header and floating summary, retain their own composer, and cannot recursively create or fork another Side chat.

## Message Rendering

- Selected transcript text uses the window's native context menu. On macOS,
  ordinary non-editable text offers `Look Up “…”`, `Search with Google`, and
  `Copy` in that order, with separators between them and `⌘C` on Copy. Look Up
  opens the system definition panel; search opens the selected text in the
  default browser; Copy preserves the actual selection. The Look Up label trims
  the selection and truncates it to 25 display columns without shortening the
  copied or searched text. Links omit Look Up. Editable text retains native
  Cut, Copy, Paste and spelling actions. Surfaces that handle their own context
  menu keep that interaction without a second native popup.
- Assistant answers, promoted Markdown and assistant realtime transcripts share one conversation token parser and direct React renderer. Ordinary source search derives compact Markdown text independently of rendering, preserves formula delimiters and normalizes directives outside top-level fences; Voice segments index their raw text. Independent document, plan and reasoning surfaces retain their own document Markdown policy. A completed conversation formula remains visible as authored text while its rendering leaf initializes.
- Fenced code in assistant answers and user messages uses the shared read-only Code presentation defined by [Page Editor Code Block Behavior](./nfm-editor-code-block-behavior.md#read-only-presentation): one subdued `--code-block-bg` surface, no nested header/body card, no line numbers, and a language label with Wrap and Copy that appears on code-block hover or while the header has keyboard focus. Syntax colors follow the light or dark scheme. Conversation code leaves consume the shared highlighter directly, without an implicit parser provider.
- Thread fenced code copy preserves the original source characters and line breaks, including Unicode separators, and goes through Nodex's clipboard fallback path so Electron permission/API gaps do not make code-block Copy inert.
- Transcript markdown rendering remains streaming-safe for in-progress turns.
- Transcript Markdown shares immutable parsed syntax while each mounted document owns its committed element identities and animation lifetime. Discarded renders do not consume those identities; appending text and completing a response preserve existing controls and focus. Completed text uses ordinary text nodes. Assistant answers, promoted Markdown and assistant realtime transcripts preserve authored line breaks; code display and copying preserve literal whitespace. Nested list normalization and heading presentation do not change the captured source.
- Conversation math keeps a single dollar literal; inline dollar fences close with the same run length, while display fences can close with a longer run. Slash math and a fenced `math` language use the same typed math leaf. Four-space indentation remains code. An unfinished display fence consumes its remaining payload without interpreting its opening-line suffix as TeX. Parse errors stay hidden while the owning message streams and expose the authored formula after completion; ordinary failures retain plain TeX. Rendering disables trusted HTML and keeps macros local to that formula.
- Complete directive attributes permit normal ordering, quoted escapes and typed literal values. Incomplete display declarations cannot acquire interactive resources. Unknown declarations remain their full authored text; consumed metadata remains separate. Registered `github-details` disclosures retain their authored summary without inventing a missing label, and initially open only for the parsed string `open="true"`. They preserve the user's disclosure state while a preceding paragraph, unrelated streaming tail or completion changes, and Find reveals their content through the same mounted disclosure. Retiring the document releases that reveal capability.
- Non-commentary assistant answers, native inline Markdown and retained assistant voice text use independent adaptive presentation buffers. Existing history appears immediately; completion, replacement, a new message identity, or reduced motion immediately shows the full source. Search and full-message copy retain canonical text. A streamed message that its settled turn names the reply keeps its rendered Markdown rather than remounting. Native inline Markdown follows its actual Turn status even when its presentation row is marked completed; embedded wide widgets remain ineligible for expansion while that Turn streams.
- Ordinary follow-ups and queued messages can carry saved widget model state as bounded untrusted context. Queue execution reads current state. Private state is never sent to the model, and steer, automation and delegated tool messages do not implicitly collect passive state. A context fingerprint advances only after a confirmed injection; ordinary resume preserves it, while accepted compaction and history revert invalidate it. Confirmed chat deletion removes related widget records; auxiliary storage failure is diagnosed without retaining an already-deleted chat.
- Every `imageView` item remains dedicated agent activity. Only raw-consecutive image-view items fold into one row; any intervening raw item, including a hidden review-mode marker, ends the run. Each row is collapsed by default, summarizes as `Viewed an image` / `Viewed N images`, and expands to a horizontally scrollable strip of 80px thumbnails. Thumbnails open one keyboard-accessible preview sequence with previous/next navigation among resolved images. Navigation retains the same dialog, and closing returns focus to the selected image's thumbnail. Review-mode markers (`enteredReviewMode`, `exitedReviewMode`) remain hidden.
- An inspected local image loads its recorded absolute path through the owning conversation's execution host when its thumbnail mounts. The thumbnail and its preview share the resolved image bytes; opening the preview does not reread the original file. Loading reserves an 80px slot. A failed read shows a compact 64px `Failed` tile with the accessible label `Image failed to load`, without a retry button. Folding and reopening the activity mounts a new read attempt.
- Local inspection reads share a cache identified by execution host, conversation and normalized absolute path. Successful entries remain fresh and do not retry automatically; unused binary entries are collected after five minutes. Inspection reads do not keep a cache subscription, so that lifetime starts when the read settles, independently of whether its thumbnail remains mounted. A mounted thumbnail retains its resolved bytes after cache collection or source-file deletion. Reopening after collection reads the recorded path again; a missing or unreadable path can then fail. This cache does not preserve inspected files across application restarts or create permanent conversation attachments.
- Image-generation output renders as one post-assistant gallery for the turn. Pending output reserves up to four square slots with the animated dot-field placeholder; completed images retain natural ratios when they fit and switch to a four-slot carousel when they overflow. Completed image output is omitted when the turn's end resources contain a presentation, while still-streaming pending output remains visible. Thumbnail and full-image descriptors resolve independently; the full descriptor owns display, download, and drag data. Gallery controls reveal on hover/focus, retry failed preview loads at most twice for each resolved preview URL, support copy-drag payloads, and open a keyboard-navigable image preview with download support. Edit and Canvas behavior is owned by [User Attachment Image Editor Behavior](./user-attachment-image-editor-behavior.md).
- Hook executions belong only to the Turn's typed `hookRuns` sidecar; they never acquire transcript item IDs, activity rows, or expandable body content. Completed turns expose a Hooks indicator in the assistant action row before the timestamp, including image-only replies. While a turn is active, its statistics are hidden. A not-sent prompt receives the indicator when no selected assistant reply or image gallery owns it; ordinary hook-feedback user rows do not repeat the assistant statistics. Blocked submit hooks expose their nonempty feedback below the user message, preserving line breaks, and replace the generic delivery-failure label with a source-aware Hooks settings link. Failed task launches retain the generic delivery status and never imply a Hook rejection.
- The Hooks tooltip uses a detailed event/source grid for `STEPS_COMMANDS` (the default), and a counts/output summary for `STEPS_PROSE` and `STEPS_EXECUTION`. Detailed rows show normalized source labels, optional trimmed status messages, and non-context output; only adjacent runs with identical event, raw source, status message, and visible output tone/text merge. Raw status and timing do not affect merging. Summary counts include all runs, count only `blocked` as Blocked and `failed` as Errors, and omit zero error/block counts. Context output is never displayed. Error, feedback, and stop output use warning emphasis in the detailed tooltip; warning output is secondary. The indicator has no click action, opens above the action row on hover or keyboard focus, and closes on Escape or blur.
- A hook feedback user row is not editable and links to Hooks settings. Feedback matching trims both the displayed user message and each Stop-hook feedback entry, retains every exact source match, and scopes the destination only when all matches normalize to the same source. Managed/system sources normalize to Admin; project links include the turn cwd only when present; plugin links do not guess a plugin id; a blocked hook prompt has no sent timestamp. Ordinary clicks open the in-app settings route, while modified clicks retain normal link behavior.
- Active-thread streaming is revisioned and frame-batched. An established renderer
  owner receives sequenced app-server notifications, reduces the shared canonical
  document, applies the scoped view projection, and commits owner-visible state
  synchronously before its serialized publication outbox sends the next snapshot
  or patch. Prose, MCP structural repair, item/turn lifecycle, thread metadata,
  requests, and errors publish through that boundary. Command output deltas,
  file-change patch updates, and terminal input update only the owner until a
  later item lifecycle publication or explicit snapshot carries the item state.
  Terminal prose drains before final
  authoritative lifecycle state. Main runs the same canonical reducers for
  no-owner recovery facts, but an active owner's accepted replica advances only
  through an accepted owner publication and main never publishes a competing
  source-null transcript.
- Every accepted replica has an ordering checkpoint `(protocolVersion, ownerEpoch, revision)`.
  Main verifies source ownership, epoch, contiguous revision, and patch applicability before
  mirroring the exact owner document. Live publication never serializes transcript contents for
  hashing. Host recovery state cannot substitute its newer history or lifecycle projection into
  an accepted owner revision. Rejection returns the current accepted checkpoint/snapshot.
  With followers, forwarded notification sequences are acknowledged after publication succeeds.
  Without followers, live updates remain local and acknowledge transport delivery directly; the
  next follower requests a fresh owner snapshot, followed by any changes received before its ACK.
  History commits update the owner-local canonical document and request snapshot publication
  through its peer stream. A subsequent read uses that document directly.
- History reads and search hydration belong to the manager's native client. A completed page
  merges against the current canonical document, retaining live updates received during the read.
  Superseded generation, boundary cursor, or item-pagination-object results cannot install.
  Automatic gap loading serializes requests for the nearest
  boundary within 800 pixels of the viewport. Bounds observed during a request replace the pending
  selection; the next iteration uses the latest bounds. A boundary applied during that run is not
  loaded again in the same run. Failed or stale requests can retry on a later viewport observation,
  even when the bounds are unchanged. Clearing the viewport stops subsequent requests.
- Large live and completed items retain their full content and protocol identity. Memory
  accounting is observational and cannot evict loaded history or replace valid content
  with an output-omitted placeholder. Physical pages retain their exact continuation cursors;
  a large page is never partially consumed while advancing past omitted items.
- Shared conversation documents omit absent optional object members before
  checkpointing and patch generation. Clearing an optional field produces a removal;
  arrays preserve their ordered entries and reject invalid or missing values.
- A follower first applies an owner snapshot behind a per-client barrier and sends
  an explicit snapshot-applied ACK. Main does not include that follower in delta
  fanout until the ACK matches both the sent and current checkpoint. Later patches
  require the same source owner, owner epoch, exact base revision and next
  revision. A missing snapshot, owner mismatch, epoch
  mismatch, revision gap, patch failure, checkpoint mismatch,
  or transport reset requests an explicit snapshot resync instead of best-effort
  merging. Replacing an owner increments the epoch, invalidates follower barriers,
  rejects stale publications/ACKs, and requires a fresh snapshot before deltas.
- Owner adoption/resume and follower `thread/resume` carry the same mandatory
  checkpoint and exact shared document as a relayed snapshot. Renderer state
  verifies the returned revision and retains that exact document as the
  publication/patch CAS baseline before deriving the materialized UI snapshot.
  A follower treats resume data as provisional and waits for a fresh owner snapshot before
  completing attachment. It can then apply the first contiguous delta, and an owner can
  publish its first optimistic mutation plus any normalization delta, without an
  intermediate baseline mismatch or synthetic epoch.
- Terminal item lifecycle is monotonic for one `(itemId, protocol type)` occurrence:
  delayed starts cannot reopen a completed/failed/interrupted occurrence, while a
  same-ID item of a different protocol type may replace that slot as a new
  occurrence. Owner, main recovery, snapshots, and followers carry the same
  lifecycle state. Renderer turn models are cached by an immutable render
  revision that observes item identity plus lifecycle/content fields, so reasoning
  deltas, patch snapshots, command output, MCP results, and terminal states refresh
  without rebuilding a second tool topology.
- Command output is coalesced for 50 ms, targets the latest matching command
  item, preserves the latest 20,000 UTF-16 code units with an explicit truncation
  marker, and drops missing conversation/turn/item targets.
- Before applying item or turn completion, renderer owners and Main fallback
  synchronously flush the entire pending command-output queue, then drain earlier
  prose. An authoritative completed command replaces provisional output, including
  null or empty output, and can materialize without a retained start. The queued
  timer has no old bytes left to append after completion. Accepted owner sequences
  retain their normal acknowledgement path through this ordering barrier.
- Live command deltas append without content deduplication or terminal-status
  filtering. Identical bytes can represent separate output occurrences. Start/resume
  buffering separately accounts for a buffered suffix already covered by the
  installed snapshot; that baseline accounting does not suppress later live output.
- Only sequenced owner notifications mutate renderer command output. Main handles
  no-owner fallback canonically; an unsequenced fallback broadcast cannot become a
  second renderer writer when ownership changes.
- File references in transcript markdown are semantic controls rather than ordinary filesystem anchors. Project and Session scenes additionally expose New tab and New window using their own Browser surface capabilities; Library, Inbox, and empty scenes do not offer those destinations. Native menu choices retain the captured URL and selection and stop when their source link is removed, replaced, or inert.

Invalid or reversed ranges are discarded at the tab-state boundary. The Files header `Open`, unsupported/oversized fallback action, and explicit `Open with` choices all use the configured external opener router; a failed opener may fall back to Finder, but no React click event is ever passed as an opener id.
- Reasoning text deltas accept safe non-negative integer part indexes and densely fill omitted preceding parts with empty strings. Canonical hydration, completion and replay retain every supplied part; no client part-count cap truncates the stream. Part-added announcements are observational, and the subsequent text delta materializes its indexed parts.

Inline/non-primary user messages in a turn render no timestamp node.

Each visible turn contributes a user marker from `turnStartedAtMs` when it has primary user input and an assistant marker from `finalAssistantStartedAtMs` when it has an assistant message. Invalid or missing marker timestamps are ignored.

After an assistant marker, a later user marker receives a separator only when the gap is strictly more than one hour; a later assistant marker uses a strictly-more-than-ten-minute gap. At most one separator appears per turn. - `Edit message` attaches to the last user message of every settled turn that carries one, not only the latest. Later steer or follow-up `userMessage` items in the same turn do not get user-bubble actions.

While the editor is open, its row and backing history stay resident even outside the virtualized window, preserving the same textarea, focus and selection without mounting the intervening rows. Cancel or a successful send releases that retention; a failed edit keeps the editor open with the error reported. Inline images, execution-host file images, and remote pointers preserve distinct resolution paths; successful images and loading slots are 80px, while failed reads show the compact 64px `Failed` tile without a retry button. Only resolved images enter the message's shared preview sequence. Ingress, source selection, and trust rules are specified in [Composer Image Attachments Behavior](./composer-image-attachments-behavior.md).
- Assistant transcript actions are owned by the turn's bucketized final-assistant lane and render after assistant prose and assistant-after artifacts in this order: `Copy`, `Fork chat from here`, optional Auto-review statistics, Hooks, completed-goal duration, memory citations, used Skills, then timestamp. - Completed turns expose metadata only when available: Auto-review opens a persistent dialog with decision counts, expandable commands, and reasons; memory citations show their notes; used Skills resolve their catalog using the conversation host and open local source files using the conversation working directory; unavailable remote file-open actions are disabled rather than redirected to the local filesystem; a completed goal shows its elapsed time on the completing turn. ## Tool and Activity Rendering

- Tool activity passes through one production classifier and one topology
  projector. Hidden items do not break adjacency; standalone items flush the
  current run; and every maximal run of groupable Thoughts, exec, materialized
  patch, non-empty web search, ordinary MCP, registered groupable dynamic tool,
  and in-progress Auto-review items first becomes a raw group. A settled non-active singleton is then demoted to its standalone family
  row, except a file-change singleton remains grouped when it does not represent
  exactly one ordinary changed file or when it contains visualization activity.
- Group membership is finalized before React leaves render. Each raw group keeps
  immutable full entries for state, facts, identity, and icon selection, plus a
  separately filtered body-entry list for expansion. Running ordinary
  read/search/list rows, defensive empty patches, and summary-only dynamic rows
  may be absent from the body without changing the group's header facts or
  topology. React consumes this presentation and never runs a second grouping
  pass.
- Completed agent-body collapse partitions the projected activity units into
  canonical expanded order, collapsible units, and collapse-persistent units.
  Steering messages with a projected steering status, hook-feedback user
  messages and final-answer messages that later work keeps inside the body
  remain visible below the `Worked for` divider while agent activity is
  collapsed. Collapse-persistent user messages use compact horizontal hover
  actions so action chrome does not reserve a second transcript row; consecutive
  bubbles retain the canonical 16px item gap. Expanding restores every unit to
  its original transcript order and ordinary action layout without duplicating
  the persistent messages.
- Tool and action surfaces use the shared local icon asset module:
  - semantic tool glyphs cover command execution, file edits, web/search, code search, list-files, approvals, denials, skills, hooks, plugins, connectors, and generic source fallbacks
  - decorative row glyphs are hidden from assistive technology; website favicons use decorative empty-alt images, while source logos expose meaningful alt text
  - icon rendering is surface-specific, not universal: collapsed activity headers and top-level command/web/MCP surfaces may show glyphs, while nested collapsed-activity body rows often stay text-only
  - visible activity glyphs use the documented `icon-xs` muted contract, chevrons use `icon-2xs`, and source/card glyphs use `icon-sm`

Grouped web-search headers use the semantic web-search glyph, while expanded/detail web rows render the favicon only when a `faviconUrl` exists; they do not add a globe fallback when no site favicon was resolved.

Web rows do not pre-group before the generic v2 pass. A live activity group whose open slice is web-search-owned renders `Searching the web` plus the latest active query/detail; a settled group renders `Searched the web`, and expanded bodies render direct detail rows without a nested web-search header.

- MCP, plugin, connector, and elicitation rows resolve source logos from available metadata, Browser Use / computer-use source identifiers, connector/plugin logo URLs, then the generic source fallback.

Node REPL and CUA REPL use the terminal glyph when richer source identity is absent. Expanding a withheld result hydrates only its addressed runtime item, and image descriptors resolve the original result-content index through the owning conversation. Native call identity remains distinct from the runtime row identity used for detail reads.
- Completed MCP server elicitation is an agent-activity leaf, not a trailing raw-payload row. `mcpToolCall` completion summarizes as `Requested permission`; other supported kinds use `Completed request`. The default-collapsed body preserves one question/answer pair, with answers `Accepted`, `Cancelled`, `Declined`, or `Completed`; tool suggestions use their suggestion reason as the question. Incomplete and unsupported OpenAI-form elicitations do not render this completed leaf, while an OpenAI form containing an `openai/imagePicker` property remains eligible for ordinary v2 grouping.

Renderable MCP app/resource rows and registry-declared standalone dynamic tools are standalone barriers. Computer-use and Browser Use calls without an app widget remain groupable. MCP source identity and dynamic registry metadata still drive labels, icons, summary facts, completed-part dedupe, specialized leaf rendering, and summary-only body omission after group membership is fixed.

## Composer Shell

Conditional next-message suggestions follow [Composer prediction behavior](composer-prediction-behavior.md), including generation, empty-editor acceptance and cache lifetime.

- Nonempty Composer context search considers the complete eligible inventory and displays the best eight results with stable provider ordering. Skill search retains all matching skills and accessible enabled apps, including matches beyond the first eight.

- Background child-agent rows remain visible alongside genuine pending questions.
- While request cards are present, the normal freeform composer editor is hidden.
- The active parent `implementPlan` request is the sole exception for composer controls: it renders the shared intelligence selector as a sibling footer below the request stack, without attachment, context-window, dictation, or send controls. Auto-review replacement and non-plan parent requests suppress that footer.
- Request cards use one dispatcher family:
  - `userInput` and `implementPlan` use the same shared questionnaire shell with `Dismiss` and keyboard-first multi-question navigation
  - `mcpServerElicitation` uses the dedicated MCP card family instead of a generic JSON approval card; URL elicitations open the provided URL on accept, while `form` and `openai/form` elicitations render supported schema fields as inputs, send `decline` on `Skip`, send `cancel` on close/Escape, and send `accept` with structured form content on `Continue`
- Unanswered `userInput`, synthesized `implementPlan`, and live MCP elicitation requests do not render inline in the transcript scroll area.

## Persistence and Recovery

- Conversation state owns identity, host, title, model settings, runtime status, rollout path and millisecond timestamps directly. Generated Thread metadata is cached independently without Turns; a server title can differ from the retained conversation title. Metadata arrival refreshes collaboration receiver details without hydrating the receiver's transcript, and removing the conversation clears its metadata entry.
- Snapshot requests never invoke `thread/read` or `thread/resume`. They serialize and rebroadcast the current manager-owned canonical conversation; when no loaded record exists, that serialization boundary may first bootstrap the manager from a persisted Codex session artifact.
- Every explicit renderer bootstrap boundary—snapshot request, bounded resume, older page, search island, side-chat start, follower snapshot, and revert—materializes each resident Turn through the same canonical projection before applying the conversation snapshot. Partial Turns preserve their opening input and explicit item boundary rather than pretending to be complete. This keeps params-first user rows, raw-echo suppression, request/review overlays, hook feedback, generated images, and hidden item identity identical to live projection. Generic snapshot application does not perform an implicit second projection.
- Reopened threads first use the manager's canonical record or its bootstrap-only persisted-session recovery input. Explicit history reads and paged resume responses then materialize generated whole turns exactly once; the renderer does not replay or re-normalize those projected rows.
- Explicit active-thread resume requests metadata first and hydrates a tail through the selected paginated-history or inline legacy-page contract. A legacy response without its requested inline page falls back to a full history read. Inline pages preserve their supplied item views and continuation state; the requested page size is not a response-rejection quota. The renderer awaits durable acceptance before its final canonical transition, owner assignment, buffered same-thread ingress replay and snapshot publication. Main and renderer reject acceptance from a retired native generation, including retirement while durable metadata is being persisted. Subsequent legacy completion follows [Bounded History and Search](#bounded-history-and-search). Failed resume leaves the current conversation resumable without publishing stale history.
- Restart recovery depends on the host manager's canonical conversation state, bootstrap-only persisted-session input, and explicit resume/history paths—not on a second renderer-side transcript authority.
- Live and restarted threads must show the same visible conversation history for the same underlying session state.

## Non-Goals

- Nodex does not expose internal bootstrap/session context as a developer-visible transcript row in this release.
- Nodex does not treat raw rollout storage as a direct UI contract.
- Browser/HTTP transport does not support `codex:*` methods in this release.

### Steering across history hydration

History merges retain local steering rows even when the returned Turn contains more items, refresh matching assistant messages, and preserve completed heartbeat Turns while any steering row still awaits its server echo. A correlated persisted user message accepts the matching steering row and leaves a `steered` marker at the server item identity; the local row precedes that marker. The opening user message remains distinct. Paginated resume and steering relocation use the target Turn’s explicit opening identity before client/input inference; a null identity confirms that no item is the opening, while an unset identity permits the normal correlation fallback. When a steering target becomes resident, its row moves into that Turn and reconciles any already-loaded echo. Live completion and hydration share the same matching and acceptance helpers.
